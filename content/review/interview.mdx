أسئلة بتتسأل فعلًا عن Clean Architecture وCubit وdio وكل موضوع في الكورس، مترتبة بأسبوعها في الخطة. جاوب بصوت عالي الأول، وبعدين افتح الإجابة النموذجية وقارن.

### SOLID

<Question id="interview-1">
<Ask>اشرح Dependency Inversion بمثال من مشروعك.</Ask>
<Answer>

الـ use case AddBookToLibrary بيعتمد على LibraryRepository، وده interface معرّف في الـ domain. الـ LibraryRepositoryImpl في الـ data بيعمل implement ليه وبيستخدم dio وdrift. فالـ domain مايعرفش أي framework، وأقدر أتسته بـ fake، وأغيّر الـ DB من غير ما ألمسه.

</Answer>
</Question>

<Question id="interview-2">
<Ask>الـ sealed classes مش بتكسر Open/Closed؟</Ask>
<Answer>

أيوه، عن قصد. في المجموعات المقفولة زي الـ Failures والـ states، الأهم إن كل حالة تتعامل صح، فالـ compiler يجبرني أعدّل كل switch. في المجموعات اللي بتكبر زي الـ interceptors بطبّق OCP. الاختيار بينهم حسب طبيعة المجموعة.

</Answer>
</Question>

<Question id="interview-3">
<Ask>إزاي تتأكد إن الـ fake بتاعك مطابق للـ implementation الحقيقي؟</Ask>
<Answer>

بالـ contract tests: test suite واحد بياخد factory للـ repository، وبشغّله مرة على الـ fake ومرة على الـ implementation. لو الاتنين عدّوا، الـ fake بيحترم نفس الـ contract (LSP)، وتستات الـ Cubit اللي عليه موثوق فيها.

</Answer>
</Question>

<Question id="interview-4">
<Ask>إمتى interface صغير أحسن من repository كامل؟</Ask>
<Answer>

لما اللي بيستخدمه محتاج جزء صغير منه، خصوصًا بين features. زي notes اللي محتاجة findById بس: بعمل BookLookup، فالـ notes مش مربوطة بتغييرات الكتابة والمزامنة، والـ fake بتاعها method واحدة (ISP).

</Answer>
</Question>

### الأسبوع 1: الأساس والحدود

<Question id="interview-5">
<Ask>إيه هي الـ dependency rule؟</Ask>
<Answer>

الـ imports بتشاور للداخل بس: الـ domain مايعرفش أي حاجة عن الـ UI أو الـ data أو أي framework. عمليًا: الـ domain مافيهوش import لـ Flutter أو dio، والـ data بتعمل implement لـ contracts معرّفة جوه الـ domain (dependency inversion)، فالاعتماد بيتعكس.

</Answer>
</Question>

<Question id="interview-6">
<Ask>feature-first ولا layer-first، وليه؟</Ask>
<Answer>

feature-first: كل اللي يخص feature في مكان واحد، فتقدر تشيلها أو تسلّمها لمطور تاني أو تحوّلها لـ package بسهولة. الـ layer-first بيخلي أي تعديل صغير يلف على 3 مجلدات بعيدة عن بعض، وبيسهّل الـ imports العشوائية بين الـ features.

</Answer>
</Question>

<Question id="interview-7">
<Ask>Clean Architecture مش over-engineering؟</Ask>
<Answer>

ممكن تكون، في app صغير أو CRUD عمره قصير. قيمتها بتبان مع business logic حقيقي، أو فريق، أو مشروع هيعيش سنين، أو تستات جدية. أنا بقرر حسب المشروع، وممكن أبدأ بـ MVVM وأضيف domain لما الـ logic يكبر.

</Answer>
</Question>

### الأسبوع 2: الـ Domain والأخطاء

<Question id="interview-8">
<Ask>إيه الفرق بين الـ Entity والـ DTO؟</Ask>
<Answer>

الـ Entity بتمثل مفهوم في الـ business بقواعده، ومش بتتغير لو الـ API اتغير. الـ DTO بيمثل شكل البيانات على الشبكة أو في الـ DB بالظبط. الـ mapper بيترجم بينهم، فتغيير الـ API بيقف عند الـ data layer.

</Answer>
</Question>

<Question id="interview-9">
<Ask>ليه Result بدل ما ترمي exceptions؟</Ask>
<Answer>

الـ signature نفسها بتقول إن العملية ممكن تفشل، فاللي بينادي مايقدرش ينسى يتعامل مع الفشل. ومع الـ sealed classes الـ compiler بيجبرك تغطي كل أنواع الـ Failures. الـ exceptions بتفضل للحاجات اللي مش متوقعة، يعني الـ bugs.

</Answer>
</Question>

<Question id="interview-10">
<Ask>يعني إيه value object؟</Ask>
<Answer>

نوع صغير بيمثل قيمة واحدة بقواعدها، زي Email أو Money، ومايتعملش غير وهو valid. ده بيمنع الـ primitive obsession: بدل String ممكن يكون أي حاجة، عندك Email مضمون إنه صح في كل مكان.

</Answer>
</Question>

### الأسبوع 3: طبقة الـ Data

<Question id="interview-11">
<Ask>إزاي تعمل token refresh لو في requests كتير رجعت 401 في نفس الوقت؟</Ask>
<Answer>

في الـ onError بتاع الـ interceptor: أول request يبدأ الـ refresh ويحط Completer كـ lock، والباقي يستنوا نفس الـ Future. بعدها كله يعيد المحاولة بالـ token الجديد. الـ refresh بيتعمل بـ Dio منفصل عشان مايدخلش نفس الـ interceptor، ولو فشل بتتمسح الـ session ويرجع UnauthorizedFailure.

</Answer>
</Question>

<Question id="interview-12">
<Ask>فين المكان الصح لتحويل الـ exceptions لـ Failures؟</Ask>
<Answer>

في الـ repository، لأنه الحد بين الـ data والـ domain. الـ data source بيرمي exceptions عادي، والـ repository بيحوّلها في مكان واحد (guard). فوق الـ repository مفيش exceptions خالص.

</Answer>
</Question>

<Question id="interview-13">
<Ask>تعمل retry لكل الطلبات؟</Ask>
<Answer>

لأ، الطلبات الـ idempotent بس زي GET. إعادة POST ممكن تضيف الحاجة مرتين. ولو لازم تعيد POST، بتبعت idempotency key عشان السيرفر يتجاهل التكرار.

</Answer>
</Question>

### الأسبوع 4: الـ Offline-first

<Question id="interview-14">
<Ask>يعني إيه single source of truth؟</Ask>
<Answer>

الـ UI بتقرا من مصدر واحد بس، وهو stream من الـ local DB. الـ network بيكتب في الـ DB ومابيرجعش بيانات للـ UI مباشرة. كده مستحيل الشاشة تعرض بيانات من الـ API مختلفة عن اللي في الكاش.

</Answer>
</Question>

<Question id="interview-15">
<Ask>بتتعامل إزاي مع الـ conflicts؟</Ask>
<Answer>

بسياسة واضحة ومكتوبة: last-write-wins بـ updatedAt، أو server-wins، أو merge لكل حقل. السيرفر بيرجع 409، والـ sync بيطبّق السياسة. الأهم إنها قرار متفق عليه وعليه تست، مش سلوك عشوائي.

</Answer>
</Question>

### الأسبوع 5: الـ Presentation بـ Cubit

<Question id="interview-16">
<Ask>إزاي تمنع race condition في البحث؟</Ask>
<Answer>

debounce عشان أقلل عدد الطلبات، وrequest id بيتزود مع كل طلب. أي نتيجة رجعت والـ id بتاعها مش الأحدث بتتجاهل. ولو عايز أوفّر الـ bandwidth كمان، بلغي الطلب نفسه في الـ data layer.

</Answer>
</Question>

<Question id="interview-17">
<Ask>Cubit ولا Bloc؟</Ask>
<Answer>

Cubit أبسط ومناسب لمعظم الشاشات. Bloc مفيد لما تحتاج تتبع كل event أو transformers جاهزة للـ concurrency. أنا بستخدم Cubit وبحل الـ concurrency بأنماط واضحة ومتستة، وده كفاية في أغلب المشاريع.

</Answer>
</Question>

<Question id="interview-18">
<Ask>فين تحط الـ navigation بعد ما العملية تنجح؟</Ask>
<Answer>

في BlocListener، ولو محتاج مع listenWhen. مش في build، لأن build ممكن يتنادى كذا مرة، فالـ navigation أو الـ snackbar هيتكرر.

</Answer>
</Question>

<Question id="interview-25">
<Ask>الـ validation مكانها فين: الـ UI ولا الـ Cubit ولا الـ domain؟</Ask>
<Answer>

في التلاتة، وكل واحد ليه شغلانة. القاعدة في الـ domain جوه value object زي `Email.create`، فبتتكتب مرة وتتستّ بـ dart test، والـ use case بياخد `Email` فمستحيل يوصله حاجة غلط. الـ Cubit بيمسك حالة الفورم: النص وtouched وsubmitAttempted وأخطاء السيرفر. والـ UI بتعرض بس وبتختار النص من الترجمة حسب الحقل. والسيرفر بيتحقق تاني، لأن الـ client مايتوثقش فيه.

</Answer>
</Question>

<Question id="interview-26">
<Ask>إزاي تعمل infinite scroll من غير ما تحمّل نفس الصفحة مرتين، ومن غير ما تخسر البيانات لو حصل error؟</Ask>
<Answer>

الحماية في الـ Cubit: flag قبل أول await، و`hasReachedEnd` بيوقف الطلبات لما الصفحات تخلص، وrequest id بيتجاهل أي صفحة راجعة لكلمة بحث قديمة. والـ error بتاع الصفحة N حقل جوه الـ Loaded state (`loadMoreFailure`)، فالليست بتفضل والـ footer يعرض retry، ورقم الصفحة مابيزيدش غير لما الطلب ينجح. وفوق ده dedupe بالـ id، ولو السيرفر بتاعك، cursor بدل offset.

</Answer>
</Question>

### الأسبوع 6: الـ DI والـ Flavors

<Question id="interview-19">
<Ask>registerFactory ولا registerLazySingleton للـ Cubit؟</Ask>
<Answer>

Factory، عشان كل شاشة تاخد instance جديد يتقفل معاها. الـ singleton للحاجات اللي مالهاش state مرتبط بشاشة زي الـ repositories والـ Dio. الاستثناء Cubit على مستوى الـ app كله زي الـ AuthCubit.

</Answer>
</Question>

<Question id="interview-20">
<Ask>بتعمل الـ flavors إزاي؟</Ask>
<Answer>

entry points منفصلة (main_dev وmain_prod)، وproductFlavors في Android، وschemes في iOS، وconfig class بيتسجل في الـ DI. مش if (kDebugMode) متوزعة في الكود.

</Answer>
</Question>

<Question id="interview-27">
<Ask>امتى تتخطى طبقة الـ domain؟ وإزاي تبرر ده في code review؟</Ask>
<Answer>

لما الـ feature مافيهاش business rules، ومصدر بياناتها واحد، ومحدش تاني بيستخدم منطقها، زي الثيم واللغة. الـ domain هنا هيبقى use case بينادي repository بينادي store من غير ما حد فيهم يضيف حاجة. بس الـ Cubit لسه بيعتمد على contract (`SettingsStore`) مش على shared_preferences، والتست شغال بـ fake. والقرار يتعكس لما الإعدادات تتزامن مع السيرفر أو يظهر فيها rule.

</Answer>
</Question>

<Question id="interview-28">
<Ask>إزاي تعمل logout نضيف وتتأكد إن مفيش بيانات من المستخدم القديم فضلت؟</Ask>
<Answer>

أعدّ كل مكان البيانات عايشة فيه وأمسحه من مكان واحد: الـ tokens من الـ secure storage، وكل جداول drift بـ `allTables`، والـ caches، والـ singletons اللي شايلة state. والـ refresh token يتلغي على السيرفر من غير ما أستنى الرد. وأحوّل للـ login بعد ما المسح يخلص مش قبله. وعشان أتأكد: integration test بيدخل بمستخدم A ويضيف كتاب، ويعمل logout، ويدخل بـ B، ويتأكد إن مفيش أي أثر لـ A.

</Answer>
</Question>

### الأسبوع 7–9: الاختبارات

<Question id="interview-21">
<Ask>إيه الفرق بين الـ fake والـ mock؟</Ask>
<Answer>

الـ mock بيتأكد من التفاعل: الـ method دي اتنادت بالـ parameters دي. الـ fake implementation بسيطة شغالة فعلًا، زي repository في الـ memory، وبيختبر السلوك. الـ fakes أقل عرضة للكسر لما التفاصيل الداخلية تتغير.

</Answer>
</Question>

<Question id="interview-22">
<Ask>بتختبر إيه في الـ Cubit؟</Ask>
<Answer>

تسلسل الـ states لكل سيناريو: نجاح، وكل نوع Failure، والنتيجة القديمة في البحث، والضغط المتكرر. بستخدم blocTest مع mock للـ use case.

</Answer>
</Question>

<Question id="interview-31">
<Ask>إيه الفرق بين الـ unit test والـ widget test والـ integration test؟ وإمتى تستخدم كل واحد؟</Ask>
<Answer>

الـ unit test بيختبر حتة logic لوحدها (use case، mapper، Cubit) في milliseconds ومن غير Flutter، وده أغلب التستات. الـ widget test بيرسم widget واحدة في بيئة test من غير جهاز، ويتأكد من اللي ظاهر والتفاعل، زي إن زرار «حاول تاني» بيظهر مع NetworkFailure. الـ integration test بيشغّل الـ app كامل على جهاز أو emulator، فهو الأبطأ والأهش، فبستخدمه للـ flows الحرجة بس زي الـ login والـ sync. القاعدة: اختبر كل حاجة في أرخص مستوى يقدر يمسكها.

</Answer>
</Question>

<Question id="interview-32">
<Ask>إيه الفرق بين `pump` و`pumpAndSettle`؟ وإمتى `pumpAndSettle` تبقى مشكلة؟</Ask>
<Answer>

`pump` بيرسم frame واحدة (أو بيقدّم الوقت مدة معينة لو اديته duration). `pumpAndSettle` بيفضل يرسم frames لحد ما مايبقاش في frames متجدولة، يعني كل الـ animations خلصت. المشكلة إن أي animation مابتخلصش، زي `CircularProgressIndicator` في حالة loading، بتخلي `pumpAndSettle` يفضل لحد ما يعمل timeout ويفشل. ساعتها بستخدم `pump` أو `pump(duration)` بوقت محدد.

</Answer>
</Question>

<Question id="interview-33">
<Ask>عندك تست بيفشل مرة من كل 20 في الـ CI. هتعمل إيه؟</Ask>
<Answer>

مش هحط retry وأنسى، لأن الـ flaky test بيعلّم الفريق يتجاهل الأحمر. أول حاجة أكرّر المشكلة: أشغّله في لوب، وبـ `--test-randomize-ordering-seed` عشان أعرف لو التستات بتعتمد على ترتيبها. الأسباب المعتادة: وقت حقيقي (`DateTime.now` أو `Future.delayed`) والحل Clock أو fake_async، أو state مشتركة بين التستات والحل setUp جديد لكل تست، أو شبكة حقيقية والحل fake. لو مش هقدر أصلّحه النهارده، بعزله بـ tag وبفتح ticket، مش بسيبه يوقّع الـ CI عشوائي.

</Answer>
</Question>

<Question id="interview-34">
<Ask>الـ coverage عندكم 95%. ده معناه إن التستات كويسة؟</Ask>
<Answer>

لأ. الـ coverage بتقول السطر ده اتنفّذ وقت التست، مش إن في `expect` اتأكد إن نتيجته صح. ممكن تست ينادي الكود كله ومايتأكدش من حاجة. الـ coverage مفيدة كإنذار (الجزء ده محدش اختبره خالص)، وكحد أدنى في الـ CI للـ domain والـ data، بس مش هدف. اللي بيقيس جودة التستات فعلًا هو: لو غيّرت الكود غلط، التست هيفشل؟ وده اللي الـ mutation testing بيقيسه.

</Answer>
</Question>

<Question id="interview-35">
<Ask>اشرح TDD. وبتستخدمه دايمًا؟</Ask>
<Answer>

Red: أكتب تست صغير بيفشل وبيوصف السلوك اللي عايزه. Green: أكتب أقل كود يخليه يعدّي. Refactor: أنضّف الكود والتستات خضرا. ميزته إن التصميم بيطلع من الاستخدام، وكل سطر عليه تست. بستخدمه في الـ business rules والـ bugs: أي bug بيبدأ بتست فاشل بيوصفه. ومابستخدموش في الحاجات الاستكشافية زي تجربة شكل UI، لأن التست هيتكتب ويتمسح كل شوية.

</Answer>
</Question>

<Question id="interview-36">
<Ask>إيه الـ golden test؟ وإيه مشاكله في الـ CI؟</Ask>
<Answer>

تست بيرسم الـ widget ويقارنها pixel بـ pixel بصورة محفوظة في الـ repo. بيمسك أي تغيير في الشكل محدش قصده، زي حاجة اتقلبت غلط في الـ RTL. مشاكله: الرسم بيختلف شوية بين macOS وLinux، فبولّد الصور على نفس المنصة اللي الـ CI بيشتغل عليها، والخطوط في التست بتبقى مربعات لو ماحمّلتش خط حقيقي. وأي تغيير مقصود في الشكل محتاج `--update-goldens` و review للصور في الـ PR.

</Answer>
</Question>

### الأسبوع 10–11: الـ API والأخطاء

<Question id="interview-37">
<Ask>إيه الفرق بين 401 و403؟ والـ app يتصرف إزاي في كل واحدة؟</Ask>
<Answer>

الـ 401 معناها السيرفر مش عارف انت مين: مفيش token، أو انتهى، أو الباسورد غلط. فالـ AuthInterceptor بيعمل refresh مرة ويعيد الطلب، ولو الـ refresh اترفض تبقى UnauthorizedFailure والـ router يرجّع لصفحة الدخول. الـ 403 معناها عارفك بس مش مسموحلك، فالـ refresh مش هيغيّر حاجة: مفيش retry ولا logout، رسالة مناسبة بس، زي «أكّد إيميلك» في الـ login بتاع Readly. ولو الـ backend بيخلط بينهم، ده بيتصلح في العقد مش بـ if في الـ app.

</Answer>
</Question>

<Question id="interview-38">
<Ask>إزاي تمسك كل الأخطاء اللي ماتمسكتش في Flutter؟</Ask>
<Answer>

`FlutterError.onError` للأخطاء اللي الـ framework بيمسكها وهو بيرسم أو في callback، و`PlatformDispatcher.instance.onError` (وبيرجّع `true`) لأي خطأ async محدش عمله await. الاتنين بيبعتوا للـ logger أو Sentry. و`ErrorWidget.builder` بيغيّر الشاشة الرمادي في الـ release. والـ `runZonedGuarded` مابقاش لازم في أغلب الحالات، و`Isolate.spawn` محتاج `onError` port، أما `Isolate.run` فبيرمي الخطأ عند الـ await.

</Answer>
</Question>

<Question id="interview-39">
<Ask>ليه الـ HTTP status لوحده مش كفاية عشان تقرر تعمل إيه؟</Ask>
<Answer>

لأنه فئة مش تفصيلة. الـ 409 في Readly ممكن تبقى `email_taken` (خطأ على حقل) أو `VERSION_CONFLICT` (الـ ConflictPolicy تقرر). والـ 404 ممكن تبقى route مش موجود (bug يروح Sentry) أو `book_not_in_library` (حالة عادية). القرار بالـ status والـ `code` من الـ body مع بعض، وأي code مش معروف بيرجع لتصرف الفئة، والـ message بتاع السيرفر عمره ما بيدخل في القرار.

</Answer>
</Question>

<Question id="interview-40">
<Ask>الـ refresh فشل. إزاي تعرض الخطأ من غير ما تضيّع البيانات اللي على الشاشة؟</Ask>
<Answer>

الـ failure حقل في الـ state جنب البيانات، والـ Error state الكاملة بس لما مفيش بيانات خالص. الـ refresh مابيعملش emit لـ Loading، والـ UI بتعرض banner «بنعرض آخر نسخة» فوق الليستة، وبيختفي لما الـ refresh ينجح. ونفس الفكرة جوه الصفحة: الجزء الإضافي اللي فشل (زي اسم المؤلف) بيبقى nullable، والصفحة تتعرض.

</Answer>
</Question>

<Question id="interview-41">
<Ask>إزاي تبعت طلبين مع بعض وتتعامل لو واحد فشل؟</Ask>
<Answer>

<Question id="interview-42">

<Question id="interview-45">
<Ask>http ولا dio؟ وإيه الفرق الحقيقي بينهم؟</Ask>

### الأسبوع 12–13: Dart Async والـ Streams

<Question id="interview-59">
<Ask>Dart single-threaded، يبقى إزاي بيعمل حاجات async؟ وإيه الفرق بين الـ microtask queue والـ event queue؟</Ask>
<Answer>

الكود بيشتغل على thread واحد في الـ isolate، بس الانتظار نفسه (الشبكة والديسك والـ timers) بيحصل بره في الـ OS أو الـ engine. لما النتيجة توصل بتدخل طابور، والـ event loop بيشغّلها لما الـ thread يفضى، والـ `await` بيعلّق الـ function ويرجّع الـ thread للـ loop فالـ UI بتكمّل. الـ loop بيفضّي الـ microtask queue كلها الأول (كمالة الـ Futures بعد `await` و`scheduleMicrotask`)، وبعدين ياخد event واحد (timer أو I/O أو gesture أو frame)، ويرجع للـ microtasks. فـ `Future.microtask` بيشتغل قبل `Future.delayed(Duration.zero)` دايمًا، والـ microtasks اللي مابتخلصش بتجمّد الـ app.

</Answer>
</Question>

<Question id="interview-60">
<Ask>`Future.wait` مع `eagerError: true` بيلغي الـ Futures التانية؟</Ask>
<Answer>

لأ. الـ Future في Dart مالوش cancel. الـ `eagerError` بيخلي الـ Future اللي راجع يكمل بأول خطأ على طول، بس الباقي بيكمّل شغله، ونتايجه وأخطاؤه بتضيع. لو الشغل ده كتابة، ممكن تقول للمستخدم «فشل» والحاجة تتعمل بعدها. ونفس الكلام لـ `timeout`: بيوقّف الانتظار، مش الشغل. الإلغاء الحقيقي لازم يبقى في الأداة نفسها: `CancelToken` في dio، أو `cancel()` للـ subscription.

</Answer>
</Question>

<Question id="interview-61">
<Ask>إيه الفرق بين asyncMap وswitchMap وexhaustMap؟</Ask>
<Answer>

التلاتة بياخدوا قيمة ويشغّلوا شغل async ليها. الـ `asyncMap` بيعمل الشغل واحد ورا التاني والقيم الجديدة بتستنى، فكل النتايج بتوصل بالترتيب، وده للعمليات اللي لازم تتعمل كلها. الـ `switchMap` بيلغي اللي شغال لما قيمة جديدة تيجي، فنتيجة آخر قيمة بس هي اللي بتوصل، وده البحث. الـ `exhaustMap` بيرمي القيم الجديدة طول ما في واحد شغال، وده زرار الحفظ. والإلغاء في `switchMap` بيلغي الـ subscription مش الـ Future نفسه، فالطلب بيكمّل ونتيجته بتترمي.

</Answer>
</Question>

<Question id="interview-62">
<Ask>إزاي الـ StreamSubscription بتعمل memory leak؟ وليه ممكن يجيلك «Cannot emit new states after calling close» مع إنك عملت cancel في الـ close؟</Ask>
<Answer>

المصدر (singleton أو الـ DB) ماسك الـ subscription، وهي ماسكة الـ callback، والـ callback ماسك الـ Cubit وكل اللي فيه. طول ما المصدر عايش محدش في السلسلة بيتمسح، والـ callback بيفضل يشتغل حتى بعد ما الشاشة اتقفلت. الحل إن اللي عمل listen يعمل cancel في الـ `close` أو الـ `dispose`. بس الـ cancel بيمنع events جديدة، مابيوقّفش callback شغال أصلًا: لو فيه `await` وبعده `emit`، والـ close حصل وهو مستني، الـ emit هيحصل على Cubit مقفول. فالشغل الـ async يتحط في الـ pipeline بـ `asyncMap` أو `switchMap` والـ callback يفضل sync، أو على الأقل `if (isClosed) return;` بعد الـ await.

</Answer>
</Question>

<Question id="interview-63">
<Ask>إيه الفرق بين async وisolate؟ وامتى `Isolate.run` وامتى `Isolate.spawn`؟</Ask>
<Answer>

الـ async بيخلي الـ isolate الواحد يعمل حاجة تانية وهو مستني حاجة بره، بس الكود كله لسه على thread واحد بالتناوب. الـ isolate التاني ليه ذاكرته وevent loop بتاعه وبيشتغل على core تاني، فهو اللي بيحل الحسابات التقيلة، والتمن إن البيانات بتتنسخ في الرسايل ومابيعرفش الـ singletons ولا الـ plugins من غير setup. الـ `Isolate.run` (واللي `compute` بيناديه على الموبايل) لشغل واحد: بيعمل isolate ويرجّع النتيجة ويموت، والخطأ بيترمي عند الـ await. الـ `Isolate.spawn` لـ isolate عايش فترة بتكلّمه برسايل كتير بـ ports، وانت المسؤول عن قفله وأخطاؤه.

</Answer>
</Question>

### الأسبوع 14–16: Cubit وBloc

<Question id="interview-46">
<Ask>إيه اللي بيحصل لو عملت emit لـ state بتساوي الحالية؟ ولو عدّلت list جوه الـ state وعملت emit ليها؟</Ask>
<Answer>

الـ Cubit بيقارن بـ `==`، ولو الاتنين متساويين الـ emit بيتجاهل ومفيش rebuild. ولو عدّلت الـ list نفسها وعملت emit لنفس الـ object، الـ `==` بيقول متساويين لأنه نفس الـ object، فالشاشة مش هتتغير. الحل immutability: list جديدة دايمًا (`[...books, book]`)، وstate بـ value equality بـ Equatable أو freezed، فالمقارنة تبقى على المحتوى مش على العنوان في الـ memory.

</Answer>
</Question>

<Question id="interview-47">
<Ask>الـ state تبقى sealed classes ولا class واحدة فيها status وcopyWith؟</Ask>
<Answer>

حسب سؤال واحد: لو الحالة دي حصلت، البيانات اللي على الشاشة بتفضل؟ لو كل حالة شاشة مختلفة تمامًا (loading، تفاصيل الكتاب، error)، sealed، والـ switch بيجبرني أتعامل مع كل حالة. لو البيانات بتفضل والحالات حواليها بتتغير (فورم بيتبعت، ليستة بتتعمل لها refresh)، class واحدة بـ status. والأغلب hybrid: sealed من بره، والـ loading والـ error الخاصين بتحديث البيانات حقول جوه الـ Loaded.

</Answer>
</Question>

<Question id="interview-48">
<Ask>`BlocProvider(create:)` ولا `BlocProvider.value`؟ وإيه الغلطة الشائعة؟</Ask>
<Answer>

الـ `create` بيعمل الـ Cubit وبيقفله لما الـ provider يتشال، فهو للـ Cubit اللي الـ widget دي صاحبته. الـ `.value` بيوفّر instance موجودة ومابيقفلهاش، فهو لما توصّل Cubit لـ route جديد أو لـ singleton عايش طول الـ app. الغلطتين: `.value(value: getIt<X>())` لـ factory، فالـ Cubit مابيتقفلش أبدًا والـ subscriptions بتاعته بتفضل شغالة. و`create` حوالين singleton، فأول شاشة تتقفل بتقفله للـ app كله، وأي emit بعدها `StateError`.

</Answer>
</Question>

<Question id="interview-49">
<Ask>`context.read` و`context.watch` و`context.select`: كل واحد مكانه فين؟</Ask>
<Answer>

الـ `read` في الـ callbacks بس (onPressed)، عشان تنادي method، ومابيسمعش على التغييرات، فلو استخدمته في build الشاشة مش هتتحدث. الـ `watch` في build، وبيعيد بناء الـ widget كلها مع كل state، فبحطه في Builder صغير أو بستخدم BlocBuilder. الـ `select` في build برضه، وبيعيد البناء بس لما القيمة اللي اخترتها تتغير. ولو عايز الـ rebuild يبقى محدد بشكل واضح في الشجرة، BlocSelector أوضح من select في أول الـ build.

</Answer>
</Question>

<Question id="interview-50">
<Ask>إزاي تعرض SnackBar أو تعمل navigation مرة واحدة من Cubit؟</Ask>
<Answer>

في BlocListener، مش في build، لأن build بيتنادى أكتر من مرة لنفس الـ state. الطريقة الأبسط إن الحاجة تبقى حقل في الـ state (`refreshFailure` أو status بقى success) مع `listenWhen` يحدد اللحظة. ولو الـ effect مالوش أي معنى كـ state (navigation بعد حفظ مثلًا)، ممكن stream منفصل للـ effects من الـ Cubit بيتقفل في `close`، بتمن إن أي effect بيحصل والشاشة مش سامعة بيضيع. والـ Cubit نفسه عمره ما بيمسك BuildContext ولا Navigator.

</Answer>
</Question>

<Question id="interview-51">
<Ask>إزاي Cubitين يتكلموا مع بعض؟</Ask>
<Answer>

مش مع بعض مباشرة. الطريقة الأولى إن الاتنين يسمعوا stream من نفس الـ repository، فأي تغيير يظهر في الاتنين لوحده، زي `watchLibrary()` في المكتبة والـ Home. التانية BlocListener في الـ UI: لما واحد يتغير، الـ listener ينادي method في التاني، وده مناسب لما الربط خاص بالشاشة دي. أما Cubit بيمسك reference لـ Cubit تاني فبيربط عمرهم ببعض، ومع get_it factory ممكن ياخد instance غير اللي الشاشة شايفاها خالص.

</Answer>
</Question>

<Question id="interview-52">
<Ask>اشرح الـ transformers بتاعة bloc_concurrency، وامتى تستخدم كل واحد.</Ask>
<Answer>

الـ default `concurrent`: كل event يبدأ فورًا والنتايج ترجع بأي ترتيب. `sequential` طابور، للعمليات اللي ترتيبها مهم زي الحفظ. `droppable` بيرمي أي event جه والـ handler شغال، للـ «حمّل الصفحة الجاية» وزرار الحفظ. `restartable` بيقفل الـ handler القديم ويبدأ الجديد، للبحث والفلاتر. وحاجتين مهمين: الـ restartable مابيلغيش الطلب نفسه، بيمنع الـ emit بتاعه بس. والـ transformer لكل `on<E>` لوحده، فالتزاحم بين نوعين events مختلفين لسه محتاج guard.

</Answer>
</Question>

<Question id="interview-53">
<Ask>امتى تستخدم HydratedCubit؟ وإيه اللي عمرك ما تحفظه بيه؟</Ask>
<Answer>

للتفضيلات وحالة الـ UI اللي المستخدم يتوقع يلاقيها زي ما سابها: فلاتر الكتالوج، وضع العرض، مسودة ملاحظة. ومابحفظش الـ loading ولا الـ errors (هترجع بعد الفتح على حالة مالهاش معنى)، ولا الـ tokens ولا أي حاجة سرية (مكانها secure storage)، ولا بيانات الـ server (مكانها drift). وبثبّت `storagePrefix` لأن الافتراضي اسم الـ class وبيتغير مع الـ obfuscation والـ rename، وبحط version في الـ JSON عشان أقدر أعمل migration، وبمسحه مع الـ logout.

</Answer>
</Question>

<Question id="interview-54">
<Ask>إيه علاقة flutter_bloc بـ provider وInheritedWidget؟</Ask>
<Answer>

flutter_bloc مبني على provider، وprovider مبني على InheritedWidget. الـ `BlocProvider` هو `InheritedProvider` بيعمل الـ Cubit ويقفله، و`context.read` و`watch` و`select` نفسهم extensions provider. فقواعد provider هي هي: الـ lookup بالـ type بالظبط، والـ context لازم يبقى تحت الـ provider، و`read` في الـ callbacks. اللي الـ bloc بيزوّده هو الـ state الـ immutable اللي بتتغير بـ emit بس، والـ stream، والـ observer، والتستات.

</Answer>
</Question>

<Question id="interview-55">
<Ask>ChangeNotifier مع provider ولا Cubit؟</Ask>
<Answer>

الاتنين بيوصلوا الـ state للشجرة بنفس الطريقة. الفرق في الـ state نفسها: الـ ChangeNotifier بيعدّل في مكانه، ولازم تفتكر `notifyListeners` بعد كل تغيير، ومفيش سجل للتغييرات. الـ Cubit بيطلّع state جديدة immutable، فالـ `==` بيقرر الـ rebuild، والـ observer بيشوف كل تغيير، والتست بيقارن تسلسل states. الـ ChangeNotifier مناسب لحاجة صغيرة جوه الـ UI، أو لفريق متفق عليه زي مثال الـ architecture الرسمي بتاع Flutter. لشاشات فيها async وrace conditions، الـ Cubit أوضح وأسهل في التست.

</Answer>
</Question>

<Question id="interview-56">
<Ask>Riverpod ولا Bloc؟</Ask>
<Answer>

Riverpod بيجمع الـ DI والـ state والـ caching في أداة واحدة، والـ lookup بيتأكد منه الـ compiler مش في الـ runtime، والـ async (`AsyncValue`) والـ derived state جاهزين. التمن codegen، وlifecycle ضمني (autoDispose، والـ Notifier بيتبني من الأول مع كل rebuild)، وstate متعرّفة كـ declarations global الشكل. الـ Bloc أوضح: كل تغيير emit، والـ concurrency بسياسات باسمها، والـ DI منفصل (get_it). الاتنين بيحافظوا على Clean Architecture لو الـ domain فاضل Dart نقي. الاختيار حسب الفريق والمشروع، مش حسب الأحدث. ولو مشروع قايم على واحد فيهم، النقل للتاني نادرًا ما بيستاهل.

</Answer>
</Question>

<Question id="interview-57">
<Ask>اشتغلت على مشروع بـ GetX. إيه المشاكل اللي ممكن تقابلها، وتنقله لـ Cubit إزاي؟</Ask>

GetX سريع في البداية، بس بيجمع الـ state والـ DI والـ routing في مكان واحد. الـ `Get.find` service locator global، والـ navigation والـ snackbar من غير context جوه الـ controller، فالـ controller بيعرف Flutter وصعب تختبره لوحده، والحدود بين الطبقات بتبوظ. النقل بيبقى شاشة شاشة: الأول أطلّع مصدر الحقيقة لـ repository بـ stream، فالقديم والجديد يقروا منه. بعدين أكتب characterization test للشاشة، وأعمل Cubit بنفس السلوك، وأبدّل الشاشة، وأمسح الـ controller. والـ DI والـ routing ينتقلوا في الآخر. والتستات خضرا في كل PR.

</Answer>
</Question>

<Question id="interview-58">
<Ask>إزاي تختار state management لمشروع جديد؟</Ask>
<Answer>

مش بالأشهر. بسأل عن الفريق: يعرف إيه، ومين هيمسك المشروع بعدنا. وعن المشروع: هيعيش قد إيه، وفيه async وstreams قد إيه، ومحتاج traceability ولا لأ. وبعدين المعايير: الـ state immutable وتغييرها صريح، والـ logic بتتست من غير Flutter، والـ domain بيفضل نقي، والـ package متصانة. الـ setState والـ ValueNotifier للـ state المحلية في أي حالة. وللشاشات بختار Cubit default وBloc للـ inputs اللي بتتزاحم، أو Riverpod لو الفريق عايز DI وcaching في أداة واحدة. وبكتب القرار في ADR بالبدائل اللي اترفضت وليه.

### الأسبوع 17–18: Riverpod

<Question id="interview-64">
<Ask>لو قررتوا تغيّروا الـ state management بكرة، هيكلّفكم كام؟</Ask>
<Answer>

أبدأ بالحدود: الـ domain والـ data مابيعرفوش الـ state management، وده متحرس بتست في الـ CI بيمنع أي import لـ flutter_bloc أو riverpod جوههم، فالتحويل بيلمس الـ presentation والـ DI وتستاتهم بس. وبعدين رقم: عدد الـ Cubits ونوعهم، وكام يوم للشاشة حسب تعقيدها، وإننا نقدر ننقل شاشة شاشة والاتنين عايشين مع بعض. وبعدين التحفظ: مش هنعمله غير لو المعايير اللي في الـ ADR اتغيرت. الإجابة الضعيفة: «كتير، لأن الـ Cubits في كل حتة».

</Answer>

<Question id="interview-65">
<Ask>لو شلت get_it وحطيت Riverpod، الـ data layer بتتغير؟</Ask>
<Answer>

لأ، لو كانت مكتوبة صح. الـ repositories والـ data sources بتاخد dependencies في الـ constructor ومابتعرفش مين بيعملها. اللي بيتغير هو الـ composition root: providers كل واحد بيقول محتاج إيه بـ `ref.watch` وبيرجّع الـ contract. اللي بيتجهز async (prefs وtokens) بيتجهز قبل `runApp` ويدخل بـ `overrideWithValue`، والـ flavors بـ overrides، والـ reset مع الـ logout بـ watch لحالة الدخول. واللي لازم أحرسه: مفيش class في الـ data بتاخد `Ref` (يبقى service locator)، والـ widgets ماتعملش watch للـ repositories مباشرة، لأن Riverpod مابيمنعش ده لوحده.

</Answer>

<Question id="interview-66">
<Ask>إيه اللي بيخلّي provider بالـ autoDispose يفضل عايش؟</Ask>
<Answer>

أي listener: `ref.watch` أو `ref.listen` من widget أو من provider تاني عايش، أو `container.listen` في تست. الـ `ref.read` مابيمسكوش. والـ graph بيعيش من تحت لفوق: الشاشة بتمسك اللي بتعمله watch، وده بيمسك اللي تحته. ولما الشاشة تكون مستخبية تحت route تاني، الـ listeners بتتوقف (pause) في Riverpod 3 مش بتتشال، فمفيش حاجة بتتمسح ومفيش rebuilds. ولو عايز provider يعيش شوية بعد آخر listener، `ref.keepAlive()` مع timer بيقفل الـ link.

</Answer>
</Question>

<Question id="interview-67">
<Ask>إيه الفرق بين `isClosed` في الـ Cubit و`ref.mounted` في الـ Notifier؟</Ask>
<Answer>

`isClosed` معناه إن الـ Cubit اتقفل، ومفيش غيره. `ref.mounted` معناه إن الـ provider لسه عايش. بس الـ Notifier عنده حالة تالتة: الـ `build` ممكن يتعاد وانت مستني (invalidate أو dependency اتغيرت) والـ provider لسه عايش، فـ `ref.mounted` بيقول `true` والـ method بتكتب فوق الـ state الجديدة. الحل إني آخد `final buildRef = ref;` قبل الـ await وأسأل `buildRef.mounted` بعده، لأن كل build ليه Ref جديد والقديم بيقول `false`. ده نفس سؤال «أنا لسه على نفس الحاجة اللي بدأت عليها؟».

</Answer>
</Question>

<Question id="interview-68">
<Ask>انتو بتستخدموا Bloc. ليه مش Riverpod؟ وينفع الاتنين في نفس الـ app؟</Ask>
<Answer>

الإجابة القوية مش «Bloc أحسن»: عملنا spike وكتبنا المكتبة والكتالوج وصفحة الكتاب بـ Riverpod. الـ domain والـ data ماتغيروش ولا سطر، وده أهم نتيجة. Riverpod كسب في البحث والصفحات والقيم المشتقة، وتعادل أو خسر في الـ submit والـ optimistic، ولأن الـ app offline-first وdrift هو الـ cache، أكبر ميزة ليه كانت متغطية، فقررنا نفضل، والقرار في ADR بالتمن والشروط اللي تخلينا نراجعه. والاتنين في نفس الـ app ينفع تقنيًا، بس بقواعد: كل feature بأداة واحدة، ومصدر الحقيقة في الـ repository، ومفيش Notifier بيقرا Cubit أو العكس، والخليط ليه تاريخ نهاية والـ CI بيمنع إن القديم يزيد.

</Answer>
</Question>

### الأسبوع 19–20: Real-time والـ Background

<Question id="interview-69">
<Ask>عندك feature محتاجة بيانات تتحدث لحظيًا. polling ولا WebSocket ولا SSE ولا push؟</Ask>
<Answer>

ابدأ بسؤالين: التأخير المقبول قد إيه، والـ app لازم يبقى مفتوح ولا لأ. دقيقة والشاشة مفتوحة: polling بـ ETag وbackoff، وسيرفر stateless. ثواني والشاشة مفتوحة: اتصال مفتوح، SSE لو اتجاه واحد وفيه resume جاهز، وWebSocket لو محتاج الاتجاهين. والـ app مقفول: push، بس كإشارة والبيانات من الـ API. وفي كل الحالات الاتصال المفتوح بيفوّت events، فلازم catch-up بـ cursor مع كل reconnect، والـ refresh العادي يفضل. والتمن: سيرفر stateful، وheartbeat، وreconnect بـ jitter، وauth للاتصال نفسه.

</Answer>
</Question>

<Question id="interview-70">
<Ask>إزاي تدخّل WebSocket في Clean Architecture؟</Ask>
<Answer>

الـ WebSocket مصدر بيانات، فمكانه الـ data layer. client واحد في core بيملك الاتصال (بيفتحه بعد الـ auth ويقفله في الـ logout والخلفية) وبيوزّع الرسايل. الـ data source بتاع كل feature بياخد الأنواع بتاعته ويحوّلها لـ DTOs بنفس الـ mapper بتاع الـ REST ويتجاهل اللي مايعرفهوش، وservice في الـ data layer بيكتب الـ events في الـ local DB، والشاشة بتقرا من الـ DB زي ما هي. كده مفيش Cubit بيعرف إن في socket، والـ offline شغال ببلاش، والتست بـ fake data source، والعقد مكتوب في AsyncAPI جنب الـ OpenAPI.

</Answer>
</Question>

<Question id="interview-71">
<Ask>إزاي تعمل reconnect لـ WebSocket صح؟</Ask>
<Answer>

الـ close code بيقرر. أكواد الشبكة والسيرفر بتستنى بـ exponential backoff مع jitter عشان آلاف الموبايلات مايرجعوش في نفس الثانية بعد deploy، والعداد بيتصفّر بس لما الاتصال يعيش فترة. الـ 4401 (الـ token خلص) معناها refresh بنفس الـ refresher بتاع الـ HTTP وreconnect، ولو اتكرر بعد refresh يبقى bug فبتبطّل. والأكواد اللي معناها «مش هينفع» (حساب مقفول، نسخة قديمة) بتوقف خالص. والـ heartbeat بيكشف الاتصال اللي مات من غير close frame، والـ connectivity تلميح بيقصّر الانتظار مش أكتر. والاتصال بيتقفل في الخلفية والـ logout، وبيرجع مع الـ resume ويعمل catch-up.

</Answer>
</Question>

<Question id="interview-72">
<Ask>الـ events بتوصل من WebSocket وممكن تتكرر أو تتأخر أو تضيع. إزاي تضمن إن الـ local DB صح؟</Ask>
<Answer>

كل كتابة جاية من السيرفر مشروطة: الصف مايكونش عليه تعديل محلي لسه ماتبعتش، والـ version اللي جاي أكبر من اللي عندك. كده التكرار والتأخير مالهمش أثر والترتيب مايفرقش. الحذف بيسيب tombstone بالـ version عشان event قديم مايرجّعش الصف. والضايع بيتكشف بـ seq: الـ cursor بيتحرك بس فوق أرقام متصلة، وأي فجوة أو reconnect بيعمل catch-up بـ `since=cursor`، والـ cursor بيتحفظ في نفس الـ transaction مع الداتا. ولو الـ cursor أقدم من اللي السيرفر محتفظ بيه، full refresh. وكل الطرق بتعدّي على نفس قاعدة الكتابة.

</Answer>
</Question>

<Question id="interview-73">
<Ask>إزاي تعمل sync للتعديلات الأوفلاين والـ app مقفول؟</Ask>
<Answer>

workmanager بيطلب من الـ OS يشغّل callback في isolate جديد: periodic كل 15 دقيقة على Android (وفي iOS النظام بيقرر)، وone-off بشرط الشبكة لما الـ app يروح الخلفية وفي عمليات مستنية، وsilent push كإشارة. الـ callback top-level بـ `@pragma('vm:entry-point')`، وبيبني DI خاص بالخلفية من غير UI ولا sockets، وبيعمل drain واحد بـ timeout أقل من الـ 30 ثانية بتاعة iOS. والمشاكل: drain في isolateين (claim atomic في الـ DB)، وعمليات اتقطعت في النص (الـ idempotency key)، والـ refresh token بين isolateين (الخلفية ماتمسحش الـ tokens). وفي الآخر ده بونص، والضمان هو الـ sync في الـ foreground.

</Answer>
</Question>

### الأسبوع 21–22: الـ Performance

<Question id="interview-74">
<Ask>الـ app بيقطّع. بتعمل إيه؟ وليه ماينفعش تقيس في الـ debug mode؟</Ask>

<Question id="interview-75">

<Question id="interview-76">
<Ask>صورة JPEG حجمها 200KB. بتاخد قد إيه في الذاكرة؟</Ask>

مالهاش علاقة بالـ 200KB. بعد الـ decode بتاخد العرض × الارتفاع × 4 bytes، فصورة 1000 × 1500 بتاخد حوالي 6MB حتى لو بتتعرض في خلية 100 × 150. عشان كده بنفك بالحجم اللي هيتعرض (`cacheWidth` أو `memCacheWidth` مضروب في الـ DPR)، وبنطلب من السيرفر المقاس الصح، وبنتأكد بـ Highlight oversized images في DevTools. والـ disk cache بتاع `cached_network_image` بيوفّر data، بس مابيحلش مشكلة الذاكرة.

<Question id="interview-77">
<Ask>إزاي تلاقي memory leak في Flutter؟</Ask>

بحدد سيناريو بيفتح ويقفل الشاشة اللي شاكك فيها. في DevTools Memory بدوس GC وباخد snapshot، وبعمل السيناريو N مرة، وGC تاني وsnapshot، وبعمل Diff. أي class زاد N مرة بيتسرّب مع كل فتحة. بختار instance منه وبشوف الـ retaining path من الـ root، وده بيقولي مين ماسكه: subscription مااتلغتش، أو AnimationController مااتعملهوش dispose، أو closure ماسك BuildContext في singleton، أو cache مالوش حد. وبفرّق بين ده وبين cache زي الـ ImageCache، اللي بيوصل لحد ويقف.

<Question id="interview-78">
<Ask>الـ Clean Architecture مش بتبطّأ الـ app بكل الـ mapping والطبقات دي؟</Ask>

لأ، وده رقم مش رأي: الـ mapping لـ 4000 object بياخد أقل من 0.1ms، والـ Dart GC مصمم للـ objects اللي عمرها قصير. الطبقات بتبقى غالية في حالتين: لما الـ mapper نفسه بيعمل شغل تقيل (parsing أو regex)، ولما الـ API بتاع الـ repository متعمل على مقاس item واحد فالشاشة بتعمل N+1 queries. والاتنين بيتصلحوا جوه الطبقات مش بإنك تشيلها. وقبل أي حاجة: قيس في profile mode بـ `Timeline.timeSync`، والـ benchmark بـ AOT وwarm-up.

### الأسبوع 23: الـ Modularization

<Question id="interview-79">
<Ask>امتى تقسّم Flutter app لـ packages؟ وإيه عيوب التقسيم؟</Ask>
<Answer>

لما المشكلة اللي بتحلها موجودة فعلًا: app تاني محتاج نفس الكود، أو فريق كبير والحدود بتتكسر رغم الـ guards، أو الـ codegen والتستات بقوا بطيئين على المشروع كله. وبقسّم بالـ features مش بالطبقات. ولمشروع صغير أو منتج لسه بيتغير، modular monolith: فولدر لكل feature فيه barrel و`src/` وتست بيحرس الـ imports، فالتقسيم بعد كده نقل فولدرات. والعيوب: pubspecs أكتر، والـ DI والترجمة والـ assets والـ routes محتاجين قرار هيعيشوا فين، والـ CI لازم يلف على الـ packages، وأغلى حاجة إن الحد الغلط تصليحه نقل ملفات بين packages، فالحدود لازم تتبني على أرقام الـ imports والـ commits.

</Answer>
</Question>

<Question id="interview-80">
<Ask>قسّمتوا لـ packages، إيه اللي يمنع حد يكسر الحدود؟</Ask>
<Answer>

3 حاجات. `depend_on_referenced_packages` كـ error، لأن الـ workspace بيعمل resolution واحدة والـ import لـ package مش في الـ pubspec بيتعمله compile عادي. وتست بيقرا الـ pubspecs نفسها: الـ core مابتعتمدش على حد، والـ features بتعتمد على features معينة بس في ليستة بأسبابها، ومحدش بيعتمد على الـ app، ومفيش دواير. وCODEOWNERS على الـ pubspecs والتست. وفوق ده الـ core والـ domain packages مافيهاش Flutter وبتتختبر بـ `dart test`، فالـ compiler نفسه بيرفض أي import لـ Flutter.

</Answer>
</Question>

<Question id="interview-81">
<Ask>feature A معتمدة على B، وB محتاجة معلومة من A. تعمل إيه؟</Ask>
<Answer>

ماعكسش السهم، لأن ده دايرة. B تعرّف interface صغير في الـ domain بتاعها بالشكل اللي محتاجاه، وA تنفّذه، والـ composition root يسجّل implementation A تحت الـ interface ده. B مابتعرفش A، والسهم الوحيد لسه A → B. ولو app مافيهوش A، يسجّل implementation فاضي.

</Answer>
</Question>

<Question id="interview-82">
<Ask>الـ CI بتاع الـ monorepo بياخد 15 دقيقة. تعمل إيه؟</Ask>
<Answer>

الأول أقيس الوقت رايح فين. بعدين: الـ checks الرخيصة (format وanalyze والـ architecture) job لوحدها بتفشل في دقيقة. والتستات تتشغّل على الـ packages اللي اتغيرت وكل اللي بيعتمد عليها، محسوبة من الـ pubspecs، كـ matrix بالتوازي، ولو اتغير الـ lock أو ملف في الـ root يبقى كله. والـ main بيشغّل كله دايمًا. وcache للـ Flutter SDK والـ pub cache بـ key من الـ `pubspec.lock`. والـ required check واحد بيجمّع النتايج، عشان الـ jobs اللي بتتعدّى ماتفضلش Pending.

</Answer>

### الأسبوع 24–25: الـ Design System والـ Accessibility

<Question id="interview-83">
<Ask>إزاي تبني design system في Flutter؟ وفين تحط ألوان مش موجودة في الـ ColorScheme؟</Ask>
<Answer>

3 طبقات: palette فيه القيم الخام ومش ظاهر للشاشات، وأدوار (semantic tokens) هي اللي الشاشات بتستخدمها، وقرارات جوه كل component. الأدوار اللي Material عنده بستخدمها زي ما هي (`ColorScheme.fromSeed` و`TextTheme`) عشان كل الـ widgets تاخدها لوحدها. والناقص (ألوان الحالات والنجاح والتحذير) في `ThemeExtension` فيه light وdark بـ `copyWith` و`lerp` حقيقيين. والمسافات والـ radius `const`. وبحرس ده بتست بيدوّر على `Color(0x` و`Colors.` برا `core_ui`، بـ allowlist للقديم بتصغر بس.

</Answer>
</Question>

<Question id="interview-84">
<Ask>إيه اللي بيتكسر في الـ RTL غير الـ padding؟</Ask>
<Answer>

الـ layout سهل لو استخدمت الـ directional APIs. الصعب 3 حاجات. الأيقونات: Flutter بيقلب أيقونات الاتجاه لوحده، فالـ `isRtl ? left : right` بيقلبها مرتين، والـ SVG بتوعك محتاجين `matchTextDirection` أو flip. النص المختلط: علامات الترقيم بتاخد اتجاه الفقرة، فعنوان إنجليزي جوه جملة عربي بتنط علامته؛ الحل isolate بـ U+2068 وU+2069 حوالين الـ placeholder، ومحتوى المستخدم اتجاهه من حروفه، والإيميل والتليفون LTR صريح. والحاجات اللي مالهاش نسخة directional: الـ CustomPainter والـ Offset في الـ animations واتجاه السحب. وكل ده بيتست بـ golden عربي وتست بيمنع الـ physical APIs.

</Answer>
</Question>

<Question id="interview-85">
<Ask>إزاي تخلي app Flutter accessible لمستخدم TalkBack؟</Ask>
<Answer>

Flutter بيبني semantics tree جنب الـ widget tree، والـ widgets الجاهزة بتملاها لوحدها. شغلي في الباقي: كل حاجة بتتداس ليها label (`tooltip` في `IconButton`، و`semanticLabel` للأيقونات اللي ليها معنى)، والصور الـ decorative `excludeFromSemantics`، والكارت اللي فيه كذا نص `MergeSemantics` عشان يتقري مرة، والعناوين headings، والتغييرات المهمة `liveRegion`. وفوق ده targets 48×48 على Android و44×44 على iOS، وcontrast 4.5:1 للنص، والمعنى مايعتمدش على اللون بس. وبحرس ده بـ `meetsGuideline` في التستات، وبتجربة بإيدي بـ TalkBack قبل كل release.

</Answer>
</Question>

<Question id="interview-86">
<Ask>المستخدم مكبّر الخط والـ layout بيبوظ. تعمل إيه؟</Ask>
<Answer>

مش هقفل التكبير: ده بيشيل ميزة accessibility عن الناس اللي محتاجاها. كل `Text` بيكبر لوحده، والمشكلة دايمًا في اللي حواليه: بشيل الارتفاعات الثابتة (`minHeight` مكان `height`، و`minimumSize` مكان `fixedSize`)، والنص جوه `Row` بياخد `Expanded`، والحاجات الصغيرة جنب بعض `Wrap`، وكل صفحة بتعمل scroll. وبقرر لكل نص يتقص ولا لأ. والـ clamp بس على أجزاء صغيرة زي labels الـ navigation بـ `withClampedTextScaling`. وماحسبش `fontSize * factor` بإيدي لأن Android 14 بيكبّر بشكل مش خطي. وبتست ده بـ goldens بخط 2.0 على موبايل صغير.

</Answer>

<Question id="interview-30">

<Question id="interview-87">
<Ask>بتخزّن الـ tokens فين، وده آمن؟</Ask>
<Answer>

في flutter_secure_storage: Keychain في iOS، ومفتاح في الـ Keystore بيشفّر القيم في Android، بإعدادات صريحة (`first_unlock_this_device` في iOS، ومستثنية من الـ backup في Android). ده بيحمي من الـ apps التانية والـ backups والموبايل المقفول. مابيحميش من موبايل rooted والـ app شغال، ولا من حد ماسك الموبايل مفتوح. التانية بحلها بقفل بصمة اختياري فوق الـ session. والأولى مالهاش حل على الجهاز: access token قصير، وrefresh token بيتلغي من السيرفر، وشاشة أجهزة فيها «اخرج». وأي secret حقيقي مايدخلش الـ app خالص، والـ CI بيعمل scan على الـ repo وعلى الـ binary.

</Answer>

<Ask>بتعمل certificate pinning في الـ apps بتاعتك؟</Ask>
<Answer>

بقرر من الـ threat model: الـ pinning بيحمي من CA مزيفة على الجهاز أو الشبكة، ومابيحميش الـ API من حد بيفك الـ app. لو قررته، بثبّت الـ CA مش الشهادة، لأن الشهادات بتتجدد كل 90 يوم أو أقل. ومعاه CA احتياطية، وتاريخ بعده النسخة القديمة ترجع لـ HTTPS العادي بدل ما تموت، وcheck في الـ CI على الشهادة الحالية. وفي Dio بعمله بـ `SecurityContext(withTrustedRoots: false)` في الـ handshake، مش `validateCertificate`، لأن ده بيتنادى بعد ما الطلب بالـ token اتبعت. ولـ app زي Readly غالبًا HTTPS عادي كفاية، وApp Check على الـ endpoints الغالية أهم.

</Answer>

<Question id="interview-89">
<Ask>إزاي بتعمل feature flags في Flutter؟</Ask>
<Answer>

contract `FeatureFlags` في الـ domain، والـ flags enum كل واحد معاه fallback ونوعه. وRemote Config في الـ data: `setDefaults` من الـ fallbacks، و`activate` للقيم اللي اتجابت في الفتحة اللي قبلها، و`fetch` في الخلفية للجاية، فالـ startup مابيستناش شبكة والـ UI مابيتغيرش في نص الاستخدام. الـ kill switches بس بتتحدث لحظيًا، وبتوقّف الطلبات مش الـ UI بس. الـ release flag الـ fallback بتاعه off، والـ kill switch on. الـ rollout بنسبة، والـ flags tags في Sentry عشان أقارن المجموعتين، والتست بـ fake. وكل release flag ليه تاريخ مسح بيبقى تست بيوقع.

</Answer>
