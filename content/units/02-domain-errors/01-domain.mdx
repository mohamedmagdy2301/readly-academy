<Level n="1" title="الفكرة بتشبيه">

<Analogy title="الكتاب والفلوس والوصفة">

الـ <b>Entity</b> هي الكتاب نفسه في مكتبتك، ليه هوية (id) حتى لو غيّرت عنوانه. الـ <b>Value Object</b> زي الفلوس: ورقة الـ 100 جنيه زي أي ورقة 100 جنيه تانية، المهم القيمة مش الورقة نفسها، ومافيش حاجة اسمها «سالب 5 جنيه». الـ <b>Use Case</b> زي وصفة: خطوات محددة لعملية واحدة، زي «ضيف كتاب لمكتبتك». والـ <b>Repository Contract</b> هو ورقة الطلبات اللي الشيف بيبعتها للمخزن.

</Analogy>

كل الحاجات دي مكتوبة بـ Dart صافي: مفيش Flutter، ولا dio، ولا JSON. لو بكرة قررت تعمل نسخة ويب أو CLI من Readly، الـ Domain هيتنقل زي ما هو.


</Level>

```dart
// domain/book.dart
class Book {
  const Book({required this.id, required this.title, required this.status});

  final BookId id;
  final String title;
  final BookStatus status;
}

enum BookStatus { wantToRead, reading, finished }
```

</CodeBlock>

<CodeBlock label="Repository contract">

```dart
// domain/library_repository.dart
abstract interface class LibraryRepository {
  Future<Result<List<Book>>> getLibrary();
  Stream<List<Book>> watchLibrary();
  Future<Result<void>> addBook(Book book);
  Future<bool> contains(BookId id);
}
```

</CodeBlock>

<CodeBlock label="Use case">

```dart
// domain/add_book_to_library.dart
class AddBookToLibrary {
  AddBookToLibrary(this._repository);

  final LibraryRepository _repository;

  Future<Result<void>> call(Book book) async {
    if (await _repository.contains(book.id)) {
      return const Err(ValidationFailure('Book already in library'));
    }
    return _repository.addBook(book);
  }
}
```

</CodeBlock>

لاحظ إن الـ use case فيه قاعدة حقيقية: «الكتاب مايتضافش مرتين». وعشان اسم الـ method هو `call`، تقدر تناديه كأنه function: `addBook(book)`.

### Invariants: قواعد لازم تفضل صح دايمًا

الـ invariant قاعدة مايصحش تتكسر أبدًا، زي «الـ BookId مايبقاش فاضي». أحسن مكان تحميها فيه هو لحظة إنشاء الـ object، عشان مايبقاش في أي object غلط في المشروع أصلًا:

<CodeBlock label="Value object بيحمي نفسه">

```dart
extension type const BookId._(String value) {
  static Result<BookId> create(String raw) {
    final v = raw.trim();
    if (v.isEmpty) return const Err(ValidationFailure('Empty book id'));
    return Success(BookId._(v));
  }
}
```

</CodeBlock>

الـ constructor خاص (`._`)، فالطريقة الوحيدة إنك تعمل BookId هي `create` اللي بتتحقق. ده اسمه <b>valid by construction</b>.

<Diagram name="d-e4975a558e">

الـ validation بتحصل عند الباب بس. أي حتة في الكود ماسكة BookId متأكدة إنه صح، ومش محتاجة تتحقق تاني.

</Diagram>

### Entity غنية ولا فاضية؟

الـ entity «الفاضية» (anemic) فيها حقول بس، وكل الـ logic بره. الـ entity «الغنية» فيها سلوكها:

<CodeBlock label="سلوك جوه الـ entity">

```dart
class Book {
  // ...fields
  Book markAsFinished() => Book(id: id, title: title, status: BookStatus.finished);

  bool get canBeReviewed => status == BookStatus.finished;
}
```

</CodeBlock>

كده قاعدة «تقدر تكتب review بس للكتاب اللي خلصته» مكتوبة في مكان واحد، بدل ما تتكرر في كل شاشة.

### StreamUseCase: لما النتيجة بتتغير مع الوقت

كل الـ use cases لحد دلوقتي بترجّع `Future`: بتسأل مرة وبتاخد إجابة مرة. بس شاشة المكتبة محتاجة تعرف <b>كل ما</b> المكتبة تتغير: المستخدم ضاف كتاب من شاشة الكتالوج، أو علّم كتاب إنه خلّصه من صفحته. لو المكتبة سألت مرة واحدة، هتفضل عارضة الليست القديمة لحد ما حد يسأل تاني.

السبب إن الـ Future بيرجّع قيمة واحدة وبيخلص. اللي محتاجه هنا <b>Stream</b>: قيمة جديدة كل ما البيانات تتغير، لحد ما اللي بيسمع يقول «كفاية». والـ contract فيه ده أصلًا: `watchLibrary()` بيرجّع `Stream<List<Book>>`، يعني وعد إن الـ repository هيطلّع الليست كاملة من جديد مع كل تغيير. إزاي بيعرف إن في تغيير ده شغل الـ Data، والـ Domain يهمه الوعد بس.

ولو الشاشة محتاجة الكتب اللي بتقراها دلوقتي بس ومترتبة بالعنوان، القاعدة دي مكانها use case، بنفس شكل اللي فاتوا بس بيرجّع Stream:

<CodeBlock label="StreamUseCase">

```dart
// domain/stream_use_case.dart
abstract class StreamUseCase<T, P> {
  Stream<T> call(P params);
}

// domain/watch_library.dart
class WatchLibraryParams {
  const WatchLibraryParams({this.status});
  final BookStatus? status; // null: every book
}

class WatchLibrary extends StreamUseCase<List<Book>, WatchLibraryParams> {
  WatchLibrary(this._repository);
  final LibraryRepository _repository;

  @override
  Stream<List<Book>> call(WatchLibraryParams params) =>
      _repository.watchLibrary().map((books) => books
          .where((b) => params.status == null || b.status == params.status)
          .toList()
        ..sort((a, b) => a.title.compareTo(b.title)));
}
```

</CodeBlock>

<CodeBlock label="الاستخدام">

```dart
final watchLibrary = WatchLibrary(repository);

final sub = watchLibrary(const WatchLibraryParams(status: BookStatus.reading))
    .listen((books) {
  // called now, and again after every change in the library
});

// when the screen closes
await sub.cancel();
```

</CodeBlock>

- <b>الـ T والـ P:</b> الـ T نوع اللي بيطلع من الـ stream، والـ P نوع الـ params. كده كل stream use case في المشروع شكله واحد: بتناديه بـ params، وبتعمل listen على اللي راجع.
- <b>الـ map:</b> بيطبّق القاعدة على كل ليست جديدة بتطلع من الـ repository. فالفلترة والترتيب بيحصلوا مع كل تغيير، مش مرة واحدة.
- <b>من غير Result:</b> الـ stream بيقول «المكتبة دلوقتي شكلها كده»، مش «طلب نجح أو فشل». التحميل من السيرفر وأخطاؤه لسه في `getLibrary()`.
- <b>الـ cancel:</b> اللي بيعمل listen لازم يعمل cancel لما يخلص، وإلا الـ stream هيفضل شغال ومحدش بيعرض نتايجه.

|  | use case بـ Future | StreamUseCase |
| --- | --- | --- |
| بيرجّع | قيمة واحدة وبيخلص | قيمة جديدة مع كل تغيير |
| بتستخدمه بـ | `await` | `listen` وبعدين `cancel` |
| مثال في Readly | `AddBookToLibrary`، `SearchBooks` | `WatchLibrary` |

امتى تعمل StreamUseCase، وامتى اللي بيستخدم يسمع على `watchLibrary()` مباشرة؟ نفس السؤال بتاع أي use case: <b>في قاعدة ولا لأ؟</b> لو في فلترة أو ترتيب أو دمج stream من repositoryين، يبقى use case، والقاعدة تتختبر بـ dart test. لو الشاشة عايزة الليست زي ما هي، الـ use case هيبقى سطر بينادي `watchLibrary()` وبس، وده ملف زيادة.

الـ Future للسؤال اللي ليه إجابة واحدة، والـ Stream للحاجة اللي بتتغير، والـ StreamUseCase بيتعمل لما يكون في قاعدة على اللي بيتغير.

### علّمت الكتاب «خلصته» والشاشة ماتغيرتش

الـ Entity هويتها الـ id، فطبيعي تفكر تخلي `==` تقارن الـ id بس: كتابين بنفس الـ id يبقوا نفس الكتاب. الكلام ده صح في الـ DDD، بس في Flutter بيعمل bug صعب تلاقيه:

<CodeBlock label="== بالـ id بس">

```dart
class Book {
  // ...fields
  @override
  bool operator ==(Object other) => other is Book && other.id == id; // id only
  @override
  int get hashCode => id.hashCode;
}

// in LibraryCubit: LibraryLoaded uses equatable, props: [books]
final updated = [
  for (final b in current.books) b.id == id ? b.markAsFinished() : b,
];
emit(LibraryLoaded(updated)); // ignored!
```

</CodeBlock>

الـ equatable بيقارن الليستتين عنصر عنصر بـ `==` بتاع Book. الكتاب القديم والجديد ليهم نفس الـ id، فالليستتين «متساويين»، فالـ state الجديدة بتساوي القديمة. والـ Cubit بيتجاهل أي emit لـ state بتساوي اللي قبلها، فالشاشة فاضلة «بقراه». ونفس الحكاية مع `BlocSelector` و`Stream.distinct()` و`didUpdateWidget`: كلهم بيسألوا `==` «في حاجة اتغيرت؟»، وانت جاوبتهم «لأ».

الحل إنك تفصل بين سؤالين مختلفين:

<CodeBlock label="سؤالين، مش سؤال واحد">

```dart
@freezed
abstract class Book with _$Book {
  const Book._();
  const factory Book({
    required BookId id,
    required String title,
    required BookStatus status,
  }) = _Book; // == compares every field: "did anything change?"

  bool isSameBookAs(Book other) => other.id == id; // "is it the same book?"
}
```

</CodeBlock>

- <b>الـ ==:</b> بيقارن كل الحقول، لأن Flutter كله مبني على إن `==` معناها «مفيش حاجة اتغيرت».
- <b>الهوية:</b> بتتسأل صراحة بـ `a.id == b.id` أو method باسم واضح. ولما تحتاج Map أو Set بالكتب، خلي الـ key هو الـ `BookId` مش الـ Book.

### القاعدة دي السيرفر بيتحقق منها كمان، أكتبها في الـ app؟

أي قاعدة في الـ app ليها نسخة على السيرفر، لأن أي حد يقدر يبعت request من غير الـ app. السؤال مش «مين يتحقق»، السؤال «أنهي قواعد تستاهل نسخة تانية في الـ app». كل نسخة زيادة ممكن تختلف عن الأصل، والأخطر إن الـ app القديم بيفضل على موبايلات الناس شهور. لو السيرفر خفّف قاعدة والـ app لسه شادد، المستخدم ممنوع من حاجة مسموحة، ومش هيعرف ليه.

| نوع القاعدة | مثال في Readly | مكانها |
| --- | --- | --- |
| شكل الـ input | الإيميل فيه @، والباسورد 8 حروف على الأقل | value object في الـ domain، والسيرفر بيتحقق تاني |
| على بيانات موجودة عندك | الكتاب مايتضافش للمكتبة مرتين | use case، لأن المكتبة كلها عندك في الـ DB |
| محتاجة بيانات مش عندك | الإيميل ده مستخدم قبل كده؟ | السيرفر بس، والـ app بيعرض رده على الحقل |
| بتتغير من غير release | الخطة المجانية فيها 100 كتاب بس | السيرفر بس |

### use case بيكلّم repositoryين: والتاني فشل

لما المستخدم يشيل كتاب من مكتبته، ملاحظاته على الكتاب ده لازم تتشال كمان. ده repositoryين في عملية واحدة، ومكانها use case:

<CodeBlock label="RemoveBookFromLibrary">

```dart
class RemoveBookFromLibrary {
  RemoveBookFromLibrary(this._library, this._notes);
  final LibraryRepository _library;
  final NotesRepository _notes;

  Future<Result<void>> call(BookId id) async {
    // the book first: if this fails, nothing changed
    switch (await _library.removeBook(id)) {
      case Err(:final failure):
        return Err(failure);
      case Success():
        return _notes.deleteNotesFor(id); // safe to call again
    }
  }
}
```

</CodeBlock>

مفيش transaction بين repositoryين، فلازم تفكر: لو الخطوة التانية فشلت، الحالة اللي فاضلة شكلها إيه؟

- <b>لو بدأت بالملاحظات:</b> الملاحظات اتمسحت والكتاب فضل. المستخدم خسر حاجة كتبها بإيده، والكتاب لسه قدامه كأن مفيش حاجة حصلت.
- <b>لو بدأت بالكتاب:</b> الكتاب اتشال والملاحظات فضلت من غير كتاب. مش ظاهرة لحد، وأي محاولة تانية بتمسحها، لأن `deleteNotesFor` لكتاب مالوش ملاحظات بيرجّع Success عادي.

القاعدة: رتّب الخطوات بحيث إن الفشل في النص يسيب أقل حالة ضرر، وخلي الخطوة التانية تنفع تتعاد (idempotent). ولو الاتنين جداول في نفس الـ drift DB، الأحسن الـ use case يطلب الحاجة بنيّتها: method واحدة زي `removeBookWithNotes` في الـ repository، والـ data layer ينفذها في transaction. الـ domain يقول «عايز إيه»، والـ data يعرف «إزاي تتعمل مرة واحدة».


</Level>

<Level n="4" title="قرارات صعبة">

- <b>الـ use case الـ pass-through:</b> لو الـ use case بينادي الـ repository وبس من غير أي قاعدة، فهو ملف زيادة. عندك اختيارين: تسيبه عشان كل الـ features شكلها واحد، أو الـ Cubit يكلّم الـ repository مباشرة لما مفيش logic. الاتنين صح، الغلط إنك تعمل كده من غير ما تقرر.
- <b>تركيب الـ use cases:</b> use case ممكن يستخدم أكتر من repository، زي `RemoveBookFromLibrary`. ده مكانه الطبيعي use case مش Cubit، لأن الـ Cubit مايصحش يقرر ترتيب الخطوات ولا يعرف إن الملاحظات تابعة للكتاب.
- <b>use case بينادي use case تاني؟</b> غالبًا لأ. لو `FinishBook` محتاج قاعدة موجودة في `AddBookToLibrary`، القاعدة دي مكانها الـ entity أو function صافية في الـ domain (domain service) والاتنين يستخدموها. لما use case ينادي التاني، الـ checks بتتكرر، وتغيير في واحد بيكسر التاني من غير ما تاخد بالك.
- <b>الـ transaction بين repositoryين:</b> في حل تاني غير method واحدة: abstraction في الـ domain زي `TransactionRunner` والـ use case يلف الخطوتين بيه. بيشتغل، بس كل الـ repositories لازم يكونوا على نفس الـ DB، وفكرة «transaction» بقت جوه الـ domain. في Readly الـ method الواحدة أوضح. ولو واحد من الاتنين على السيرفر، مفيش transaction أصلًا: الترتيب والـ idempotency، والأحسن السيرفر يمسح الملاحظات لوحده لما الكتاب يتشال.
- <b>الوقت قاعدة كمان:</b> لو `markAsFinished` محتاجة تسجّل امتى الكتاب خلص، ماتناديش `DateTime.now()` جوه الـ entity. خليها تاخد الوقت كـ parameter، والـ use case ياخده من `Clock` (من درس SOLID)، فالتست يحدد الوقت بنفسه.
- <b>الـ Domain بيتختبر بـ dart test:</b> لأنه مافيهوش Flutter، تستاته بتشتغل في أجزاء من الثانية. لو احتجت Flutter عشان تختبر قاعدة، يبقى القاعدة دي في مكان غلط.

<Note kind="interview" title="سؤال interview">

«إيه الفرق بين Entity وValue Object؟» الـ Entity ليها هوية (id) وبتفضل نفس الحاجة حتى لو بياناتها اتغيرت. الـ Value Object مالوش هوية: اتنين بنفس القيمة يبقوا نفس الحاجة، وبيحمي قواعده من لحظة إنشائه. ولو سألك «يبقى الـ == في الـ Entity بالـ id؟»: في Flutter لأ، الـ == بيقارن كل الحقول عشان الـ Cubit والـ widgets يعرفوا إن حاجة اتغيرت، والهوية بتتسأل صراحة بالـ id.

</Note>

<Note kind="interview" title="سؤال interview">

«use case بيعمل خطوتين على repositoryين، والتانية فشلت. تعمل إيه؟» مفيش transaction بين repositoryين، فبرتّب الخطوات بحيث الفشل في النص يسيب أقل ضرر (الكتاب الأول، والملاحظات بعده)، والخطوة التانية تنفع تتعاد. ولو الاتنين في نفس الـ DB، بنقل العملية لـ method واحدة في الـ data layer تتنفذ في transaction، والـ domain يفضل بيعبّر عن النيّة بس.

</Note>


</Level>

### الـ value object بـ extension type

الـ Email مايتعملش غير وهو valid، فأي كود ماسك Email مش محتاج validation تاني. والـ extension type ملوش تكلفة في الـ runtime.

```dart
extension type const Email._(String value) {
  static final _pattern = RegExp(r'^[^@\s]+@[^@\s]+\.[^@\s]+$');

  static Result<Email> create(String input) {
    final normalized = input.trim().toLowerCase();
    return _pattern.hasMatch(normalized)
        ? Success(Email._(normalized))
        : const Err(ValidationFailure('Invalid email'));
  }
}
```
