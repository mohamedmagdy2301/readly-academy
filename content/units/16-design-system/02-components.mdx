<Analogy title="سلسلة محلات الفطير">

سلسلة محلات فطير ليها 20 فرع. أي فرع تدخله، الفطيرة نفس الحجم ونفس الطعم. السر مش إن الطباخين شاطرين، السر في <b>كارت الطلب</b>: فيه الحجم (صغير، كبير)، والحشو من ليستة ثابتة، وخلاص. الكاشير مايقدرش يوعدك «اعملهالي أرفع شوية»، لأن الكارت مافيهوش الخانة دي. ولو كل فرع زوّد خانات على مزاجه، بعد سنة هيبقى عندك 20 فطيرة مختلفة.

والمطبخ مايعرفش انت مين. مش بيسأل «ده زبون دايم؟». بياخد الكارت، ويطلّع الفطيرة. اللي يعرف الزبون هو الكاشير اللي برا.

</Analogy>

الـ component في الـ design system هو الفطيرة، والـ constructor بتاعه هو كارت الطلب. كل parameter خانة في الكارت: لو الخانات قليلة وواضحة، كل الشاشات هتطلع شبه بعض. ولو فيه `color` و`padding` و`fontSize` مفتوحين، كل شاشة هتعمل نسختها.

والـ component مايعرفش الـ domain. `ReadlyButton` مايعرفش إن ده زرار «ضيف للمكتبة». بياخد نص وcallback، والشاشة هي اللي تعرف المعنى.

</Level>

### الخطوة الأولى: theme للـ Material widgets

قبل ما تكتب أي component، اسأل: هل الـ `FilledButton` العادي ممكن يبقى شكل Readly لو ظبطت الثيم بتاعه؟ غالبًا أيوه:

<CodeBlock label="AppTheme: الأزرار بتاخد شكل Readly في كل مكان">

```dart
static ThemeData _build(Brightness brightness) {
  final scheme = ColorScheme.fromSeed(seedColor: Palette.teal600, brightness: brightness);

  const minSize = Size(64, 48);

    colorScheme: scheme,

      style: FilledButton.styleFrom(shape: shape, minimumSize: minSize),
    ),
    outlinedButtonTheme: OutlinedButtonThemeData(
      style: OutlinedButton.styleFrom(shape: shape, minimumSize: minSize),
    ),
    textButtonTheme: TextButtonThemeData(
      style: TextButton.styleFrom(shape: shape, minimumSize: minSize),
```

</CodeBlock>

ونفس الكود بالظبط في زرار الـ retry بتاع `ErrorView`. وفي زرار «احفظ الملاحظة». 3 نسخ، وفيهم نفس المشكلتين اللي هتشوفهم في Level 3: الزرار بيصغر لما الـ spinner يظهر، وقارئ الشاشة بيقول «زرار» من غير اسم. ده سلوك مش شكل، والثيم مايقدرش يعمله. يبقى component:

<CodeBlock label="packages/core_ui/lib/src/components/readly_button.dart">

```dart
enum ReadlyButtonVariant { primary, secondary, text, danger }

class ReadlyButton extends StatelessWidget {
  const ReadlyButton({
    super.key,
    required this.label,
    required this.onPressed,
    this.variant = ReadlyButtonVariant.primary,
    this.icon,
    this.loading = false,
    this.expand = false,
  });

  final String label;
  final VoidCallback? onPressed; // null = disabled, like every Flutter button
  final ReadlyButtonVariant variant;
  final IconData? icon;
  final bool loading;
  final bool expand; // full width, for forms and bottom bars

  @override
  Widget build(BuildContext context) {
    final scheme = context.colorScheme;
    final content = Stack(
      alignment: Alignment.center,
      children: [
        // keeps the button's width, and keeps the label for screen readers
        Opacity(
          opacity: loading ? 0 : 1,
          alwaysIncludeSemantics: true,
          child: icon == null
              ? Text(label)
              : Row(
                  mainAxisSize: MainAxisSize.min,
                  children: [Icon(icon, size: 18), const SizedBox(width: AppSpace.sm), Text(label)],
                ),
        ),
        if (loading)
          const SizedBox.square(
            dimension: 20,
            child: CircularProgressIndicator(strokeWidth: 2),
          ),
      ],
    );
    final pressed = loading ? null : onPressed;

    final button = switch (variant) {
      ReadlyButtonVariant.primary => FilledButton(onPressed: pressed, child: content),
      ReadlyButtonVariant.secondary => OutlinedButton(onPressed: pressed, child: content),
      ReadlyButtonVariant.text => TextButton(onPressed: pressed, child: content),
      ReadlyButtonVariant.danger => FilledButton(
          onPressed: pressed,
          style: FilledButton.styleFrom(
            backgroundColor: scheme.error,
            foregroundColor: scheme.onError,
          ),
          child: content,
        ),
    };
    return expand ? SizedBox(width: double.infinity, child: button) : button;
  }
}
```

</CodeBlock>

- <b>الـ `onPressed: null` معناها disabled:</b> نفس عرف Flutter في كل زرار. مفيش `enabled: false` جنبها، عشان مايبقاش فيه طريقتين لنفس الحاجة، ومايبقاش فيه حالة غريبة زي `enabled: true` و`onPressed: null`.
- <b>الـ `loading` بيقفل الزرار لوحده:</b> الشاشة مش محتاجة تكتب `submitting ? null : ...`. وده ماكانش بيحمي من الضغط المتكرر لوحده: الحماية الحقيقية في الـ Cubit زي ما قلنا في درس الـ Forms. الزرار المقفول للشكل.
- <b>الـ variant enum:</b> 4 اختيارات بس، والـ `switch` بيجبرك تغطيهم كلهم. وفي التست تقدر تلف على `ReadlyButtonVariant.values` وتصوّرهم كلهم في golden واحد.
- <b>الـ `Opacity` والـ `Stack`:</b> النص بيفضل موجود وهو شفاف، فالزرار مايصغرش لما الـ spinner يظهر. و`alwaysIncludeSemantics: true` بيخلي قارئ الشاشة يقرا اسم الزرار حتى وهو شفاف.
- <b>المقاسات والألوان من الثيم:</b> الـ component مافيهوش `minimumSize` ولا shape. دول جايين من الـ `filledButtonTheme` اللي فوق. الـ component بيزوّد السلوك بس.

| | في `core_ui` | في الـ feature |

### الـ ErrorView اتنقل والـ build وقف

<b>اللي بيبوظ:</b> بتنقل `ErrorView` من `apps/readly/lib/core/ui/` لـ `core_ui`. أول سطر بيضرب: `AppLocalizations.of(context)!.retry`. الـ `AppLocalizations` في الـ app، والـ `core_ui` مايقدرش يعمل import للـ app، لأن الـ app بيعتمد عليه. ولو حاولت تزوّد الـ app في الـ dependencies بتاعة الـ core_ui، هيبقى عندك دايرة.

<b>ليه:</b> الـ component كان بيعرف حاجة مش بتاعته: النص. وده كان شغال لأنه كان جوه الـ app.

<b>الحل:</b> النص يدخل من برا، زي أي حاجة تانية:

<CodeBlock label="ErrorView في core_ui">

والشاشات اللي بتستخدمه كتير بتعمل helper صغير في الـ feature أو الـ app: `ErrorView(retryLabel: l10n.retry, ...)`. الـ `assert` بيمسك اللي نسي الـ label وهو بيطوّر، بدل ما الزرار يطلع فاضي.

والبديل الأكبر: `core_ui` يبقى ليه ملف ARB بتاعه (الـ `flutter gen-l10n` بيشتغل جوه أي package)، والـ app يضيف الـ delegate بتاعه في `localizationsDelegates`. يستاهل لما الـ components تبقى فيها نصوص ثابتة كتير («إلغاء»، «اقفل»، «حاول تاني»). لـ 3 نصوص، الـ parameters أبسط.

### الـ goldens بتاعة core_ui طالعة بخط غلط

<b>اللي بيبوظ:</b> الـ components في الـ app شكلها تمام. بس أول golden في `packages/core_ui/test/` طالع بالمربعات، حتى بعد ما نقلت `flutter_test_config.dart` بتاع [درس الـ goldens](/course/testing/golden-tests/) جوه الـ package.

<b>ليه:</b> خط Cairo متعرّف في الـ pubspec بتاع الـ app. الـ `loadAppFonts` بيقرا الـ `FontManifest.json` بتاع الـ package اللي التست شغال فيها، والـ `core_ui` مافيهاش خطوط. الـ package بتعتمد على حاجة موجودة برّاها بس، وده نفس الغلط بتاع الـ `AppLocalizations`.

<b>الحل:</b> الخط جزء من الـ design system، فمكانه `core_ui`:

<CodeBlock label="الخط في core_ui">

```yaml
# packages/core_ui/pubspec.yaml
flutter:
  fonts:
    - family: Cairo
      fonts:
        - asset: fonts/Cairo-Regular.ttf
        - asset: fonts/Cairo-Bold.ttf

```


الخط اللي متعرّف في package اسمه الحقيقي `packages/core_ui/Cairo`. والـ `package:` في الـ `ThemeData` بيزوّد البادئة دي على كل الـ text themes، وده نفس الـ `package:` اللي في `TextStyle` و`AssetImage`. ومن غيره الـ app هيدوّر على `Cairo` في خطوطه هو، ومش هيلاقيه، ويرجع للخط الافتراضي من غير ولا error. والـ `FontManifest.json` بتاع الـ app فيه خطوط كل الـ packages اللي بيعتمد عليها، فالـ `loadAppFonts` في تستات الـ app لسه شغال.

### زرار بـ 4 booleans

<b>اللي بيبوظ:</b> الـ `ReadlyButton` الأول كان كده:

```dart
ReadlyButton(label: '...', isPrimary: true, isOutlined: true, isDanger: true, isSmall: false)
```

يعني primary وoutlined في نفس الوقت؟ والـ danger يكسب ولا الـ primary؟ كل واحد في الفريق جاوب بطريقة، والكود جواه بقى `if` جوه `if`.

<b>ليه:</b> 4 booleans معناهم 16 تركيبة، و4 بس منهم ليها معنى. الـ API بيسمح بحاجات الـ design مافيهاش.

<b>الحل:</b> اللي مايجتمعوش مع بعض يبقوا enum واحد (`variant`). والـ booleans تفضل للحاجات اللي فعلًا مستقلة: `loading` و`expand` ممكن يبقوا مع أي variant. القاعدة: لو boolean ماينفعش يبقى true مع boolean تاني، الاتنين قيم في enum.

### «ممكن أعدّي لون للزرار ده بس؟»

<b>اللي بيبوظ:</b> شاشة الـ onboarding عايزة زرار أبيض على صورة. حد زوّد `Color? backgroundColor` في `ReadlyButton` «عشان الشاشة دي بس». بعد 3 شهور فيه 14 شاشة بتعدّي ألوان، ونص الأزرار في الـ dark mode مش مقروءة، لأن كل واحد عدّى لون من غير الـ `on` بتاعه.

<b>ليه:</b> كل parameter مفتوح باب. والباب ده بيدخل منه كل القرارات اللي الـ design system كان موجود عشان يمنعها.

<b>الحل:</b> قبل ما تفتح parameter، اسأل: ده variant جديد ولا استثناء؟

- <b>لو بيتكرر وله معنى</b> (زرار على خلفية صورة)، ده variant: `ReadlyButtonVariant.onImage`، بلون معمول له حساب في الـ light والـ dark، بعد ما الـ designer يوافق.
- <b>لو استثناء فعلًا في شاشة واحدة</b>، الشاشة تلف الزرار في `Theme` بـ `copyWith` (زي درس الـ tokens) أو تستخدم `FilledButton` بـ style خاص. الاستثناء يبان في الشاشة اللي عملته، مش يبقى جزء من الـ API لكل الناس.

### component بيعمل كل حاجة

<b>اللي بيبوظ:</b> الـ `BookTile` بقى بياخد 19 parameter: `showStatus` و`showProgress` و`compact` و`onLongPress` و`trailing` و`showSyncBadge` و`highlightQuery`... وفيه 6 أماكن بتستخدمه، كل واحد بتركيبة مختلفة. أي تعديل في واحد بيكسر التاني.

<b>ليه:</b> الـ component بيحاول يبقى كل الـ tiles في الـ app. الـ parameters الكتير علامة إن فيه أكتر من component جواه.

<b>الحل:</b> اقسم حسب الاستخدام الحقيقي: `BookTile` في المكتبة، و`CatalogResultTile` في البحث (فيه highlight ومافيهوش حالة). والحاجات المشتركة بينهم (الغلاف، العنوان بالـ style بتاعه) تبقى widgets صغيرة يتبنوا منها. نسختين واضحين أحسن من component واحد بـ 19 خانة.

### الـ component بيجيب الـ Cubit بنفسه

<b>اللي بيبوظ:</b> حد كتب `SyncBadge` بيعمل `getIt<SyncService>()` جوه الـ `initState`. شغال في الـ app، بس مايتحطش في catalog، ومايتستّش من غير get_it، ولو اتحط في شاشة قبل ما الـ DI يجهز بيقع.

<b>ليه:</b> الـ widget بيجيب الـ data بتاعته بنفسه بدل ما ياخدها.

<b>الحل:</b> الـ `SyncBadge` في [درس عمر الـ subscription](/course/dart-async/lifecycle/) بياخد `Stream<int>` من برا، وده الصح. القاعدة لأي component: الـ data بتدخل من الـ constructor، والأحداث بتطلع بـ callbacks. اللي بيوصّل الـ Cubit هو الشاشة أو الـ Page، زي ما اتعمل في [درس الـ flutter_bloc widgets](/course/state-management/flutter-bloc-widgets/).

### الـ catalog: تشوف كل حاجة في مكان واحد

<b>اللي بيبوظ:</b> الـ designer سأل «الزرار الـ danger وهو loading شكله إيه في الـ dark؟». عشان تشوفه لازم تفتح شاشة فيها زرار danger، وتعمل حاجة تخليه loading، وتقلب dark. 5 دقايق لسؤال واحد.

```dart
            IconButton(
              tooltip: 'Dark',
              icon: const Icon(Icons.dark_mode_outlined),
              onPressed: () => setState(() =>
                  _mode = _mode == ThemeMode.light ? ThemeMode.dark : ThemeMode.light),
            ),
            IconButton(
              tooltip: 'RTL / LTR',
              icon: const Icon(Icons.translate),
              onPressed: () => setState(() =>
                  _locale = _locale.languageCode == 'ar' ? const Locale('en') : const Locale('ar')),
            ),
          ]),
          body: ListView(
            padding: const EdgeInsets.all(AppSpace.lg),
            children: [
              for (final v in ReadlyButtonVariant.values) ...[
                ReadlyButton(label: 'احفظ ${v.name}', variant: v, onPressed: () {}),
                const SizedBox(height: AppSpace.sm),
                ReadlyButton(label: 'loading ${v.name}', variant: v, loading: true, onPressed: () {}),
                const SizedBox(height: AppSpace.sm),
                ReadlyButton(label: 'disabled ${v.name}', variant: v, onPressed: null),
                const SizedBox(height: AppSpace.lg),
              ],
            ],
          ),
        ),
      );
}
```

</CodeBlock>

بيعتمد على `core_ui` بس، فبيفتح في ثانية من غير backend ولا login. وده نفس الـ matrix اللي الـ golden tests بتصوّرها في [درس تست الـ Design System](/course/design-system/testing-ds/). ولو الـ catalog كبر، فيه packages معمولة للفكرة دي زي widgetbook، بتديك knobs تغيّر بيها الـ parameters من الـ UI.

</Level>

<Level n="4" title="قرارات الـ senior">

- <b>theme الأول، component تاني:</b> لو اللي عايزه شكل بس (لون، radius، ارتفاع)، ظبّط الـ Material theme. كل `FilledButton` في الـ app هيمشي وراه، حتى اللي محدش فاكر يستخدم الـ component فيه. اعمل component لما في سلوك (loading)، أو تركيبة بتتكرر (أيقونة + نص + spinner)، أو لما عايز تقفل اختيارات (4 variants بس).
- <b>القاعدة التلاتية:</b> أول مرة تكتب الحاجة في الشاشة. تاني مرة تنسخها وتاخد بالك. تالت مرة تعملها component. الـ component اللي اتعمل من أول استخدام بيتصمم على حالة واحدة، وبيتكسر في التانية.
- <b>اتبع عرف Flutter:</b> `onPressed` nullable للـ disabled، `child` لو بتاخد widget و`label` لو بتاخد نص، `const` constructor، و`super.key`. اللي بيستخدم الـ component عارف Flutter، فكل حاجة شبهه بتبقى مفهومة من غير docs.
- <b>data جوا، callbacks برا:</b> الـ component مابيعملش `getIt` ولا `context.read` ولا navigation. ده اللي بيخليه يتحط في catalog ويتصوّر في golden ويتنقل بين features.
- <b>مين بيغيّر الـ core_ui؟</b> أي تعديل فيه بيلمس كل الـ features. خليه في الـ CODEOWNERS بتاع واحد أو اتنين في الفريق، وأي PR فيه component جديد أو parameter جديد بيتراجع من حد بيفكر في الـ API، مش بس في الشاشة اللي محتاجاه.
- <b>الـ core_ui بيحميك من تغييرات Flutter نفسه:</b> مثال حي: Flutter بينقل الـ Material والـ Cupertino من الـ framework لـ packages منفصلة (`material_ui` و`cupertino_ui`)، ومن 3.47 بقوا متاحين opt-in، والـ `package:flutter/material.dart` هيبقى deprecated في نسخة جاية. لو كل feature بتبني أزرارها من `FilledButton` على طول، الهجرة بتلمس كل ملف. لو الـ features بتستخدم `ReadlyButton` والثيم في `core_ui`، أغلب الهجرة في package واحدة.
- <b>تغيير API مستخدم في 40 مكان:</b> في workspace مفيش versions: كل الـ features بتشوف نفس النسخة من `core_ui` في نفس اللحظة. فالتغيير اللي بيكسر بيتعمل على مرحلتين: الـ API الجديد يدخل والقديم عليه `@Deprecated('Use variant: ReadlyButtonVariant.danger')`، فالـ analyzer بيعلّم على كل مكان. وبعد ما الأماكن تتنقل، القديم يتشال. ولو التغيير ميكانيكي، Dart بيدعم data-driven fixes (ملف `lib/fix_data.yaml` في الـ package)، فـ `dart fix --apply` بينقل الأماكن كلها لوحده.

<Note kind="interview" title="سؤال interview">

«بتصمم الـ API بتاع component مشترك إزاي؟» أبدأ بسؤال: الـ Material widget بالثيم كفاية؟ لو أيوه مش هعمل component. لو لأ، الـ API بيبقى أضيق ما يمكن: الاختيارات اللي ماتجتمعش enum واحد (variant)، والحالات المستقلة booleans (loading)، والـ disabled هو `onPressed: null` زي Flutter. مفيش parameters للون أو الـ padding، لأن دي قرارات الـ design system مش الشاشة، والاستثناء الحقيقي بيتعمل بـ Theme override في الشاشة نفسها. الـ component مايعرفش الـ domain ولا الـ l10n ولا الـ DI: النصوص والـ data بتدخل، والأحداث بتطلع. وبيتحط في package في قاع الشجرة، وليه catalog وgoldens بكل variant وحالة.

</Note>

</Level>

</Answer>
