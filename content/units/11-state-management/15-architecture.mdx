<Level n="1" title="الفكرة بتشبيه">

<Analogy title="فندق كبير">

في الفندق، كل حاجة ليها مكان وعمر. <b>الاستقبال والأمن</b> موجودين طول ما الفندق فاتح، وكل النزلا بيتعاملوا مع نفس الموظفين. <b>الدور</b> بتاعك بيتفتح لك من ساعة الـ check-in، ولما تعمل check-out الكارت بتاعك بيتلغي وكل حاجة على الدور ليك بتتشال. <b>الأوضة</b> بتتجهز لما تدخلها، وبتتنضف أول ما تسيبها. و<b>الأباجورة</b> اللي جنب السرير ليها مفتاح لوحدها، ومحدش في الاستقبال محتاج يعرف هي والعة ولا لأ.

والفندق ده بيبوظ بطريقتين. يا إما تحط حاجة في مكان أوسع من اللازم: تخلي مفتاح الأباجورة في الاستقبال، فكل نزيل يقدر يطفيها. يا إما في مكان أضيق: تحط الأمن جوه أوضة واحدة، فلما النزيل يمشي والأوضة تتقفل، الفندق كله يبقى من غير أمن. وفي غلطة تالتة: إن موظف الأوضة 305 يدخل يرتّب الأوضة 306 بنفسه بدل ما يكلّم الاستقبال.

</Analogy>

الـ Cubits في app حقيقي بالظبط كده. في الوحدة دي اتعلمت تكتب كل نوع Cubit لوحده. الدرس ده عن الصورة الكاملة في Readly: كل Cubit <b>مكانه فين</b> في الطبقات، و<b>اسمه وملفه</b> إيه، و<b>بيعيش فين وقد إيه</b> (الـ app كله، ولا طول ما المستخدم داخل، ولا صفحة واحدة، ولا widget واحد)، و<b>بيتسجّل إزاي</b> في get_it، و<b>بيكلّم الـ Cubits التانية إزاي</b> من غير ما يمسكهم. وفي الآخر كتالوج بأشهر الأخطاء وقايمة تراجع بيها أي Cubit في أي PR.

كل قرار من دول ليه سؤال واحد بيحسمه:

| القرار | السؤال اللي بيحسمه |
| --- | --- |
| الـ Cubit يعرف مين؟ | لو شلت Flutter كله، الـ Cubit ده يتعمله compile ويتختبر بـ `dart test`؟ |
| يتحط فين في الشجرة؟ | مين أوطى widget فوق <b>كل</b> اللي محتاجينه؟ |
| يعيش قد إيه؟ | لو الـ scope ده اتشال، الـ state دي لسه ليها معنى؟ |
| يتسجّل إزاي؟ | في حد <b>بره</b> شجرة الـ widgets محتاج نفس النسخة؟ |
| يكلّم Cubit تاني إزاي؟ | مين مصدر الحقيقة للبيانات دي؟ |

</Level>

<Level n="2" title="الكود الأساسي">

### الـ Cubit مكانه فين في Clean Architecture

الـ Cubit في الـ presentation layer، والسهم بتاعه رايح لجوه بس، زي ما اتفقنا من درس الطبقات في الوحدة 1. هو بيعرف الـ domain (use cases وcontracts وentities وFailure)، ومايعرفش أي حاجة عن الـ data ولا عن Flutter:

| الـ Cubit يعتمد على | مسموح؟ | ليه |
| --- | --- | --- |
| use case (`GetLibrary`، `AddBookToLibrary`) | أيوه | ده الطبيعي لما في logic |
| repository contract (`LibraryRepository`) | أيوه | لما مفيش logic، زي `AuthCubit` و`SyncStatusCubit` (قرار الـ pass-through من درس الـ Domain) |
| contract بتاع feature تانية من الـ barrel (`BookLookup`) | أيوه | ده الـ public API بتاعها |
| `Result`، `Failure`، الـ entities | أيوه | لغة الـ domain |
| `dart:async` (`Stream`، `Timer`، `StreamSubscription`) | أيوه | Dart صافي |
| `LibraryRepositoryImpl`، DTO، dio، drift، shared_preferences | لأ | تفاصيل الـ data، ولو اتغيرت الشاشة تقع |
| `BuildContext`، `Navigator`، `GoRouter`، `ScaffoldMessenger` | لأ | الـ Cubit بيوصف «إيه اللي حصل»، والـ UI تقرر «نعمل إيه» |
| `package:flutter` (`Color`، `ThemeMode`، `TextEditingController`) | لأ | الـ Cubit مابقاش Dart صافي، و`bloc_lint` بيمسكه |
| `getIt` | لأ | الـ dependencies تتخبى (درس الـ DI) |
| Cubit تاني | لأ | الـ lifecycle بتاعهم يتربط ببعض (Level 3) |

ويبان ده في أول سطور الملف:

<CodeBlock label="features/library/presentation/library_cubit.dart">

```dart
import 'dart:async';

import 'package:bloc/bloc.dart'; // not flutter_bloc: the Cubit needs no Flutter
import 'package:core/core.dart'; // Result, Failure

import '../domain/book.dart';
import '../domain/get_library.dart';
import '../domain/library_repository.dart'; // the contract, never the Impl
import 'library_state.dart';

class LibraryCubit extends Cubit<LibraryState> {
  LibraryCubit(this._getLibrary, this._repository) : super(const LibraryLoading());

  final GetLibrary _getLibrary;
  final LibraryRepository _repository;
  StreamSubscription<List<Book>>? _sub;

  // load(), refresh(), watch() as in the Cubit lesson of unit 5
}
```

</CodeBlock>

- <b>الـ `package:bloc` مش `flutter_bloc`:</b> الـ `Cubit` نفسه جاي من `bloc`، و`flutter_bloc` بيعمل له re-export وبيجيب معاه Flutter. الـ Cubit مش محتاج `BlocProvider` ولا `BlocBuilder`، فبيعمل import للي محتاجه بس. وبما إنك بتعمل import لـ `bloc` مباشرة، لازم يبقى مكتوب في `dependencies` في الـ pubspec، وإلا `depend_on_referenced_packages` من درس «حراسة المعمارية» هيعلّم عليه.
- <b>الاختبار السريع:</b> لو الملف ده اتنقل لـ package Dart صافية من غير Flutter، يتعمله compile؟ لو أيوه، الـ Cubit في مكانه الصح. وده نفس اللي عملناه في درس «أول Cubit سطر بسطر» لما شغّلنا Cubit بـ `dart run`.

### الملفات والأسامي

<CodeBlock label="feature واحدة من جوه">

```text

      └─ sync_badge.dart
```

</CodeBlock>

| الحاجة | القاعدة | مثال |
| --- | --- | --- |
| ملف الـ Cubit | اسم الـ class بالـ snake_case، وفيه الـ Cubit لوحده | `LibraryCubit` في `library_cubit.dart` |
| ملف الـ state | جنبه بنفس البادئة | `library_state.dart` |

| الـ Page | فيها الـ `BlocProvider` بس | `LibraryPage` |
| الـ View | فيها الـ Builders والـ Listeners، وبتاخد الـ Cubit من الـ context | `LibraryView` |

- <b>الـ Page والـ View:</b> الـ Page هي المكان الوحيد اللي بيتعمل فيه الـ Cubit (بالـ `getIt`، زي ما قلنا في درس الـ DI: الـ composition root والـ routes بس). الـ View مابتعرفش الـ Cubit جه منين، فالـ widget test بيحط فوقها `MockLibraryCubit` بـ `BlocProvider.value` من غير get_it خالص، زي [درس الـ widget tests](/course/testing/widget-tests/).
- <b>الأسامي مش ذوق بس:</b> الـ rule `prefer_file_naming_conventions` في `bloc_lint` بتعلّم على أي Cubit ملفه مش على اسمه. وده بيفرق لما تدوّر: `library_cubit` في الـ search بيوصلك على طول.

### الـ state في ملف لوحده ولا `part`؟

الاتنين شغالين مع `sealed`، لأن الـ `part` جزء من نفس الـ library، والـ sealed محتاج كل الـ subclasses في نفس الـ library:

<CodeBlock label="اختيار 1: ملف لوحده (الأبسط)">

```dart
// library_state.dart: the sealed class and all its subclasses live here
sealed class LibraryState {
  const LibraryState();
}
final class LibraryLoading extends LibraryState { /* ... */ }

// library_cubit.dart
import 'library_state.dart';
```

</CodeBlock>

<CodeBlock label="اختيار 2: part (اللي الـ VS Code extension بتاع bloc بيولّده)">

```dart
// library_cubit.dart
import 'package:bloc/bloc.dart';
part 'library_state.dart';

// library_state.dart
part of 'library_cubit.dart';

sealed class LibraryState {
  const LibraryState();
}
```

</CodeBlock>

| | ملف لوحده | `part` |
| --- | --- | --- |
| الـ widget أو التست محتاج الـ states بس | import للـ state بس | لازم import للـ Cubit كله |
| الـ imports | كل ملف بيعمل import للي محتاجه | الـ imports كلها في ملف الـ Cubit |
| مع freezed | `library_state.dart` فيه `part 'library_state.freezed.dart'` عادي | الـ part جوه part مش مسموح، فالـ freezed part بيروح لملف الـ Cubit |
| private helpers مشتركة بين الـ Cubit والـ state | مش ممكن | ممكن (نفس الـ library) |

Readly ماشية بالملف اللي لوحده. المهم إن الفريق يختار واحد ويكتبه، مش كل feature بشكل.

### خريطة الأماكن في Readly

دلوقتي أهم قرار: كل Cubit بيتحط فين. القاعدة: <b>في أوطى مكان فوق كل الـ widgets اللي محتاجاه</b>. أوطى من كده، في حد مش هيلاقيه (`ProviderNotFoundException`). وأعلى من كده، هيعيش أكتر من اللازم ويشيل state قديمة.

<Diagram name="d-sm-scope-map">

الـ scopes الأربعة في Readly. الـ AuthCubit والـ SettingsCubit والـ SyncStatusCubit فوق الـ MaterialApp. الـ ProfileCubit في الـ shell فبيموت مع الـ logout. كل تاب ليه الـ Cubit بتاعه وبيفضل عايش وهو مستخبي، وكل صفحة جوه التاب ليها Cubits بتتقفل لما ترجع منها. والـ BookTileCubit متقطّع لأنه بيتعمل بس لو الـ tile ليه سلوك لوحده يستاهل.

</Diagram>

| الـ scope | بيتحط فين | Cubits في Readly | بيموت إمتى |
| --- | --- | --- | --- |
| الـ app | فوق `MaterialApp.router` في `ReadlyApp` | `AuthCubit`، `SettingsCubit`، `SyncStatusCubit` | مع الـ app |
| الـ shell | في الـ `builder` بتاع `StatefulShellRoute` | `ProfileCubit` (اسم المستخدم وصورته في كل التابات) | مع الـ logout، لأن الـ redirect بيشيل الـ shell كله |
| الـ branch | الـ route اللي في أول كل تاب | `LibraryCubit`، `CatalogCubit` | مع الـ shell، مش لما تروح تاب تاني (الـ IndexedStack) |
| الـ route | الـ route اللي اتعمله push | `BookDetailsCubit`، `NotesCubit`، `AddBookCubit`، `LoginCubit` | لما ترجع من الصفحة |
| الـ widget | جوه الـ `itemBuilder` | `BookTileCubit` لو استاهل (درس «أنواع الـ Cubit (2)») | لما الـ tile يخرج من الشجرة |

وبالكود، من بره لجوه:

<CodeBlock label="الـ app: ReadlyApp">

```dart
class ReadlyApp extends StatelessWidget {
  const ReadlyApp({super.key});

  @override
  Widget build(BuildContext context) => MultiBlocProvider(
        providers: [
          // get_it owns these two (the router and resetOnLogout use the same instance)
          BlocProvider.value(value: getIt<AuthCubit>()),
          BlocProvider.value(value: getIt<SyncStatusCubit>()),
          // created and closed here, once for the whole app
          BlocProvider(create: (_) => getIt<SettingsCubit>()),
        ],
        child: BlocListener<AuthCubit, AuthState>(
          listenWhen: (prev, curr) => prev is Authenticated && curr is! Authenticated,
          listener: (context, _) => context.read<SettingsCubit>().reset(),
          child: BlocBuilder<SettingsCubit, SettingsState>(
            builder: (context, settings) => MaterialApp.router(
              theme: AppTheme.light,
              darkTheme: AppTheme.dark,
              themeMode: settings.themeMode,
              locale: settings.locale,
              localizationsDelegates: AppLocalizations.localizationsDelegates,
              supportedLocales: AppLocalizations.supportedLocales,
              routerConfig: router,
            ),
          ),
        ),
      );
}
```

</CodeBlock>

ده نفس الـ `ReadlyApp` بتاع [درس الإعدادات](/course/di-scale/settings/) بتعديل واحد: الـ `AuthCubit` بقى `BlocProvider.value`، زي الـ `SyncStatusCubit` في [درس Offline-first](/course/offline/offline/). ليه ده بيفرق هتشوفه في Level 3.

### التسجيل في get_it: factory ولا lazySingleton

في [درس الـ DI](/course/di-scale/di/) القاعدة كانت: الـ Cubit `registerFactory`، والاستثناء الـ AuthCubit. هنا بنكمّلها لكل الحالات:

| الحالة | التسجيل | الـ provider | مين بيقفله |
| --- | --- | --- | --- |
| Cubit شاشة أو تاب أو widget | `registerFactory` | `BlocProvider(create: ...)` | الـ BlocProvider لما يتشال |
| محتاج قيمة من الـ route (id) | `registerFactoryParam` | `BlocProvider(create: ...)` | الـ BlocProvider |
| حد <b>بره</b> الشجرة محتاج نفس النسخة (الـ router، listener في الـ DI) | `registerLazySingleton` + `dispose` | `BlocProvider.value` | get_it (`reset` أو `resetLazySingleton`) |
| واحد للـ app بس محدش بره الشجرة محتاجه (`SettingsCubit`) | `registerFactory` | `BlocProvider(create: ...)` فوق الـ app | الـ BlocProvider، مع الـ app |

<CodeBlock label="كل feature بتسجّل الـ Cubits بتاعتها">

```dart
// packages/feature_library/lib/src/library_di.dart
void registerLibrary(GetIt getIt) {
  getIt
    // ... data sources, repository, use cases (architecture guards lesson)
    // screen Cubits: a new instance per BlocProvider, closed with it
    ..registerFactory(() => LibraryCubit(getIt(), getIt()))
    ..registerFactory(() => BookDetailsCubit(getIt()))
    ..registerFactory(() => AddBookCubit(getIt()))
    // the router and the app shell read the same instance
    ..registerLazySingleton(
      () => SyncStatusCubit(getIt()),
      dispose: (cubit) => cubit.close(), // runs on reset / resetLazySingleton
    );
}

// packages/feature_notes/lib/src/notes_di.dart
void registerNotes(GetIt getIt) {
  getIt.registerFactoryParam<NotesCubit, BookId, void>(
    (bookId, _) => NotesCubit(getIt(), bookId),
  );
}
```

</CodeBlock>

- <b>الـ registerFactoryParam:</b> بياخد لحد 2 parameters، والتاني `void` لو مش محتاجه. وبتطلبه بـ `getIt<NotesCubit>(param1: bookId)`. ولو بتستخدم injectable، نفس الحكاية بـ `@factoryParam` على الـ parameter في الـ constructor.
- <b>الـ dispose في الـ lazySingleton:</b> لما الـ logout يعمل `resetLazySingleton` (درس الـ Session)، get_it بينادي `close()` على النسخة القديمة قبل ما يرميها، فالـ subscription بتاعها مايفضلش شغال في الخلفية.
- <b>الـ singleton بيتسأل عنه سؤال واحد:</b> «مين بره الـ widgets محتاجه؟». الـ `AuthCubit` محتاجه الـ router (`refreshListenable`) والـ `resetOnLogout`. لو الإجابة «ولا حد»، يبقى factory حتى لو بيتعمل مرة واحدة، زي الـ `SettingsCubit`.

</Level>

<Level n="3" title="المشاكل الحقيقية وحلولها">

### الـ AuthCubit بقى `.value`: مين المالك

الغلطتين بتوع الـ ownership (`create` لـ singleton فبيتقفل مع أول صفحة تتشال والـ app يضرب بعدها بـ `Cannot emit new states after calling close`، و`.value` لـ factory فمحدش بيقفله ويفضل leak) متشرحين بالتفصيل في درس «flutter_bloc بالتفصيل». القاعدة واحدة: <b>اللي عمل الـ Cubit هو اللي يقفله</b>، وفي Readly بتترجم للجدول ده:

| التسجيل | الـ provider الصح | لو عكستهم |
| --- | --- | --- |
| `registerFactory` | `BlocProvider(create: ...)` | `.value`: leak، ومحدش بيقفله |
| `registerLazySingleton` | `BlocProvider.value` | `create`: الـ singleton بيتقفل مع أول صفحة تتشال |

وعشان كده غيرنا الـ `AuthCubit` لـ `.value` في `ReadlyApp`. في درس الإعدادات كان `BlocProvider(create: ...)`، وده شغال عمليًا لأن `ReadlyApp` عايش طول عمر الـ app، فالـ provider عمره ما بيتشال. بس الكود بيقول حاجة غلط: إن الـ provider هو المالك، والحقيقة إن get_it هو المالك (الـ router والـ `resetOnLogout` بيستخدموا نفس النسخة). وأول integration test يعمل `pumpWidget(ReadlyApp(...))` مرتين في نفس الـ process، الـ BlocProvider بتاع التست الأول بيقفل الـ AuthCubit اللي get_it لسه شايله، والتست التاني بيضرب. الـ `.value` بيقول الحقيقة، ومش بيغيّر أي سلوك تاني.

### تاب الكتالوج محتاج يعرف «الكتاب ده عندي؟»

في الكتالوج، عايزين علامة على كل كتاب موجود في مكتبة المستخدم. أسرع حل جه في دماغ حد: ننقل الـ `LibraryCubit` لفوق الـ shell، والكتالوج يعمل `context.watch<LibraryCubit>()` ويدوّر في `books`.

الحل ده بيبوظ 3 حاجات مرة واحدة:

- <b>الـ lifetime:</b> الـ `LibraryCubit` بقى عايش لكل الـ shell، وبيحمّل المكتبة حتى لو المستخدم عمره مافتح تابها.
- <b>الـ state مش مصممة للسؤال ده:</b> لو `LibraryCubit` في `LibraryLoading` أو `LibraryError`، الكتالوج هيقول «مش عندك» لكل الكتب. والـ refresh في تاب المكتبة بيعيد بناء كل tiles الكتالوج.
- <b>الحدود:</b> الـ catalog بقت بتعمل import للـ presentation بتاع الـ library. يعني لو حد غيّر شكل `LibraryState`، الكتالوج يقع.

الكتالوج مش محتاج «الـ state بتاعة شاشة المكتبة». محتاج <b>معلومة</b> من الـ library. والمعلومة مكانها الـ domain contract اللي الـ library بتصدّره في الـ barrel، زي `BookLookup` في درس SOLID:

<CodeBlock label="الـ contract بيكبر بـ stream">

```dart
// feature_library/lib/src/domain/book_lookup.dart (exported by the barrel)
abstract interface class BookLookup {
  Future<Result<Book>> findById(BookId id);
  Stream<Set<BookId>> watchLibraryIds(); // new: what's in the library, live
}

// feature_catalog/lib/src/presentation/catalog_cubit.dart
class CatalogCubit extends Cubit<CatalogState> {
  CatalogCubit(this._searchBooks, this._lookup) : super(const CatalogLoading());

  final SearchBooks _searchBooks;
  final BookLookup _lookup; // the library's public contract, not LibraryCubit
  StreamSubscription<Set<BookId>>? _ownedSub;
  Set<BookId> _owned = const {};

  Future<void> loadFirst(String query) async {
    _ownedSub ??= _lookup.watchLibraryIds().listen((ids) {
      _owned = ids; // the next CatalogLoaded starts with it too
      if (state case final CatalogLoaded loaded) emit(loaded.copyWith(owned: ids));
    });
    // ... the pagination lesson's code, emitting CatalogLoaded(..., owned: _owned)
  }

  @override
  Future<void> close() async {
    await _ownedSub?.cancel();
    return super.close();
  }
}
```

</CodeBlock>

الـ AddBookCubit مابيقولش للـ LibraryCubit «ضيف الكتاب». بيضيفه في الـ repository، والـ drift بيطلّع الليستة الجديدة على `watchLibrary()`، فالمكتبة بتتحدّث لوحدها. ونفس الـ stream بيوصل للكتالوج عن طريق `BookLookup`.

</Diagram>

دي نفس علامة «في مكتبتك» اللي في درس «أنواع الـ Cubit (2)» (ونفس قاعدة درس «Cubit متقدم»: الاتنين يسمعوا على stream من نفس المصدر)، بس عبر features: المصدر بقى contract من الـ barrel مش `LibraryRepository` نفسه. والـ `owned` يتحط في `CatalogLoaded` بس، لأن قبل الـ loaded مفيش كتب تتعلّم أصلًا. والـ `_owned` بيفتكر آخر قيمة، عشان لو الـ ids وصلت والصفحة الأولى لسه بتحمّل، أول `CatalogLoaded` يطلع بيها بدل ما يستنى تغيير جاي في المكتبة. والاشتراك هنا بيبدأ مع أول بحث (`??=` عشان يحصل مرة واحدة)، بس الـ constructor كمان مقبول زي درس «أنواع الـ Cubit (2)»: ده stream محلي من غير parameters، مش request. وبعدين الـ tile بيسأل بـ `context.select` عن الكتاب بتاعه بس، زي علامة السحابة في درس Offline-first.

ودي الطرق الأربعة لتواصل الـ Cubits، بالترتيب:

| الطريقة | امتى | مثال في Readly |
| --- | --- | --- |
| stream من نفس الـ repository أو contract | الاتنين محتاجين نفس البيانات | `LibraryCubit` و`CatalogCubit` على الـ books |
| `BlocListener` في widget فوق الاتنين | حدث في واحد لازم يحرّك التاني، والاتنين في الـ UI | الـ logout بيعمل `reset()` للـ `SettingsCubit` (درس الإعدادات) |
| listener في الـ composition root | حاجة مش widget محتاجة تعرف | `resetOnLogout` بيمسح الـ caches (درس الـ Session) |
| Cubit بياخد Cubit في الـ constructor | أبدًا | |

وليه الأخيرة «أبدًا»؟ ده في كتالوج الـ anti-patterns تحت.

### `bloc lint` علّم على الـ SettingsCubit

دخّلت `bloc_lint` (الجزء الجاي)، وأول تشغيل علّم على `settings_cubit.dart` بـ `avoid_flutter_imports`. الـ `SettingsState` في درس الإعدادات بيشيل `ThemeMode`، وده جاي من `package:flutter/material.dart`. الكود شغال، والتست شغال بـ `flutter test`. فهل نسيب الـ rule؟

الـ rule مش عشان `ThemeMode` نفسه. هي عشان أول import لـ Flutter بيفتح الباب لـ `BuildContext` و`Color` و`TextEditingController` في نفس الملف، ومحدش هيلاحظ الفرق. والحل هنا 10 سطور: enum بتاعك، والـ UI تحوّله:

<CodeBlock label="ThemePreference بدل ThemeMode">

```dart
// settings/data/settings_store.dart, next to the store contract: pure Dart
// (settings has no domain folder, see the Settings lesson)
enum ThemePreference { system, light, dark }

// settings/presentation/theme_preference_ui.dart: the only Flutter-aware part
extension ThemePreferenceUi on ThemePreference {
  ThemeMode get themeMode => switch (this) {
        ThemePreference.system => ThemeMode.system,
        ThemePreference.light => ThemeMode.light,
        ThemePreference.dark => ThemeMode.dark,
      };
}

// ReadlyApp: SettingsState.theme is a ThemePreference now
themeMode: settings.theme.themeMode,
```

</CodeBlock>

- <b>الـ SettingsStore بيحفظ الـ enum:</b> الـ contract بتاعه بقى `ThemePreference get theme` و`saveTheme(ThemePreference)` بدل `ThemeMode`، والـ implementation بيحفظه بـ `name` زي ما كان بيحفظ `ThemeMode`. لو القيم المحفوظة عند المستخدمين هي `'system'` و`'light'` و`'dark'`، نفس الأسامي، فمفيش migration.
- <b>والـ Locale؟</b> `Locale` جاي من `dart:ui` مش من `package:flutter`، بس هو برضه نوع بتاع الـ UI. لو عايز الـ SettingsCubit Dart صافي 100%، احفظ `languageCode` كـ `String`، والـ UI تعمل `Locale(code)`. ده قرار، مش لازم تعمله في نفس الـ PR.
- <b>مفيش استثناءات:</b> rule فيها استثناء واحد بتبقى rule فيها عشرة بعد سنة. لو الحل رخيص زي هنا، صلّح الكود مش الـ rule.

والحاجات اللي `bloc_lint` مايعرفهاش، زي «الـ Cubit مايعملش import لـ data أو لـ Cubit تاني»، بتتزوّد على الـ architecture test بتاع [درس «حراسة المعمارية»](/course/quality/architecture-guards/)، بنفس الـ helpers اللي هناك (`allPackages` و`_directive`):

<CodeBlock label="tools/architecture/test/architecture_test.dart (test جديد)">

```dart
final _cubitFile = RegExp(r'_(cubit|bloc)\.dart$');
const forbiddenInCubit = ['package:dio/', 'package:drift/', 'package:go_router/', '/data/'];

test('cubits import no infrastructure and no other cubit', () {
  final violations = <String>[];
  for (final pkg in allPackages) {
    final lib = Directory('${pkg.path}/lib');
    if (!lib.existsSync()) continue;
    for (final file in lib.listSync(recursive: true).whereType<File>()) {
      if (!_cubitFile.hasMatch(file.path)) continue;
      final src = file.readAsStringSync();
      if (src.contains('getIt')) violations.add('${file.path} -> getIt');
      for (final m in _directive.allMatches(src)) {
        final uri = m[1]!;
        if (forbiddenInCubit.any(uri.contains) || _cubitFile.hasMatch(uri)) {
          violations.add('${file.path} -> $uri');
        }
      }
    }
  }
  expect(violations, isEmpty);
});
```

</CodeBlock>

- <b>الـ `_cubitFile.hasMatch(uri)`:</b> ملف Cubit بيعمل import لملف تاني اسمه `_cubit.dart` يبقى Cubit بيعتمد على Cubit. والـ state في `library_state.dart` مش بتتمسك لأن اسمها مش `_cubit`.
- <b>الـ `getIt` كنص:</b> نفس الـ rule النصية اللي اقترحناها في درس الأخطاء الشائعة. مش محتاج تعرف الـ import جاي منين.
- <b>الـ test ده بيعتمد على الأسامي:</b> لو حد سمّى Cubit `library_controller.dart`، التست مش هيشوفه. وده بالظبط شغل `prefer_file_naming_conventions`: الـ lint بيضمن الاسم، والتست بيعتمد عليه.

### الـ tile عرض حالة كتاب تاني

`BookTileCubit` لكل كتاب في المكتبة من غير `key`: المستخدم علّم كتاب «خلصته»، الليست اترتبت، والـ spinner ظهر على كتاب تاني. Flutter بيربط الـ elements بالمكان مش بالكتاب، فالـ BlocProvider اللي في نفس المكان فضل بالـ Cubit القديم. الحل (`key: ValueKey(book.id)` على الـ BlocProvider) والسؤال اللي قبله («الـ tile محتاج Cubit أصلًا، ولا `Set<BookId> updating` في `LibraryLoaded` كفاية؟») متشرحين بالكود في درس «أنواع الـ Cubit (2)». اللي يخص الدرس ده: الـ Cubit لكل item هو أوطى scope في الخريطة، ومكانه في الـ review checklist تحت.

### الأداء: الـ scope بيحدد حجم الـ rebuild

مكان الـ `BlocBuilder` في الشجرة هو اللي بيحدد كام widget بيتعاد بناؤه مع كل state. شوية قواعد بتفرق في Readly:

- <b>الـ Builder أوطى ما يمكن:</b> `BlocBuilder<SyncStatusCubit, SyncStatus>` فوق الـ `Scaffold` بتاع المكتبة معناه إن كل الصفحة بتتبني مع كل عملية في الـ sync queue. حطه حوالين الـ badge بس.
- <b>الـ select للـ items:</b> `context.select((SyncStatusCubit c) => c.state.unsynced.contains(book.id))` جوه كل tile، زي درس Offline-first. الـ tile بيتبني بس لما الإجابة بتاعته هو تتغير.
- <b>الـ buildWhen للحقول اللي ملهاش دعوة:</b> زرار الـ refresh مايتبنيش لما `refreshFailure` يتغير. أو `BlocSelector` بيختار `isRefreshing` بس.
- <b>القيم اللي بتتغير بسرعة مش في الـ state:</b> مكان الـ scroll، أو progress تحميل بيتغير 60 مرة في الثانية. ده يا إما يفضل في الـ widget، يا إما يتعمله throttle قبل الـ emit.
- <b>الـ getters التقيلة:</b> الـ default إن القيم المشتقة getters، زي درس «تصميم الـ State». بس getter بيعمل sort لـ 2000 كتاب وبيتنادى في كل build تمنه كبير. احسبه مرة في الـ Cubit وخزّنه في الـ state، أو `late final` جوه الـ state (والـ constructor ساعتها مايبقاش `const`).
- <b>التابات العايشة ليها تمن:</b> الـ IndexedStack بيخلي 3 تابات بالـ Cubits والليستات بتاعتهم في الميموري. ده مقبول لـ 3 تابات. لـ 8 تابات فيها صور كتير، فكّر.

وماتخمّنش: افتح DevTools وفعّل عدّاد الـ rebuilds، واعمل الحركة اللي شاكك فيها، وشوف مين اتبنى كام مرة. التفاصيل في درس «flutter_bloc بالتفصيل».

</Level>

<Level n="4" title="قرارات الـ senior">

- <b>كل Cubit جديد بيتسأل 3 أسئلة في الـ review:</b> بيعيش فين؟ مين بيقفله؟ مين مصدر الحقيقة للبيانات اللي فيه؟ لو صاحب الـ PR مش عارف يجاوب، المشكلة في التصميم مش في الكود.
- <b>الـ scope الأوسع بيبان أسهل، وهو الأغلى:</b> «حطه فوق الـ app وخلاص، كده كل الشاشات توصله» بيحل `ProviderNotFoundException` النهارده، وبيعمل bugs بكرة: state المستخدم القديم بعد الـ logout، وتحميل بيانات لشاشات محدش فتحها، وCubits بتسمع على الـ DB طول عمر الـ app. الـ app scope للحاجات اللي الـ app كله محتاجها فعلًا: الـ session والإعدادات وحالة المزامنة.
- <b>الـ shell هو الـ «user scope» ببلاش:</b> الـ redirect بيشيل الـ shell مع الـ logout، فأي Cubit متحط فيه بيتقفل لوحده. ده أرخص من lazySingletons وقايمة `resetLazySingleton` لازم تفتكر تزوّد عليها (درس الـ Session اقترح `pushNewScope` في get_it لنفس السبب).
- <b>Page/View مش رفاهية:</b> هي اللي بتخلي كل widget test يحط `MockCubit` من غير get_it، وبتخلي مكان الـ `BlocProvider` واحد ومعروف. ولو الشاشة محتاجة Cubitين أو تلاتة، الـ Page فيها `MultiBlocProvider`، والـ View مش بتعرف.
- <b>الاتساق أهم من الاختيار:</b> `part` ولا ملف لوحده، Cubit ولا Bloc، `context.read` ولا `BlocProvider.of`. كل واحد فيهم مقبول. اللي مش مقبول إن كل feature تبقى بشكل. اكتب القرار في ADR قصير، وخلّي الـ lint يفرضه لو في rule ليه.
- <b>ماتبنيش base Cubit عشان الـ boilerplate:</b> `AsyncCubit<T>` بيوفّر 10 سطور في كل Cubit، وبعد شهرين كل Cubit محتاج حالة مختلفة شوية والـ base مليان flags. ده اتشرح في درس «أنواع الـ Cubit (2)». لو في سلوك بيتكرر فعلًا (زي الـ `isClosed` بعد كل await)، الـ mixin الصغير من درس «Cubit متقدم» أنضف.
- <b>اعرف امتى تكسر القاعدة:</b> الـ `AuthCubit` والـ `SyncStatusCubit` بيسمعوا على stream في الـ constructor، وده مقبول لأن شغلهم الوحيد إنهم يعكسوا stream طول عمر الـ app، ومفيش شاشة هتنادي `watch()`. الـ Cubit بتاع الشاشة لأ: الشاشة هي اللي بتقرر امتى يحمّل (كتالوج الـ anti-patterns تحت).
- <b>التست جزء من التصميم:</b> لو الـ Cubit صعب يتختبر (محتاج get_it، أو BuildContext، أو بيعمل request وهو بيتعمل)، ده عرض لمشكلة في التصميم من اللي في كتالوج الـ anti-patterns تحت. التستات نفسها في [درس «تست الـ Cubit»](/course/testing/cubit-tests/) في الوحدة 8.

| الـ anti-pattern | العَرَض في Readly | البديل | بيتمسك بـ |
| --- | --- | --- | --- |
| god Cubit | `LibraryCubit` فيه الليستة والبحث والتحديد ووضع العرض والملاحظات، وأي تعديل بيكسر حاجة تانية | Cubit لكل جزء مستقل في الشاشة | الـ review (ملف فوق 300 سطر، state فيها 12 حقل) |

| state بتتعدّل في مكانها | `state.books.add(book); emit(state);` والشاشة مابتتغيرش | list جديدة أو `copyWith` | الـ review، و`List.unmodifiable` بيرمي وقت التشغيل |
| Cubit ماسك Cubit | `HomeCubit(this._library)` بيسمع على `_library.stream` | stream من الـ repository، أو BlocListener | الـ architecture test فوق |
| Cubit لكل widget من غير سبب | `ExpandedCubit` لنص «اقرا أكتر» | `setState` أو `ValueNotifier` للـ state المؤقتة | الـ review |
| lifetime غلط | singleton بـ `create`، أو factory بـ `.value` | الجدول في Level 3 | الـ review، وcrash أو leak |
| get_it جوه الـ Cubit | `final _repo = getIt<...>()` | constructor injection | الـ architecture test فوق (درس الأخطاء الشائعة) |

والسبعة اللي بيظهروا أكتر في الـ PRs، بالكود:

```dart
class AddBookCubit extends Cubit<AddBookState> {
```

```dart
    emit(const AddBookSaving());
    final result = await _addBook(book);
    if (isClosed) return;
    emit(switch (result) {
      Success() => const AddBookSaved(),
      Err(:final failure) => AddBookError(failure),

// UI: fire and forget, the BlocListener reacts
```

- <b>مصدرين للحقيقة:</b> في الـ «قبل» الـ `bool` اللي راجع بيقول حاجة، والـ state بتقول حاجة تانية (أو ولا حاجة). والـ `isSaving` ماحدش بيسمع عليه، فالزرار مش هيتقفل وهو بيحفظ.
- <b>الـ Failure راحت فين؟</b> الـ `false` مابيقولش النت فاصل ولا السيرفر رفض. في الـ «بعد» الـ `AddBookError(failure)` بتوصل للـ UI كاملة.

<BeforeAfter>

<Side label="قبل" kind="before">

```dart
class HomeCubit extends Cubit<HomeStats> {

    _sub = _library.stream.listen((s) {
      if (s is LibraryLoaded) emit(HomeStats.from(s.books));
```

</Side>

<Side label="بعد" kind="after">

```dart
class HomeCubit extends Cubit<HomeStats> {
  HomeCubit(LibraryRepository repository) : super(const HomeStats()) {
    _sub = repository.watchLibrary().listen((books) => emit(HomeStats.from(books)));
  }
  late final StreamSubscription<List<Book>> _sub;

  @override
  Future<void> close() async {
    await _sub.cancel();
    return super.close();
  }
}
```

</Side>

</BeforeAfter>

- <b>أنهي نسخة؟</b> الـ `LibraryCubit` factory. لو get_it عمل واحد جديد عشان الـ `HomeCubit`، فده Cubit تاني غير اللي في التاب، محدش نادى `load()` بتاعه، فالإحصائيات فاضية للأبد. ولو اتبعت من الـ context، يبقى الإحصائيات مربوطة بعمر تاب المكتبة.
- <b>الـ stream اللي بيقول الحقيقة:</b> الـ `LibraryState` فيها loading وerror وrefreshing، وكل ده مالوش دعوة بالإحصائيات. الـ `watchLibrary()` بيطلّع الكتب بس، ومن الـ DB مباشرة.
- <b>والـ close:</b> أي Cubit بيسمع على stream بيلغي الاشتراك في `close()`، زي درس الـ Cubit في الوحدة 5.

<LessonPart title="قايمة مراجعة أي Cubit في PR">

عدّي عليها على أي Cubit جديد أو اتعدّل قبل ما تطلب review. اللي مكتوب قبله «أداة» بيتمسك لوحده (`bloc lint` أو الـ architecture test أو الـ compiler)، والباقي محتاج عينك.

<CheatGrid>

<CheatCard title="الطبقة والـ imports">

- <b>أداة:</b> مفيش import لـ Flutter، والـ Cubit بيعمل import لـ `package:bloc` مش `flutter_bloc`.
- <b>أداة:</b> مفيش dio ولا drift ولا `data/` ولا `getIt`.
- <b>أداة:</b> مفيش Cubit تاني في الـ imports.
- بيعتمد على use cases أو contracts بس، وكلهم جايين من الـ constructor.

</CheatCard>

<CheatCard title="الـ state">

- immutable: كل emit object جديد، والـ lists مابتتعدّلش في مكانها.
- بتتقارن بالقيمة (Equatable أو freezed أو `==` مكتوب).
- الـ Failure حقل جنب البيانات لما في بيانات على الشاشة.
- مفيش `Color` ولا نصوص متترجمة ولا controllers.
- <b>أداة:</b> الـ switch في الـ UI exhaustive من غير `_`.

</CheatCard>

<CheatCard title="الـ API بتاع الـ Cubit">

- <b>أداة:</b> الـ methods الـ public بترجّع `void` أو `Future<void>`.
- <b>أداة:</b> مفيش fields public.
- <b>أداة:</b> اسم الملف على اسم الـ class.
- أسامي الـ methods نية المستخدم: `load`، `refresh`، `queryChanged`.
- مفيش request ولا emit في الـ constructor (إلا Cubits الـ app اللي بتعكس stream).

</CheatCard>

<CheatCard title="الـ async والـ lifecycle">

- `isClosed` بعد كل `await` قبل الـ emit.
- الضغط المتكرر والنتايج القديمة متحاميين (flag أو request id أو transformer).
- كل `StreamSubscription` و`Timer` بيتلغوا في `close()`.
- الـ errors اللي مش جزء من الـ state بتتبلّغ بـ `addError`.

</CheatCard>

<CheatCard title="المكان والـ DI">

- متحط في أوطى مكان فوق كل اللي محتاجينه.
- factory مع `create`، وsingleton مع `.value`. مفيش عكس.
- الـ singleton ليه سبب: حد بره الشجرة محتاج نفس النسخة، وليه `dispose`.
- الـ parameters من الـ route بتيجي في الـ constructor (`registerFactoryParam`)، مش setter.
- Cubit لكل item بس لو الـ item ليه دورة لوحده، ومعاه `ValueKey`.

</CheatCard>

<CheatCard title="الـ UI والتواصل">

- الـ navigation والـ snackbar والـ dialog في BlocListener.
- الـ BlocBuilder أوطى ما يمكن، والـ items بـ `context.select` أو `BlocSelector`.
- مفيش فلترة ولا ترتيب ولا validation جوه `build`.
- الـ Cubits اللي محتاجة نفس البيانات بتسمع على الـ repository، مش على بعض.

</CheatCard>

<CheatCard title="التست">

- blocTest لكل method × كل نتيجة للـ use case.
- تست للسباق (ضغطتين، نتيجة قديمة) وللـ cleanup بعد `close()`.
- widget test للـ View بـ `MockCubit`، من غير get_it.
- التفاصيل في الوحدة 8: «تست الـ Cubit» و«الـ widget tests».

</CheatCard>

</CheatGrid>
