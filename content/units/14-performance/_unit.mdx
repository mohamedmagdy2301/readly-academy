---
title: "الـ Performance: تقيس قبل ما تصلّح"
description: "الـ profile mode والـ DevTools وميزانية الـ frame، والـ rebuilds والقوائم الطويلة وأغلفة الكتب، والشغل التقيل على الـ main isolate، والـ memory leaks، ووقت فتح الـ app، وتمن طبقات الـ Clean Architecture بالأرقام. كل درس بيبدأ بمشكلة اتقاست في Readly وبيخلص بقياس تاني."
---

Readly دلوقتي فيه كل حاجة: مكتبة بتتزامن، وكتالوج بيتجاب صفحة ورا صفحة، وstream من drift للشاشة، وCubits لكل حاجة. والشكاوى بدأت: «المكتبة بتقطّع وأنا بعمل scroll»، و«الـ app بياخد وقت لحد ما يفتح»، و«الموبايل بيسخن وبعد ساعة الـ app بيقفل لوحده». والغلطة اللي كل فريق بيعملها هنا إنه يبدأ يغيّر: يحط `const` في كل حتة، ويشيل طبقات، ويحوّل كل حاجة لـ isolate. وفي الآخر الـ app لا بقى أسرع ولا حد عارف إيه اللي فرق.

الوحدة دي ماشية على قاعدة واحدة: <b>مفيش optimization من غير رقم قبله ورقم بعده.</b> كل درس بيبدأ بمشكلة حقيقية في Readly اتقاست في profile mode على موبايل متوسط، وبعدين الحل، وبعدين القياس تاني. هتتعلم تقرا الـ timeline وتعرف الـ jank جاي من الـ UI thread ولا الـ raster، وتعدّ الـ rebuilds، وتبني ليستة 4000 كتاب ماتقطّعش، وتفك أغلفة الكتب بالحجم اللي محتاجه بس، وتلاقي الـ object اللي فضل في الـ memory بعد ما الشاشة اتقفلت، وتقص وقت فتح الـ app. وفي الآخر هتقيس السؤال اللي كل interview بيسأله: هل الـ Clean Architecture بطيئة؟ والإجابة هتبقى رقم، مش رأي.
