<Level n="1" title="الفكرة بتشبيه">

<Analogy title="المطعم">

تخيل مطعم صغير فيه شخص واحد بياخد الطلب، ويطبخ، ويغسل الأطباق، ويحاسب. في الأول ماشي الحال. لما الزباين تزيد، الطلبات بتتلخبط، ولو عايز تغيّر مورد الخضار لازم تكلّمه هو، ولو عيّى المطعم كله بيقف. المطعم الكبير بيقسّم الشغل: جرسون في الصالة، شيف في المطبخ، ومسؤول مخزن. الجرسون مايعرفش المورد مين، والشيف مايعرفش الزبون قاعد على أنهي ترابيزة.

</Analogy>

الـ app بتاعك زي المطعم ده بالظبط. في الأول ممكن تكتب كل حاجة في الـ widget وتمشي. لما المشروع يكبر، أو يدخل معاك مطور تاني، أو العميل يطلب تغيير، بتكتشف إن أي تعديل صغير بيكسر حاجة تانية مالهاش علاقة.


</Level>

<Level n="2" title="شكل المشكلة في الكود">

ده كود حقيقي بيتكتب كتير: شاشة المكتبة في Readly، كل حاجة فيها في مكان واحد:

<CodeBlock label="قبل: كل حاجة في الـ widget">

```dart
class _LibraryPageState extends State<LibraryPage> {
  List<Map<String, dynamic>> books = [];
  bool loading = true;
  String? error;

  @override
  void initState() {
    super.initState();
    _load();
  }

  Future<void> _load() async {
    try {
      final res = await Dio().get(
        'https://api.readly.app/library',
        options: Options(headers: {'Authorization': 'Bearer $token'}),
      );
      final list = (res.data as List).cast<Map<String, dynamic>>();
      list.removeWhere((b) => b['status'] == 'archived'); // business rule!
      setState(() {
        books = list;
        loading = false;
      });
    } catch (e) {
      setState(() {
        error = 'Something went wrong';
        loading = false;
      });
    }
  }

  @override
  Widget build(BuildContext context) {
    if (loading) return const CircularProgressIndicator();
    if (error != null) return Text(error!);
    return ListView(
      children: [for (final b in books) Text(b['title'])],
    );
  }
}
```

</CodeBlock>

الكود ده شغال، بس فيه 5 مشاكل هتظهر مع الوقت:

- <b>مايتختبرش:</b> عشان تتأكد إن الكتب المؤرشفة بتتشال، لازم تشغّل الشاشة وتكلّم سيرفر حقيقي.
- <b>تغيير الـ API بيكسر الـ UI:</b> لو السيرفر غيّر اسم `title` لـ `name`، لازم تفتح الشاشة وتعدّل فيها.
- <b>القاعدة متدفنة:</b> «الكتب المؤرشفة ماتظهرش» قاعدة business، بس مستخبية جوه الـ UI. لو شاشة تانية محتاجاها هتتكرر.
- <b>الخطأ بيضيع:</b> النت الفاصل وخطأ السيرفر والـ bug في الكود كلهم بيظهروا «Something went wrong».
- <b>مفيش إعادة استخدام:</b> لو عايز نفس البيانات في widget للشاشة الرئيسية، هتنسخ الكود.

على الشمال: widget واحد شايل كل حاجة. على اليمين: نفس الشغل متوزع على 3 أجزاء، وكل جزء ليه سبب واحد يتغير بيه.

<Level n="3" title="المعمارية بالظبط هي إيه؟">

المعمارية مش «اعمل فولدر اسمه domain». المعمارية هي مجموعة قرارات بتجاوب على سؤالين:

1. <b>مين يعرف مين؟</b> يعني مين يعمل import لمين. الـ UI يعرف dio؟ القاعدة تعرف شكل الـ JSON؟
2. <b>كل نوع تغيير بيقع فين؟</b> لو الـ API اتغير، أنهي ملف يتعدّل؟ لو القاعدة اتغيرت؟ لو النص اتغير؟

المعمارية الكويسة هي اللي فيها إجابة السؤال التاني دايمًا «ملف واحد». في الكود اللي فوق، الإجابة على كل أنواع التغيير هي «الشاشة»، وده معناه إن الشاشة هتتكسر مع أي تغيير.

<Note kind="info" title="تكلفة التغيير">

في المشروع المتلخبط، تكلفة أي تعديل بتزيد مع حجم المشروع لأن كل حاجة مربوطة بكل حاجة. في المشروع المتقسم صح، تكلفة التعديل بتفضل ثابتة تقريبًا، لأن التغيير بيقع في مكانه وبس.

</Note>

نفس الشاشة لما تتقسم، ده شكلها مختصر. كل جزء ليه سبب واحد يتغير بيه:

<CodeBlock label="بعد: 3 أجزاء">

```dart
// data: knows dio and the JSON shape
class LibraryRepositoryImpl implements LibraryRepository {
  LibraryRepositoryImpl(this._remote);
  final LibraryRemoteSource _remote;

  @override
  Future<Result<List<Book>>> getLibrary() => guard(() async {
        final dtos = await _remote.fetchLibrary();
        return dtos.map((d) => d.toEntity()).toList();
      });
}

// domain: the rule, in plain Dart
class GetLibrary {
  GetLibrary(this._repository);
  final LibraryRepository _repository;

  Future<Result<List<Book>>> call() async => switch (await _repository.getLibrary()) {
        Success(:final value) => Success(value.where((b) => !b.isArchived).toList()),
        Err(:final failure) => Err(failure),
      };
}

// presentation: only shows what the Cubit says
BlocBuilder<LibraryCubit, LibraryState>(
  builder: (context, state) => switch (state) {
    LibraryLoading() => const CircularProgressIndicator(),
    LibraryLoaded(:final books) => BookList(books: books),
    LibraryError(:final failure) => ErrorView(message: failure.localized(AppLocalizations.of(context)!)),
  },
)
```

</CodeBlock>

مش لازم تفهم كل سطر دلوقتي. درس «أول feature ملف بملف» بيبني ده من الأول، والوحدات اللي بعده بتعمّق في كل جزء. المهم هنا إنك تشوف المشاكل اللي فوق وهي بتتحل:

### العميل عايز المكتبة تشتغل من غير نت

في نسخة الـ widget، هتفتح الشاشة وتزوّد DB وتقرر امتى تقرا منها، جنب الـ dio والـ setState والقاعدة. في النسخة المتقسمة، التغيير كله في `LibraryRepositoryImpl`: يقرا من الـ DB الأول، ويحدّث من السيرفر. الـ use case والـ Cubit والشاشة مش هيعرفوا إن حاجة اتغيرت، لأن الـ contract لسه بيرجّع `Result<List<Book>>`.

### عايز تتأكد إن الكتب المؤرشفة مابتظهرش

في نسخة الـ widget، التست محتاج سيرفر حقيقي فيه كتاب مؤرشف، وشاشة شغالة. في النسخة المتقسمة، القاعدة في `GetLibrary`، وده Dart صافي:

<CodeBlock label="تست القاعدة في أجزاء من الثانية">

```dart
class FakeLibraryRepository implements LibraryRepository {
  FakeLibraryRepository(this.books);
  final List<Book> books;

  @override
  Future<Result<List<Book>>> getLibrary() async => Success(books);
  // ... other methods
}

test('archived books are hidden', () async {
  final getLibrary = GetLibrary(FakeLibraryRepository([tReading, tArchived]));

  final result = await getLibrary();

  expect((result as Success<List<Book>>).value, [tReading]);
});
```

</CodeBlock>

### الشاشة الرئيسية محتاجة نفس الكتب

مطور تاني عمل widget «بتقرا دلوقتي» في الشاشة الرئيسية، ونسخ الطلب، ونسي سطر `removeWhere`. فالكتب المؤرشفة ظهرت هناك ومش ظاهرة في المكتبة، وكل شاشة بقت بتقول حاجة. القاعدة لما تبقى في مكان واحد (`GetLibrary`، أو getter زي `book.isArchived` جوه الـ entity)، أي شاشة تانية بتستخدمها بدل ما تنسخها.

### «Something went wrong» لكل حاجة

الـ `catch (e)` بيبلع كل حاجة: النت الفاصل، والـ session اللي خلصت، والـ null error في الكود. المستخدم مش عارف يعمل إيه، وانت مش عارف إن في bug. في النسخة المتقسمة، الـ repository بيحوّل أخطاء الشبكة بس لـ Failures ليها أنواع، والشاشة بتعرض لكل نوع رد مختلف، والـ bug الحقيقي بيضرب ويوصل لتقرير الـ crash. ده درس الأخطاء في الوحدة 2.


</Level>

<Level n="4" title="المعمارية ليها تمن">

كل طبقة إضافية معناها ملفات أكتر وكود أكتر لنفس الميزة. في prototype أو hackathon أو app هيتشال بعد شهر، المعمارية الكاملة ممكن تكون عبء مش فايدة.

المطور المحترف مش اللي بيطبّق Clean Architecture في كل حاجة. المحترف اللي يعرف يحسب التمن ده ويقرر: المشروع ده هيعيش قد إيه؟ فيه قواعد business حقيقية؟ هيشتغل عليه كام واحد؟ (هنرجع للقرار ده في درس «Clean ولا MVVM؟» في الوحدة 12).

| السؤال | لو الإجابة كده، المعمارية بتستاهل | لو كده، خففها |
| --- | --- | --- |
| المشروع هيعيش قد إيه؟ | سنين، وهيتطور | أسابيع، أو demo |
| كام واحد بيشتغل عليه؟ | أكتر من واحد، أو هيتسلم لفريق تاني | انت لوحدك ومش هتلمسه تاني |
| فيه قواعد business؟ | آه: صلاحيات، حسابات، offline، conflicts | شاشات بتعرض اللي جاي من الـ API زي ما هو |
| مصادر البيانات | أكتر من API، وDB محلية، وكاش | API واحد |
| التستات | لازم، والـ CI بيمنع الـ merge | مش مطلوبة |

- <b>المعمارية مش كل أو لا شيء:</b> حتى في app صغير، فصل الـ UI عن الطلبات بـ repository تمنه قليل وفايدته كبيرة. الـ use cases والـ value objects والـ packages بتضيفهم لما القواعد تظهر، مش من أول يوم.
- <b>الفولدرات مش معمارية:</b> مشروع فيه فولدرات `domain` و`data` و`presentation`، والـ domain بيعمل import لـ dio، ده layer-first شكلًا بس. المعمارية هي اتجاه الـ imports، والفولدرات مجرد مكان.
- <b>علامات الـ over-engineering:</b> use case لكل getter من غير ولا قاعدة، وinterface لكل class حتى اللي عمرها ما هيبقى ليها fake أو implementation تاني، و5 ملفات عشان تعرض نص ثابت. لو مش قادر تقول الطبقة دي بتحميك من أنهي تغيير، يبقى مالهاش لازمة.
- <b>تكلفة إنك تأجل:</b> تحويل مشروع متلخبط لمتقسم أغلى بكتير من إنك تبدأ متقسم، لأن القواعد بتكون اتنسخت في 10 شاشات. علشان كده في درس «Refactor feature قديمة لـ Clean» في الوحدة 12 بنعمله feature feature، مش مرة واحدة.

<Note kind="interview" title="سؤال interview">

«ليه بتستخدم Clean Architecture؟» الإجابة الضعيفة: «عشان الكود يبقى نظيف». الإجابة القوية: «عشان كل نوع تغيير يقع في مكان واحد، والقواعد تتختبر من غير UI ولا سيرفر، وبقرر أستخدمها حسب حجم المشروع وعمره».

</Note>


</Level>

<Question id="why-1">
<Ask>في كود الشاشة اللي فوق، لو السيرفر بقى يرجّع الكتب جوه `{'data': [...]}` بدل list مباشرة، هتعدّل فين؟</Ask>
<Answer>

في الشاشة نفسها، لأن الـ parsing جواها. وده بالظبط المشكلة: تغيير في شكل الـ API وصل للـ UI.

</Answer>

<Question id="why-2">
<Ask>المعمارية بتجاوب على أنهي سؤالين؟</Ask>
<Answer>

مين يعرف مين (الـ imports)، وكل نوع تغيير بيقع فين.

</Answer>
</Question>

<Question id="why-3">
<Ask>امتى تكون المعمارية الكاملة قرار غلط؟</Ask>
<Answer>

في prototype أو app قصير العمر أو مفيهوش قواعد business حقيقية، لأن تمن الملفات الزيادة أكبر من الفايدة.

</Answer>
</Question>
