<Level n="1" title="الفكرة بتشبيه">

<Analogy title="المطعم">

تخيل مطعم صغير فيه شخص واحد بياخد الطلب، ويطبخ، ويغسل الأطباق، ويحاسب. في الأول ماشي الحال. لما الزباين تزيد، الطلبات بتتلخبط، ولو عايز تغيّر مورد الخضار لازم تكلّمه هو، ولو عيّى المطعم كله بيقف. المطعم الكبير بيقسّم الشغل: جرسون في الصالة، شيف في المطبخ، ومسؤول مخزن. الجرسون مايعرفش المورد مين، والشيف مايعرفش الزبون قاعد على أنهي ترابيزة.

</Analogy>

الـ app بتاعك زي المطعم ده بالظبط. في الأول ممكن تكتب كل حاجة في الـ widget وتمشي. لما المشروع يكبر، أو يدخل معاك مطور تاني، أو العميل يطلب تغيير، بتكتشف إن أي تعديل صغير بيكسر حاجة تانية مالهاش علاقة.


</Level>

<Level n="2" title="شكل المشكلة في الكود">

ده كود حقيقي بيتكتب كتير: شاشة المكتبة في Readly، كل حاجة فيها في مكان واحد:

<CodeBlock label="قبل: كل حاجة في الـ widget">

```dart
class _LibraryPageState extends State<LibraryPage> {
  List<Map<String, dynamic>> books = [];
  bool loading = true;
  String? error;

  @override
  void initState() {
    super.initState();
    _load();
  }

  Future<void> _load() async {
    try {
      final res = await Dio().get(
        'https://api.readly.app/library',
        options: Options(headers: {'Authorization': 'Bearer $token'}),
      );
      final list = (res.data as List).cast<Map<String, dynamic>>();
      list.removeWhere((b) => b['status'] == 'archived'); // business rule!
      setState(() {
        books = list;
        loading = false;
      });
    } catch (e) {
      setState(() {
        error = 'Something went wrong';
        loading = false;
      });
    }
  }

  @override
  Widget build(BuildContext context) {
    if (loading) return const CircularProgressIndicator();
    if (error != null) return Text(error!);
    return ListView(
      children: [for (final b in books) Text(b['title'])],
    );
  }
}
```

</CodeBlock>

الكود ده شغال، بس فيه 5 مشاكل هتظهر مع الوقت:

- <b>مايتختبرش:</b> عشان تتأكد إن الكتب المؤرشفة بتتشال، لازم تشغّل الشاشة وتكلّم سيرفر حقيقي.
- <b>تغيير الـ API بيكسر الـ UI:</b> لو السيرفر غيّر اسم `title` لـ `name`، لازم تفتح الشاشة وتعدّل فيها.
- <b>القاعدة متدفنة:</b> «الكتب المؤرشفة ماتظهرش» قاعدة business، بس مستخبية جوه الـ UI. لو شاشة تانية محتاجاها هتتكرر.
- <b>الخطأ بيضيع:</b> النت الفاصل وخطأ السيرفر والـ bug في الكود كلهم بيظهروا «Something went wrong».
- <b>مفيش إعادة استخدام:</b> لو عايز نفس البيانات في widget للشاشة الرئيسية، هتنسخ الكود.

<Diagram name="d-ce06f8f057">

على الشمال: widget واحد شايل كل حاجة. على اليمين: نفس الشغل متوزع على 3 أجزاء، وكل جزء ليه سبب واحد يتغير بيه.

</Diagram>


</Level>

<Level n="3" title="المعمارية بالظبط هي إيه؟">

المعمارية مش «اعمل فولدر اسمه domain». المعمارية هي مجموعة قرارات بتجاوب على سؤالين:

1. <b>مين يعرف مين؟</b> يعني مين يعمل import لمين. الـ UI يعرف dio؟ القاعدة تعرف شكل الـ JSON؟
2. <b>كل نوع تغيير بيقع فين؟</b> لو الـ API اتغير، أنهي ملف يتعدّل؟ لو القاعدة اتغيرت؟ لو النص اتغير؟

المعمارية الكويسة هي اللي فيها إجابة السؤال التاني دايمًا «ملف واحد». في الكود اللي فوق، الإجابة على كل أنواع التغيير هي «الشاشة»، وده معناه إن الشاشة هتتكسر مع أي تغيير.

<Note kind="info" title="تكلفة التغيير">

في المشروع المتلخبط، تكلفة أي تعديل بتزيد مع حجم المشروع لأن كل حاجة مربوطة بكل حاجة. في المشروع المتقسم صح، تكلفة التعديل بتفضل ثابتة تقريبًا، لأن التغيير بيقع في مكانه وبس.

</Note>


</Level>

<Level n="4" title="المعمارية ليها تمن">

كل طبقة إضافية معناها ملفات أكتر وكود أكتر لنفس الميزة. في prototype أو hackathon أو app هيتشال بعد شهر، المعمارية الكاملة ممكن تكون عبء مش فايدة.

المطور المحترف مش اللي بيطبّق Clean Architecture في كل حاجة. المحترف اللي يعرف يحسب التمن ده ويقرر: المشروع ده هيعيش قد إيه؟ فيه قواعد business حقيقية؟ هيشتغل عليه كام واحد؟ (هنرجع للقرار ده في درس «Clean ولا MVVM؟» في الوحدة 8).

<Note kind="interview" title="سؤال interview">

«ليه بتستخدم Clean Architecture؟» الإجابة الضعيفة: «عشان الكود يبقى نظيف». الإجابة القوية: «عشان كل نوع تغيير يقع في مكان واحد، والقواعد تتختبر من غير UI ولا سيرفر، وبقرر أستخدمها حسب حجم المشروع وعمره».

</Note>


</Level>

<Quiz>

<Question id="why-1">
<Ask>في كود الشاشة اللي فوق، لو السيرفر بقى يرجّع الكتب جوه `{'data': [...]}` بدل list مباشرة، هتعدّل فين؟</Ask>
<Answer>

في الشاشة نفسها، لأن الـ parsing جواها. وده بالظبط المشكلة: تغيير في شكل الـ API وصل للـ UI.

</Answer>
</Question>

<Question id="why-2">
<Ask>المعمارية بتجاوب على أنهي سؤالين؟</Ask>
<Answer>

مين يعرف مين (الـ imports)، وكل نوع تغيير بيقع فين.

</Answer>
</Question>

<Question id="why-3">
<Ask>امتى تكون المعمارية الكاملة قرار غلط؟</Ask>
<Answer>

في prototype أو app قصير العمر أو مفيهوش قواعد business حقيقية، لأن تمن الملفات الزيادة أكبر من الفايدة.

</Answer>
</Question>

</Quiz>
