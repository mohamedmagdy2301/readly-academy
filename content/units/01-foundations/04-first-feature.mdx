<Analogy title="طلب واحد من المطبخ للترابيزة">

قبل ما تتعلم كل محطة في المطعم بالتفصيل، بتمشي ورا <b>طلب واحد</b> من أوله لآخره. الشيف بيكتب الوصفة الأول (إيه اللي الطبق محتاجه)، وبعدين ورقة الطلبات للمخزن، والمخزن بيعرف يجيب المكونات منين، والجرسون بيقدّم الطبق، والمدير بيوزّع مين يشتغل مع مين، وفي الآخر حد بيدوق قبل ما الطبق يطلع. بعد كده تقدر تتخصص في أي محطة وانت عارف هي فين في الصورة.

</Analogy>

الدرس ده هو الطلب الواحد. هنبني feature صغيرة في Readly: المستخدم بيدوس على كتاب في الكتالوج، وتفتح صفحة فيها الغلاف والعنوان والوصف والمواضيع، جاية من Open Library على `/works/<id>.json`. اخترناها لأنها قراية بس، وطلب واحد، ومن غير login، ومع ذلك بتعدّي على كل طبقة.

الترتيب من جوه لبره: الـ Domain الأول، بعدين الـ Data، بعدين الـ Presentation، وبعدين التوصيل والتست. السبب إن الـ Domain مابيعتمدش على حد، فكل ملف بتكتبه بيعمل import لملفات اتكتبت قبله بس، والكود بيعمل compile في كل خطوة.

### قبل ما نبدأ: الـ core

<CodeBlock label="core/result.dart و core/failure.dart (نسخة أولى)">

```dart
// core/result.dart
sealed class Result<T> {
  const Result();
}

final class Success<T> extends Result<T> {
  const Success(this.value);
  final T value;
}

final class Err<T> extends Result<T> {
  const Err(this.failure);
  final Failure failure;
}

// core/failure.dart
sealed class Failure {
  const Failure(this.message);
  final String message; // for logs, not for the user
}

final class NetworkFailure extends Failure {
  const NetworkFailure() : super('No internet connection');
}

final class ServerFailure extends Failure {
  const ServerFailure(super.message, {this.statusCode});
  final int? statusCode;
}

final class ValidationFailure extends Failure {
  const ValidationFailure(super.message);
}

// core/book_id.dart: a String with its own type
extension type const BookId(String value) {}
```

</CodeBlock>

ده نفس شكل `Result` و`Failure` في درس الأخطاء، بس بأنواع أقل. هنعمّق ده في درس الأخطاء: `UnauthorizedFailure` و`CacheFailure`، وليه الـ Failure sealed، وترجمتها لرسايل. والـ `BookId` هنا extension type بسيط بيمنعك تبعت عنوان كتاب مكان الـ id. في درس الـ Domain هيبقى ليه constructor خاص و`create` بيتحقق.

### 6. الـ repository implementation

<CodeBlock label="core/guard.dart (نسخة أولى)">

```dart
Future<Result<T>> guard<T>(Future<T> Function() run) async {
  try {
    return Success(await run());
  } on DioException catch (e) {
    return Err(switch (e.type) {
      DioExceptionType.connectionError ||
      DioExceptionType.connectionTimeout =>
        const NetworkFailure(),
      _ => ServerFailure(e.message ?? 'Unexpected error', statusCode: e.response?.statusCode),
    });
  }
}
```

</CodeBlock>

<CodeBlock label="features/catalog/data/catalog_repository_impl.dart">

### 7. الـ states والـ Cubit

<CodeBlock label="features/catalog/presentation/book_details_cubit.dart">

```dart
sealed class BookDetailsState {
  const BookDetailsState();
}
final class BookDetailsLoading extends BookDetailsState {
  const BookDetailsLoading();
}
final class BookDetailsLoaded extends BookDetailsState {
  const BookDetailsLoaded(this.book);
  final BookDetails book;
}
final class BookDetailsError extends BookDetailsState {
  const BookDetailsError(this.failure);
  final Failure failure;
}

class BookDetailsCubit extends Cubit<BookDetailsState> {
  BookDetailsCubit(this._getBookDetails) : super(const BookDetailsLoading());
  final GetBookDetails _getBookDetails;

  Future<void> load(String id) async {
    emit(const BookDetailsLoading());
    final result = await _getBookDetails(id);
    emit(switch (result) {
      Success(:final value) => BookDetailsLoaded(value),
      Err(:final failure) => BookDetailsError(failure),
    });
  }
}
```

</CodeBlock>

الـ Cubit بيعمل import للـ Domain بس: `GetBookDetails` و`BookDetails` و`Failure`. مايعرفش إن في dio أو JSON أصلًا. هنعمّق ده في درس الـ Cubit: الـ race conditions والـ refresh والـ side effects.

### الـ description مرة String ومرة Map

افتح كتب كتير، وفجأة الـ app يقع بـ `type '_Map<String, dynamic>' is not a subtype of type 'String?' in type cast`. السبب إن Open Library بيرجّع الـ description بشكلين: نص عادي، أو object:

```json
"description": { "type": "/type/text", "value": "The main character of..." }
```

والـ `guard` مابيمسكش الـ TypeError، وده صح: ده bug في فهمنا للـ API، لازم يضرب ويتصلح، مش يتخبى ورا «حصلت مشكلة». الحل في مكان واحد، الـ `fromJson`، بـ switch على الشكل:

<CodeBlock label="pattern لكل شكل">

```dart
factory WorkDto.fromJson(Map<String, dynamic> json) => WorkDto(
      key: json['key'] as String,
      title: json['title'] as String,
      description: switch (json['description']) {
        String text => text,
        {'value': String text} => text, // {"type": "/type/text", "value": ...}
        _ => null,
      },
      // ...covers, subjects as before
    );
```

</CodeBlock>

الـ map pattern `{'value': String text}` بيتأكد إن القيمة Map، وفيها مفتاح `value`، وقيمته String، وبيطلّعها في `text`، والمفاتيح الزيادة زي `type` مابتفرقش. وقبل ما تقفل الـ bug، اكتب التست اللي كان هيمسكه:

<CodeBlock label="test/features/catalog/data/work_dto_test.dart">

```dart
test('reads description in both shapes', () {
  final plain = WorkDto.fromJson({'key': '/works/OL1W', 'title': 'A', 'description': 'text'});
  final typed = WorkDto.fromJson({
    'key': '/works/OL1W',
    'title': 'A',
    'description': {'type': '/type/text', 'value': 'text'},
  });

  expect(plain.description, 'text');
  expect(typed.description, 'text');

```

</CodeBlock>

لاحظ إن الـ entity والـ Cubit والشاشة ماتغيروش. تغيير في شكل الـ API وقف عند الـ DTO، وده بالظبط اللي الطبقات بتشتريه.

### اسم المؤلف مش في الرد

الـ `authors` فيها keys بس، زي `/authors/OL34184A`. الاسم محتاج طلب تاني لـ `/authors/OL34184A.json`، اللي بيرجّع `name`. لو حطيت الطلب التاني في الـ Cubit، الـ Cubit هيعرف تفاصيل Open Library. مكانه الـ repository: هو اللي بيجمّع الـ entity من أكتر من مصدر.

<CodeBlock label="طلبين ورا الـ repository">

```dart
// work_dto.dart: read the author ids with a nested pattern
authorIds: [
  for (final a in json['authors'] as List? ?? const [])
    if (a case {'author': {'key': String key}}) key.split('/').last,
],

// catalog_remote_source.dart
Future<String> fetchAuthorName(String authorId) async {
  final res = await _dio.get<Map<String, dynamic>>('/authors/$authorId.json');
  return res.data!['name'] as String;
}

// catalog_repository_impl.dart
@override
Future<Result<BookDetails>> getBookDetails(BookId id) => guard(() async {
      final work = await _remote.fetchWork(id.value);
      final names = await Future.wait(work.authorIds.take(3).map(_authorNameOrNull));
      return work.toEntity(authors: names.nonNulls.toList());
    });

Future<String?> _authorNameOrNull(String authorId) async {
  try {
    return await _remote.fetchAuthorName(authorId);
  } on DioException {
    return null; // a missing author name should not hide the whole book
  }
}
```

</CodeBlock>

- <b>الـ Future.wait:</b> طلبات المؤلفين بتطلع مع بعض مش ورا بعض. 3 مؤلفين = وقت طلب واحد تقريبًا.
- <b>الـ take(3):</b> في works ليها مؤلفين كتير. الصفحة مش محتاجاهم كلهم، والطلبات ليها تمن.
- <b>فشل المؤلف مش فشل الكتاب:</b> لو طلب المؤلف وقع، الصفحة تظهر من غير اسمه أحسن من صفحة error. ده قرار business، ومكانه الـ repository مش الـ UI.

والـ entity زاد فيها `final List<String> authors` بـ default `const []`، والـ mapper بقى بياخد الأسماء: `toEntity(authors: ...)`. الـ Cubit مايعرفش إن الطلب بقى 3 طلبات.

### المستخدم رجع قبل ما الرد يوصل

النت بطيء، والمستخدم فتح الكتاب ورجع على طول. الـ BlocProvider عمل close للـ Cubit، وبعدها الرد وصل والـ Cubit عمل emit، فيطلع `Bad state: Cannot emit new states after calling close`. الحل سطر واحد بعد كل await:

<CodeBlock label="isClosed">

```dart
Future<void> load(String id) async {
  emit(const BookDetailsLoading());
  final result = await _getBookDetails(id);
  if (isClosed) return; // the page is gone
  emit(switch (result) {
    Success(:final value) => BookDetailsLoaded(value),
    Err(:final failure) => BookDetailsError(failure),
  });
}
```

</CodeBlock>

### الكتاب مش موجود: زرار «جرّب تاني» مالوش لازمة

حد فتح deep link لكتاب اتشال من Open Library، فالسيرفر رجّع 404. الشاشة بتقول «جرّب تاني»، والمستخدم هيدوس 10 مرات على طلب عمره ما هينجح. الـ 404 مش زي النت الفاصل، والقرار على نوع الـ Failure وتفاصيله، مش على نص:

<CodeBlock label="رسالة لكل نوع">

```dart
BookDetailsError(:final failure) => switch (failure) {
    ServerFailure(statusCode: 404) => const Center(child: Text('الكتاب ده مش موجود')),
    NetworkFailure() => RetryView(
        message: 'مفيش اتصال بالنت',
        onRetry: () => context.read<BookDetailsCubit>().load(id),
      ),
    _ => RetryView(
        message: 'حصلت مشكلة، جرّب تاني',
        onRetry: () => context.read<BookDetailsCubit>().load(id),
      ),
  },
```

</CodeBlock>

الـ `ServerFailure(statusCode: 404)` pattern بيتأكد من النوع والحقل مع بعض. ونفس الفكرة في درس الـ Forms مع الـ 403 والـ 409.

### صفحة فاضية لما تفتح من نتيجة البحث

نتيجة البحث في Open Library فيها `"key": "/works/OL45804W"`. لو الـ mapper بتاع البحث حط الـ key ده زي ما هو في `Book.id`، اللينك هيبقى `/catalog/books//works/OL45804W`، والـ route مش هيعمل match. القاعدة: الـ id في الـ entity نضيف، وشكل Open Library بيتشال في الـ mapper. فـ `key.split('/').last` لازم يبقى في mapper البحث كمان، مش في الـ UI قبل الـ push.

### اتنين Dio من نفس النوع

في الأسبوع 3 هتسجّل Dio تاني للـ backend بتاعك، عليه `AuthInterceptor` بيحط الـ token. لو سجّلته `registerLazySingleton<Dio>` هو كمان، get_it هيرمي error إن `Dio` متسجل قبل كده. والأخطر لو حد «حلّها» إن الاتنين يبقوا واحد: الـ token بتاع المستخدم هيتبعت لـ Open Library مع كل طلب. الحل اسم لكل نسخة:

<CodeBlock label="instanceName">

```dart
getIt
  ..registerLazySingleton<Dio>(
    () => Dio(BaseOptions(baseUrl: 'https://openlibrary.org')),
    instanceName: 'openLibrary',
  )
  ..registerLazySingleton<CatalogRemoteSource>(
    () => CatalogRemoteSource(getIt<Dio>(instanceName: 'openLibrary')),
  );
```

</CodeBlock>

هنعمّق ده في درس الـ DI: injectable والـ `@Named`، والـ flavors.

</Level>

<Level n="4" title="قرارات الـ senior">

- <b>من جوه لبره ولا من بره لجوه؟</b> إحنا بدأنا بالـ Domain عشان كل خطوة تعمل compile وتتختبر. بس كتير من الفرق بتبدأ بالشاشة بـ state متكتبة بإيدها، عشان يتأكدوا من الـ UX مع الـ designer قبل أي API، وبعدين يدخلوا لجوه. الاتنين صح. اللي مش بيتغير هو اتجاه الـ imports، مش ترتيب الكتابة.
- <b>الـ GetBookDetails تقريبًا pass-through:</b> فيه trim وcheck بس. ممكن تسيبه عشان كل الـ features شكلها واحد، أو الـ Cubit يكلّم الـ repository على طول. الغلط إنك تعمل كده من غير ما تقرر. درس الـ Domain بيدخل في السؤال ده.
- <b>BookDetails منفصل ولا Book بحقول nullable؟</b> لو `Book` فيه `description?` و`subjects?` و`authors?` عشان صفحة التفاصيل، كل شاشة هتسأل «الحقل ده موجود ولا لأ؟». كل entity بالضمانات بتاعتها أوضح، والتمن mapper زيادة.
- <b>الكاش:</b> تفاصيل الكتاب نادرًا ما تتغير، فهي مرشح ممتاز لـ cache-first: map في الذاكرة جوه الـ repository بيخلي الرجوع للكتاب فوري، والـ Cubit مش هيحس. وفي درس Offline-first ممكن تحفظها في drift. ماتحطش الكاش في الـ Cubit، لأنه بيتقفل مع الشاشة.
- <b>اتعامل مع Open Library بأدب:</b> ده API مجاني ومن غير key، وبيطلب من الـ apps اللي بتكلّمه كتير تبعت `User-Agent` فيه اسم الـ app ووسيلة تواصل. حطه في `BaseOptions(headers: ...)` على الـ Dio بتاعه بس، وماتعملش طلبات مالهاش لازمة (زي المؤلفين كلهم).
- <b>11 ملف لصفحة واحدة:</b> ده التمن اللي درس «ليه أصلًا محتاجين Architecture» اتكلم عنه. في MVVM الصفحة دي ممكن تبقى 4 ملفات. اللي بتاخده قصاده إن كل تغيير ليه مكان واحد: شكل الـ JSON في الـ DTO، والقاعدة في الـ use case، والنص في الشاشة. وده قرار هنرجعله في درس «Clean ولا MVVM؟».

<Note kind="interview" title="سؤال interview">

«احكيلي رحلة ضغطة على كتاب لحد ما التفاصيل تظهر.» الـ route بيعمل الـ Cubit من get_it وينادي `load(id)`. الـ Cubit بيعمل emit لـ Loading وينادي الـ use case، اللي بيتحقق من الـ id ويطلب من الـ repository contract. الـ implementation في الـ Data بينادي الـ remote source اللي بيعمل الطلب بـ dio، ويحوّل الـ DTO لـ entity بالـ mapper، والـ DioException لـ Failure بالـ guard. الـ Result بيطلع لفوق، والـ Cubit بيعمل switch ويعمل emit لـ Loaded أو Error، والـ BlocBuilder بيرسم. البيانات طالعة من تحت لفوق، والـ imports كلها بتشاور على الـ Domain.

</Note>

### الـ data كاملة بعد Level 3

```dart
// work_dto.dart
class WorkDto {
  const WorkDto({
    required this.key,
    required this.title,
    this.description,
    this.covers = const [],
    this.subjects = const [],
    this.authorIds = const [],
  });

  final String key;
  final String title;
  final String? description;
  final List<int> covers;
  final List<String> subjects;
  final List<String> authorIds;

  factory WorkDto.fromJson(Map<String, dynamic> json) => WorkDto(
        key: json['key'] as String,
        title: json['title'] as String,
        description: switch (json['description']) {
          String text => text,
          {'value': String text} => text,
          _ => null,
        },
        covers: (json['covers'] as List?)?.whereType<int>().toList() ?? const [],
        subjects: (json['subjects'] as List?)?.whereType<String>().toList() ?? const [],
        authorIds: [
          for (final a in json['authors'] as List? ?? const [])
            if (a case {'author': {'key': String key}}) key.split('/').last,
        ],
      );
}

// work_mapper.dart
extension WorkDtoMapper on WorkDto {
  BookDetails toEntity({required List<String> authors}) => BookDetails(
        id: BookId(key.split('/').last),
        title: title,
        authors: authors,
        description: description,
        coverUrl: covers.isEmpty
            ? null
            : Uri.parse('https://covers.openlibrary.org/b/id/${covers.first}-L.jpg'),
        subjects: subjects,
      );
}

// catalog_repository_impl.dart
class CatalogRepositoryImpl implements CatalogRepository {
  CatalogRepositoryImpl(this._remote);
  final CatalogRemoteSource _remote;

  @override
  Future<Result<BookDetails>> getBookDetails(BookId id) => guard(() async {
        final work = await _remote.fetchWork(id.value);
        final names = await Future.wait(work.authorIds.take(3).map(_authorNameOrNull));
        return work.toEntity(authors: names.nonNulls.toList());
      });

  Future<String?> _authorNameOrNull(String authorId) async {
    try {
      return await _remote.fetchAuthorName(authorId);
    } on DioException {
      return null;
    }
  }
}
```
