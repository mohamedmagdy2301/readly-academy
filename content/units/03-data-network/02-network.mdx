<Level n="1" title="الفكرة بتشبيه">

<Analogy title="مكتب البريد">

كل جواب (request) بيعدّي على سير فيه موظفين قبل ما يخرج. واحد بيلزق الطابع (الـ token)، وواحد بيسجّل الجواب في الدفتر (الـ log). ولو الجواب رجع مكتوب عليه «الطابع منتهي»، في موظف بيجيب طابع جديد ويبعته تاني من غير ما صاحب الجواب يحس. الموظفين دول هما الـ <b>interceptors</b>.

</Analogy>

كل request بيعدّي على الـ interceptors بالترتيب قبل ما يوصل للسيرفر، والـ response بيرجع عليهم بالعكس.

</Diagram>

| نوع الـ DioException | معناه | بيتحول لـ |
| --- | --- | --- |
| `connectionError` و`connectionTimeout` | مفيش نت أو السيرفر مش بيرد | NetworkFailure |
| `badResponse` مع 401 | الـ token انتهى أو مش صالح | UnauthorizedFailure (بعد محاولة refresh) |
| `badResponse` مع 4xx أو 5xx | السيرفر رفض أو عنده مشكلة | ServerFailure |
| `cancel` | الطلب اتلغى عن قصد | غالبًا تتجاهله |


</Level>

<Level n="3" title="الـ interceptors والـ token refresh">

أصعب جزء في الشبكة: الـ access token بينتهي كل شوية، ولازم تجدده من غير ما المستخدم يحس. والمشكلة الحقيقية لما 3 طلبات يرجعوا 401 في نفس اللحظة: مش عايز 3 refresh، عايز واحد والباقي يستنوه.

<CodeBlock label="AuthInterceptor كامل">

```dart
class AuthInterceptor extends Interceptor {
  AuthInterceptor(this._tokens, this._refreshDio, this._dio);

  final TokenStore _tokens;
  final Dio _refreshDio; // separate client: no AuthInterceptor on it
  final Dio _dio;        // the main client, used to retry
  Completer<String?>? _refreshing;

  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) async {
    final token = await _tokens.accessToken;
    if (token != null) options.headers['Authorization'] = 'Bearer $token';
    handler.next(options);
  }

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    final is401 = err.response?.statusCode == 401;
    final alreadyRetried = err.requestOptions.extra['retried'] == true;
    final skipAuth = err.requestOptions.extra['skipAuth'] == true; // login, register
    if (!is401 || alreadyRetried || skipAuth) return handler.next(err);

    final String? newToken;
    try {
      newToken = await _refreshOnce();
    } catch (e) {
      // the refresh never reached a verdict (offline, server down): pass that error on
      return handler.next(e is DioException ? e : err);
    }
    if (newToken == null) return handler.next(err); // becomes UnauthorizedFailure

    final options = err.requestOptions
      ..headers['Authorization'] = 'Bearer $newToken'
      ..extra['retried'] = true;
    try {
      handler.resolve(await _dio.fetch(options));
    } on DioException catch (e) {
      handler.next(e);
    }
  }

  Future<String?> _refreshOnce() {
    final running = _refreshing;
    if (running != null) return running.future; // wait for the same refresh

    final completer = Completer<String?>();
    _refreshing = completer;
    () async {
      try {
        final res = await _refreshDio.post('/auth/refresh',
            data: {'refreshToken': await _tokens.refreshToken});
        final access = res.data['accessToken'] as String;
        await _tokens.save(access: access, refresh: res.data['refreshToken'] as String);
        completer.complete(access);
      } catch (e) {
        final rejected = e is DioException && e.response?.statusCode == 401;
        if (rejected) {
          await _tokens.clear(); // the server said no: the session is over
          completer.complete(null);
        } else {
          completer.completeError(e); // keep the tokens, the user stays logged in
        }
      } finally {
        _refreshing = null;
      }
    }();
    return completer.future;
  }
}
```

</CodeBlock>

1. <b>الـ onRequest:</b> بيضيف الـ token لكل طلب.
2. <b>الـ onError:</b> لو 401 ومحاولناش قبل كده، يجدد الـ token ويعيد نفس الطلب.
3. <b>الـ Completer:</b> أول طلب يبدأ الـ refresh ويحط Completer. أي طلب تاني يلاقيه موجود فيستنى نفس الـ future بدل ما يبدأ refresh جديد.
4. <b>الـ refreshDio منفصل:</b> لو الـ refresh نفسه رجع 401 وهو معدّي على نفس الـ interceptor، هيدخل في loop لا نهائي.
5. <b>الـ extra['retried']:</b> بيمنع إن نفس الطلب يتعاد مرتين لو رجع 401 تاني.
6. <b>الـ extra['skipAuth']:</b> طلبات الـ login والتسجيل الـ remote source بيعلّمها بيه. الـ 401 هناك معناها «الإيميل أو الباسورد غلط»، مش token خلص، فمفيش refresh.
7. <b>المسح مع 401 بس:</b> الـ tokens بتتمسح بس لو السيرفر رفض الـ refresh token نفسه. لو النت قطع وقت الـ refresh، الـ refresh token لسه سليم، فبيفضل محفوظ والطلب بيفشل كـ NetworkFailure، والمستخدم يفضل جوه.

<CodeBlock label="Retry مع backoff للـ GET بس">

```dart
class RetryInterceptor extends Interceptor {
  RetryInterceptor(this._dio, {this.maxAttempts = 3});
  final Dio _dio;
  final int maxAttempts;

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    final options = err.requestOptions;
    final attempt = (options.extra['attempt'] as int?) ?? 0;
    final isNetwork = err.type == DioExceptionType.connectionError ||
        err.type == DioExceptionType.connectionTimeout;
    if (options.method != 'GET' || !isNetwork || attempt >= maxAttempts) {
      return handler.next(err);
    }
    await Future.delayed(Duration(milliseconds: 300 * (1 << attempt))); // 300, 600, 1200
    options.extra['attempt'] = attempt + 1;
    try {
      handler.resolve(await _dio.fetch(options));
    } on DioException catch (e) {
      handler.next(e);
    }
  }
}
```

</CodeBlock>

### الـ token بتاعك راح لـ Open Library

قلنا Dio واحد للمشروع. بس Readly بيكلّم سيرفرين: الـ API بتاعنا، وOpen Library للكتالوج. لو الـ CatalogRemoteSource استخدم نفس الـ Dio بـ URL كامل (`https://openlibrary.org/search.json`)، الـ AuthInterceptor هيحط `Authorization: Bearer ...` على الطلب. يعني الـ access token بتاع المستخدم بيتبعت لسيرفر مش بتاعك، وبيتسجل في الـ logs بتاعته. ولو Open Library رجّع 401 لأي سبب، الـ interceptor هيعمل refresh لـ token مالوش علاقة بالموضوع.

القاعدة الصح: <b>Dio واحد لكل backend</b>، كل واحد بالـ base URL والـ interceptors بتوعه:

<CodeBlock label="di/network.dart">

```dart
Dio buildApiDio(AppConfig config, TokenStore tokens) {
  final options = BaseOptions(
    baseUrl: config.baseUrl, // per flavor: dev, staging, prod
    connectTimeout: const Duration(seconds: 10),
    receiveTimeout: const Duration(seconds: 15),
  );
  final dio = Dio(options);
  final refreshDio = Dio(options); // same server, no AuthInterceptor
  dio.interceptors.addAll([
    AuthInterceptor(tokens, refreshDio, dio),
    RetryInterceptor(dio),
  ]);
  return dio;
}

Dio buildOpenLibraryDio() {
  final dio = Dio(BaseOptions(
    baseUrl: 'https://openlibrary.org',
    connectTimeout: const Duration(seconds: 10),
    receiveTimeout: const Duration(seconds: 20),
  ));
  dio.interceptors.add(RetryInterceptor(dio)); // retries yes, our token never
  return dio;
}

// di/setup.dart
getIt
  ..registerLazySingleton<Dio>(() => buildApiDio(getIt(), getIt()), instanceName: 'api')
  ..registerLazySingleton<Dio>(buildOpenLibraryDio, instanceName: 'openLibrary')
  ..registerLazySingleton(() => LibraryRemoteSource(getIt<Dio>(instanceName: 'api')))
  ..registerLazySingleton(() => CatalogRemoteSource(getIt<Dio>(instanceName: 'openLibrary')));
```

</CodeBlock>

الـ `AppConfig` هو بتاع درس الـ flavors في الوحدة 6: كل environment ليه base URL، فمفيش URL مكتوب جوه أي data source. والـ data source مايعرفش هو واخد أنهي Dio، بياخد اللي اتبعتله في الـ constructor.

### الـ timeouts التلاتة مش زي بعض

| الـ timeout | بيقيس إيه | امتى بيضرب |
| --- | --- | --- |
| `connectTimeout` | فتح الاتصال بالسيرفر | السيرفر مش موجود أو النت مقطوع |
| `sendTimeout` | رفع الـ body | رفع صورة غلاف على نت ضعيف |
| `receiveTimeout` | الوقت لحد أول جزء من الرد، وبعدها بين كل جزء والتاني | السيرفر بطيء في الرد، أو سكت في النص |

الـ `receiveTimeout` مش الوقت الكلي للطلب. لو السيرفر بيبعت الرد حتة حتة ببطء، والفرق بين كل حتة والتانية أقل من 15 ثانية، الطلب ممكن ياخد دقايق ومايضربش. ولو endpoint معين محتاج وقت أطول (تصدير المكتبة كلها مثلًا)، غيّره للطلب ده بس:

```dart
await _dio.get<List<dynamic>>(
  '/library/export',
  options: Options(receiveTimeout: const Duration(seconds: 60)),
);
```

وفي مشكلة في الـ `_mapDio` بتاع درس الأخطاء: بيحوّل `connectionError` و`connectionTimeout` بس لـ NetworkFailure. الـ `receiveTimeout` والـ `sendTimeout` بيقعوا في الـ `_`، فبيبقوا ServerFailure. يعني المستخدم على نت ضعيف بيتقاله «في مشكلة في السيرفر»، وزرار «حاول تاني» ممكن يختفي. الاتنين دول من النت غالبًا:

```dart
DioExceptionType.connectionError ||
DioExceptionType.connectionTimeout ||
DioExceptionType.sendTimeout ||
DioExceptionType.receiveTimeout =>
  const NetworkFailure(),
```

### المستخدم كتب كلمة جديدة والطلب القديم لسه شغال

في درس الـ Pagination، الـ Cubit بيتجاهل نتيجة البحث القديمة بـ request id. ده بيحمي الشاشة، بس الطلب القديم لسه بيحمّل بيانات محدش هيشوفها. الـ `CancelToken` بتاع dio بيقفل الطلب نفسه. ومكانه الـ data source، لأنه الحتة الوحيدة اللي تعرف dio:

<CodeBlock label="CatalogRemoteSource بيلغي البحث القديم">

```dart
class CatalogRemoteSource {
  CatalogRemoteSource(this._dio);
  final Dio _dio;
  CancelToken _searchToken = CancelToken();

  Future<SearchPageDto> search(String query, {required int page}) async {
    if (page == 1) {
      _searchToken.cancel('replaced by a new search'); // old pages are useless now
      _searchToken = CancelToken();
    }
    final res = await _dio.get<Map<String, dynamic>>(
      '/search.json',
      queryParameters: {'q': query, 'page': page, 'limit': pageSize},
      cancelToken: _searchToken,
    );
    return SearchPageDto.fromJson(res.data!);
  }
}
```

</CodeBlock>

- <b>الـ page 1 بس هي اللي بتلغي:</b> صفحة 1 معناها بحث جديد أو refresh، فأي طلب للبحث القديم مالوش لازمة. الـ loadMore لنفس البحث بيستخدم نفس الـ token، فبيتلغي مع البحث بتاعه.
- <b>الطلب الملغي بيرجع DioException:</b> نوعه `cancel`، والـ guard بيحوّله Failure زي أي فشل. والـ Cubit بيتجاهله بالـ request id، لأنه نتيجة لطلب قديم.
- <b>الإلغاء مش بديل عن الـ request id:</b> ممكن الرد يكون وصل فعلًا قبل الـ cancel بجزء من الثانية. الإلغاء بيوفّر bandwidth، والـ request id هو اللي بيضمن إن الشاشة صح.

### الـ POST اتعاد والكتاب اتضاف مرتين

المستخدم ضاف كتاب، والطلب وصل للسيرفر واتنفذ، بس الرد ماوصلش (`receiveTimeout`). من ناحية الـ app، مش معروف الكتاب اتضاف ولا لأ. لو الـ SyncService بتاع درس Offline-first أعاد الطلب، الكتاب ممكن يبقى في المكتبة مرتين.

الحل <b>idempotency key</b>: الـ app بيعمل مفتاح فريد للعملية، ويبعته مع كل محاولة. السيرفر بيحفظ المفاتيح اللي شافها، ولو جاله نفس المفتاح تاني بيرجّع نفس الرد الأول من غير ما ينفذ تاني.

<CodeBlock label="المفتاح بيتعمل مع العملية، مش مع المحاولة">

```dart
// one more column in the sync queue table (Offline-first lesson):
// filled once when the op is inserted, then saved with it
TextColumn get idempotencyKey => text().clientDefault(() => const Uuid().v4())();

// data source: every attempt for this op sends the same key
Future<void> addBook(BookDto book, {required String idempotencyKey}) =>
    _dio.post<void>(
      '/library',
      data: book.toJson(),
      options: Options(headers: {'Idempotency-Key': idempotencyKey}),
    );
```

</CodeBlock>

الغلطة المشهورة إنك تعمل المفتاح جوه interceptor أو جوه `addBook`. كده كل محاولة بمفتاح جديد، والسيرفر يشوفهم طلبات مختلفة، والمفتاح مابيعملش أي حاجة. المفتاح لازم يتولد مرة واحدة ويتحفظ مع العملية في الـ queue، فيعيش حتى لو الـ app اتقفل واتفتح.

### الـ retry policy كاملة

دلوقتي الـ RetryInterceptor يقدر يعرف الـ POST الآمن، ويحترم السيرفر لما يقوله «استنى»:

<CodeBlock label="RetryInterceptor بيكبر">

```dart
class RetryInterceptor extends Interceptor {
  RetryInterceptor(this._dio, {this.maxAttempts = 3, Random? random})
      : _random = random ?? Random();
  final Dio _dio;
  final int maxAttempts;
  final Random _random;

  static const _transient = {
    DioExceptionType.connectionError,
    DioExceptionType.connectionTimeout,
    DioExceptionType.receiveTimeout,
  };

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    final options = err.requestOptions;
    final attempt = (options.extra['attempt'] as int?) ?? 0;
    final status = err.response?.statusCode;
    final safe = options.method == 'GET' || options.headers.containsKey('Idempotency-Key');
    final retryable = _transient.contains(err.type) ||
        status == 429 || status == 502 || status == 503 || status == 504;
    if (!safe || !retryable || attempt >= maxAttempts) return handler.next(err);

    final wait = _retryAfter(err.response) ?? _backoff(attempt);
    if (wait > const Duration(seconds: 30)) return handler.next(err); // too long to hold a spinner
    await Future.delayed(wait);
    options.extra['attempt'] = attempt + 1;
    try {
      handler.resolve(await _dio.fetch(options));
    } on DioException catch (e) {
      handler.next(e);
    }
  }

  // 300, 600, 1200 ms, plus up to 300 ms of random jitter
  Duration _backoff(int attempt) =>
      Duration(milliseconds: 300 * (1 << attempt) + _random.nextInt(300));

  Duration? _retryAfter(Response<dynamic>? res) {
    final seconds = int.tryParse(res?.headers.value('retry-after') ?? '');
    return seconds == null ? null : Duration(seconds: seconds);
  }
}
```

</CodeBlock>

- <b>الـ jitter:</b> لو السيرفر وقع دقيقة ورجع، كل الأجهزة هتعيد في نفس الـ 300ms بالظبط، وتوقّعه تاني. الرقم العشوائي بيفرّقهم. والـ `Random` بيتبعت في الـ constructor عشان التست يثبّته.
- <b>الـ Retry-After:</b> مع 429 (طلبات كتير) أو 503، السيرفر ممكن يقولك تستنى كام ثانية. لو الوقت ده طويل، الأحسن الـ Failure توصل للمستخدم بدل spinner دقيقة.
- <b>الـ 500 مش في الليستة:</b> غالبًا bug في السيرفر، ونفس الطلب هيوقعه تاني. الـ 502 والـ 503 والـ 504 معناهم إن السيرفر مش متاح دلوقتي، ودي ممكن تتحل لوحدها.


</Level>

<Level n="4" title="تفاصيل الـ production">

| الطلب | يتعاد تلقائي؟ | ليه |
| --- | --- | --- |
| GET | أيوه، للأخطاء المؤقتة | بيقرا بس، فتكراره مابيغيرش حاجة |
| PUT وDELETE | لو الـ backend بيطبّق معناهم صح | «خلّي الحالة كذا» و«امسح ده» نتيجتهم واحدة لو اتكرروا |
| POST وPATCH | بـ Idempotency-Key بس | من غيره ممكن العملية تتنفذ مرتين |
| أي 4xx غير 429 | لأ | الطلب نفسه غلط، وهيرجع نفس الرد |
| 401 | مش شغل الـ retry | الـ AuthInterceptor بيعمل refresh |

- <b>الكتابة في الـ offline-first:</b> الـ retry بتاع الـ interceptor عايش في الذاكرة، فلو الـ app اتقفل المحاولات بتضيع. إعادة الكتابة شغل الـ SyncService، لأن الـ queue محفوظة في الـ DB. والـ interceptor يخليه للقراية والطلبات اللي المستخدم مستنيها دلوقتي.
- <b>الإلغاء مكانه الـ data layer:</b> الـ `CancelToken` بتاع dio مايدخلش الـ Cubit عشان الـ Cubit مايعرفش dio. لو محتاج إلغاء، الـ data source يمسكه، زي البحث فوق.
- <b>الـ timeouts:</b> من غيرها الطلب ممكن يفضل معلّق دقايق على نت ضعيف، والمستخدم شايف loading للأبد. وdio مافيهوش timeout للطلب كله، فلو محتاج حد أقصى كلي، اعمله بـ CancelToken وTimer.
- <b>الـ logs:</b> الـ LogInterceptor بتاع dio بيطبع الـ headers كاملة، يعني الـ token. خليه في dev بس، والحل الكامل (interceptor بيخفي الحساس ويبعت لـ AppLogger) في درس الـ Observability.
- <b>ماتطفيش التحقق من الشهادة:</b> `badCertificateCallback = (cert, host, port) => true` بيحل مشكلة شهادة الـ dev server في دقيقة، وبيوصل للـ production بالغلط، وساعتها أي حد على نفس الـ WiFi يقدر يقرا ويعدّل كل الطلبات. ولو الـ backend شغال على جهازك بـ http: Android بيمنع الـ cleartext من API 28، وiOS بيمنعه بالـ ATS. افتح استثناء لـ `10.0.2.2` (الـ localhost من جوه الـ emulator) في نسخة الـ debug بس: `network_security_config` في `src/debug` على Android، وInfo.plist بتاع الـ debug على iOS.
- <b>الـ certificate pinning:</b> الـ app يقبل شهادة السيرفر بتاعك بس، حتى لو حد ركّب CA مزيفة على الجهاز. في dio بيتعمل في الـ `IOHttpClientAdapter`، والأحسن بـ `SecurityContext(withTrustedRoots: false)` وقت الـ handshake، لأن `validateCertificate` بيتنادى بعد ما الطلب نفسه (بالـ `Authorization` header) اتبعت. التفاصيل والكود في [درس الشبكة والـ threat model](/course/production/security-network/). التمن: لما الشهادة تتجدد، أي نسخة قديمة من الـ app هتبطّل تشتغل لحد ما المستخدم يعمل update، فلازم pin احتياطي وخطة تجديد. لـ app بنك يستاهل، لـ Readly غالبًا HTTPS عادي كفاية.

<Note kind="interview" title="سؤال interview">

«3 requests رجعوا 401 في نفس الوقت، إزاي تضمن refresh واحد؟» بـ Completer كـ lock: أول طلب يبدأ الـ refresh، والباقي يستنوا نفس الـ future، وبعدين كله يعيد بالـ token الجديد. والـ refresh بيتعمل بـ Dio منفصل عشان مايدخلش loop.

</Note>

<Note kind="interview" title="سؤال interview">

«إمتى تعمل retry لطلب فشل؟» لما الحاجتين يتحققوا: الفشل مؤقت (نت، timeout، 429، 502 لـ 504)، والطلب آمن يتكرر (GET، أو POST معاه Idempotency-Key اتولد مرة واحدة مع العملية). مع backoff بيكبر وjitter عشان الأجهزة ماتعيدش كلها مع بعض، واحترام Retry-After، وحد أقصى للمحاولات وللوقت. ومابعيدش 4xx أبدًا. والكتابة في app offline-first بيعيدها الـ SyncService من queue محفوظة، مش الـ interceptor.

</Note>

<Question id="network-4">
<Ask>`POST /library` ضرب `receiveTimeout`. الكتاب اتضاف على السيرفر ولا لأ؟ وتعيد الطلب إزاي من غير ما يتكرر؟</Ask>
<Answer>

مش معروف: الطلب ممكن يكون اتنفذ والرد بس اللي ماوصلش. تعيده بـ `Idempotency-Key` اتولد مرة واحدة مع العملية واتحفظ معاها، فالسيرفر يشوف نفس المفتاح ويرجّع الرد الأول من غير ما يضيف تاني. لو المفتاح اتولد مع كل محاولة، مالوش أي لازمة.

</Answer>
</Question>

<Question id="network-5">
<Ask>الـ CatalogRemoteSource بيستخدم نفس الـ Dio بتاع الـ API بـ URL كامل لـ Open Library. إيه المشكلة؟</Ask>

</Answer>
