آخر وحدة بتسأل أسئلة الـ senior: أنهي معمارية لأنهي feature، وإزاي تعرف إن الـ app بيقع في الـ production، وإزاي تصلّح كود قديم من غير ما توقّف الشغل، وإزاي تبني وتنزّل من غير ما تعتمد على جهاز واحد. Escore جاوب على كل سؤال فيهم، ساعات بقرار وساعات من غير.

### Clean ولا MVVM: الاتنين، من غير ما حد يقرر

درس «Clean ولا MVVM؟» قال إن القرار بيتاخد لكل feature: CRUD بسيط ياخد MVVM (Cubit بيكلّم repository)، وfeature فيها قواعد تاخد Clean كامل. لو بصيت على Escore هتلاقي القرار ده اتاخد، بس كل feature لوحدها:

| الـ feature | الشكل الفعلي | يناسبها؟ |
| --- | --- | --- |
| matches | MVVM: الـ Cubits بتكلّم `MatchesRepository`، وuse case واحد للـ vote | آه: قراية لايف، والقواعد في `domain/utils` مش في use cases |
| news | Clean كامل: 20 use case | زيادة: أغلبهم pass-through |
| tournaments | خليط: 7 use cases لـ 11 method | مش واضح |
| settings | MVVM، وجنبه domain Clean محدش بيستخدمه | MVVM مناسب، والـ domain لازم يتمسح |
| app_config | Clean كامل في 15 ملف | آه: صغيرة وفيها قاعدة مهمة (fail-open) |

يعني Escore طبّق الـ decision guide بتاع الدرس من غير ما يكتبه. والنتيجة إن أي حد جديد بيفتح feature مش عارف يقلّد أنهي واحدة. قرار H-16 في matches كان الوحيد اللي اتكتب بسببه («only those with real logic»). لو القرار ده كان اتكتب في `docs/` كـ ADR واتطبّق على باقي الـ features، كان الخليط ده بقى سياسة واضحة مش صدفة.

### الـ Observability

#### Crashlytics بيفرّق بين الـ crash والخطأ اللي الـ app بيعدّيه

ده أحسن كود production في المشروع، والسبب مكتوب جواه:

<CodeBlock label="lib/core/services/crash_reporting/crash_reporter.dart">

```dart
/// Wiring `FlutterError.onError` straight to `recordFlutterFatalError` (the
/// FlutterFire quick-start default) files the second group as *crashes*. That
/// is what drove crash-free users to ~97.6% on 1.2.2 while nothing ever
/// actually died: the top three "crashes" were a `PathNotFoundException` from
/// `cached_network_image`, a 30s `TimeoutException` from the YouTube iframe
/// bridge, and offline `SocketException`s from image downloads.
///
/// Nothing is silenced here — recoverable failures are still reported, just as
/// **non-fatal** with a `recoverable:<label>` reason.
abstract final class CrashReporter {
  static void install() {
    final crashlytics = FirebaseCrashlytics.instance
      ..setCrashlyticsCollectionEnabled(!kDebugMode);

    FlutterError.onError = (details) {
      final label = classify(details.exception, details.stack);
      if (label == null) {
        crashlytics.recordFlutterFatalError(details);
        return;
      }
      FlutterError.presentError(details);
      crashlytics.recordError(details.exception, details.stack,
          reason: 'recoverable:$label', printDetails: false);
    };
    // PlatformDispatcher.instance.onError: same classification
  }

  static String? classify(Object error, StackTrace? stack) {
    if (error is FileSystemException) return 'file-system';
    if (error is SocketException || error is HttpException ||
        error is TlsException || error is NetworkImageLoadException) {
      return 'network';
    }
    if (error is TimeoutException) return 'timeout';
    if (error is IOException) return 'io';
    // ...
  }
}
```

</CodeBlock>

درس الـ Logging والـ Monitoring قال: الـ metric لازم يقيس الحاجة اللي بتهمك. Escore شاف crash-free بينزل لـ 97.6% مع إن مفيش حاجة كانت بتقع فعلًا: صورة اتمسحت من الـ cache، أو فيديو YouTube مااتحمّلش، أو صورة مانزلتش من غير نت. الحل ماكانش إنهم يخبّوا الأخطاء دي. الأخطاء لسه بتتسجل، بس كـ non-fatal وجنبها label. كده رقم الـ crash-free بقى بيقيس الـ crashes الحقيقية، والضوضاء لسه موجودة لو حد عايز يدوّر فيها. والقرار نفسه في function صافية عليها تست.

وفيه كمان interceptor لـ Firebase Performance بيقيس كل طلب HTTP، وبيشتغل في الـ release بس.

#### اللي ناقص

- مفيش `setUserIdentifier` ولا breadcrumbs (`crashlytics.log`). لما الـ crash يحصل، مش هتعرف المستخدم كان بيعمل إيه قبله.
- الـ `BlocObserver.onError` بيطبع في الـ debug بس، ومابيبعتش لـ Crashlytics. فأي exception جوه Cubit بيتمسك ويختفي.
- الـ logs كلها (أكتر من 600 استدعاء لـ `logger()` و`LoggerHelper`) بتتشال في الـ release، ومفيش أي حاجة بتتبعت لأي مكان. ده كويس للخصوصية والأداء، بس معناه إن الـ release مالوش أي log.
- Firebase بيتعمله init في الـ splash مش في `main()`، فأي error قبل كده مش بيتسجل.

### الـ Refactor: الـ debt متوثّق ومترقّم

درس «Refactor feature قديمة لـ Clean» قال: ماتعملش rewrite، اتحرك خطوة خطوة وكل خطوة لوحدها بتطلع release. Escore بيعمل كده فعلًا، ودي الأدلة اللي في الكود:

- **risk register** في `docs/architecture/_inventory/` فيه 40 مشكلة مترقّمة بالسبب والحل.
- **TODOs بأرقام**: `TODO(TRN-M-11)` بيقول بالظبط إيه اللي ناقص («route through TournamentsRepository once a typed TournamentTeamEntity exists»)، و`TODO(dark-only)` بيعلّم كل مكان اتقفل فيه الـ light theme مؤقتًا، فلما يرجع هتلاقي كل الأماكن بـ grep واحد.
- **قرارات مرقّمة في الكومنتات**: `H-16` (شيل الـ use cases الفاضية)، و`M-17` (اكتب النتيجة اللايف في الـ cache).
- **feature flags compile-time** بتسمح إن الكود القديم والجديد يعيشوا مع بعض: `kUseTournamentFeed` بيقلب بين endpoint الماتشات القديم والجديد، والكومنت بيقول «the old code path is kept intact».

#### بس الـ refactor بيسيب حاجات وراه

```dart
/// Held at `false` for the store release: the feature is written end to end
/// but is not finished being reviewed ...
// TODO(news-comments): flip to true once the feature is signed off
const bool kNewsCommentsEnabled = true;
```

الكومنت بيقول `false`، والـ TODO بيقول «اقلبها `true` لما تخلص»، والقيمة `true`. يعني حد قلبها ومحدّثش الكومنت ولا مسح الـ TODO. ونفس الحاجة في 5 ملفات بتشاور على `lib/core/network/api_client.dart`، وده ملف اتشال في refactor قديم. الكومنت اللي بيكدب أسوأ من مفيش كومنت، لأن اللي بيقراه هيصدّقه. أي refactor لازم يدوّر بـ grep على اسم الحاجة اللي اتشالت قبل ما يخلص.

### الـ Release

| | الكورس (درس الـ Flavors والـ release) | Escore |
| --- | --- | --- |
| الـ environments | flavors + `--dart-define-from-file` | ملف `.env` واحد بيتعدّل بالإيد |
| الـ build | CI بيبني من tag | سكريبتات على جهاز المطوّر (`build-release.sh` و`.ps1`) |
| الـ checks قبل الـ build | analyze + test | مفيش |
| الـ hotfixes | release جديد | Shorebird: patch للـ Dart من غير ما يعدّي على الـ store |
| الـ signing | secrets في الـ CI | env vars أو `key.properties` محلي |
| الـ dependencies | versions متثبّتة | حوالي 65 dependency من غير version، والـ `pubspec.lock` هو اللي ماسكهم |
| الـ obfuscation | `--obfuscate --split-debug-info` | مفيش |

**Shorebird** هو أهم حاجة هنا: لو فيه bug في Dart، الفريق بيطلّع patch بيوصل للمستخدمين في دقايق من غير review الـ store. ده بيعوّض جزء من غياب الـ CI، لأن الغلطة بتتصلّح بسرعة. بس ماينفعش يبقى بديل عن إن الغلطة ماتوصلش أصلًا.

وفيه حاجات صغيرة بتوضّح ليه الـ CI مهم مش رفاهية:

- `build-release.sh` بيستخدم Flutter `3.44.1`، و`build-appbundle.sh` بيستخدم `3.41.4`. يعني الـ APK والـ AAB ممكن يكونوا مبنيين بنسختين مختلفتين.
- سكريبت الـ Windows بيزوّد رقم الـ build **قبل** الـ build، وسكريبت الـ Mac بيزوّده **بعد** ما ينجح. لو الـ build فشل على Windows، الرقم بيتحرق.
- لو مفاتيح الـ release مش موجودة، `build.gradle.kts` بيبني بمفتاح الـ debug من غير أي error. والـ store هيرفضه وقت الرفع، بس بعد ما الوقت ضاع.

```kotlin
signingConfig = if (hasReleaseSigning) {
    signingConfigs.getByName("release")
} else {
    signingConfigs.getByName("debug")
}
```

القاعدة: الـ release build لازم يفشل بصوت عالي لو ناقصه حاجة، مش يكمّل ببديل ساكت.

### الأمان: التخزين والأسرار والشبكة

درس «الأسرار والتخزين الحساس» ودرس «الشبكة والـ threat model» قالوا: اعمل جرد بكل مكان البيانات عايشة فيه، ومفيش secret في الـ app، والـ logs ماتطلّعش حاجة. Escore عامل أغلب الإعدادات صح، والمشاكل كلها في الحتت اللي «مؤقتًا» أو «للتوافق مع القديم».

#### الـ secure storage بإعداد الدرس بالظبط، ونسخة plaintext جنبه

<CodeBlock label="lib/core/storage/secure_storage.dart">

```dart
factory FlutterSecureStorageImpl.withDefaults() {
  return FlutterSecureStorageImpl(
    androidOptions: const AndroidOptions(),
    iosOptions: const IOSOptions(
      accessibility: KeychainAccessibility.first_unlock_this_device,
    ),
  );
}
```

</CodeBlock>

ده نفس الإعداد اللي في الدرس: Keystore في Android، و`first_unlock_this_device` في iOS. والـ refresh token بيتحفظ هناك بس، والسبب مكتوب في الكود نفسه:

<CodeBlock label="lib/core/api/dio_consumer/auth_interceptor.dart">

```dart
// Save to SecureStorage (primary, secure)
await secureStorage.write(StorageKeys.accessToken, accessToken);

// Save to legacy storage (for backward compatibility with DioConfigurator)
await _cacheManager.setData(
  key: StorageKeys.keyTokenUser,
  value: accessToken,
);

// Save refresh token if provided.
//
// SecureStorage only — never mirror this into SharedPreferences. Unlike
// the access token below, nothing needs the refresh token synchronously,
// and a plaintext copy survives logout and can revive the session.
```

</CodeBlock>

يعني الفريق عارف إن النسخة الـ plaintext خطر، وطبّق ده على الـ refresh token، وساب الـ access token يتكتب في SharedPreferences (`jwt_token`) في الـ login والـ refresh، عشان الـ router guards بتقراه sync. والـ `DioConfigurator` بيرجع للنسخة دي لو الـ secure storage فاضي. ومفيش `dataExtractionRules` ولا `allowBackup` في الـ manifest، فالـ default (`true`) شغال، والـ prefs دي بتدخل في الـ Auto Backup.

الـ access token عمره قصير، فالضرر أقل من الـ refresh. بس الجدول بتاع الدرس بيقول إن الـ secure storage بيحمي من الـ backups والموبايل المقفول، والنسخة الـ plaintext بتلغي الحماية دي للـ token اللي بيتبعت مع كل طلب. الحل نفس اللي في درس الـ Session: الـ guards تقرا حالة الـ session من الذاكرة (الـ AuthCubit)، مش من ملف، والنسخة القديمة تتمسح في أول فتحة بعد الـ update.

#### الـ logout: منظم، وفيه أماكن اتنست

الـ `AuthRepositoryImpl.logout()` بيعمل الحاجات الصعبة صح: الطلبات للسيرفر (unregister للجهاز، وlogout، وGoogle signOut) بالتوازي وبحد 4 ثواني، وبعدين المسح المحلي من غير ما يستنى. و`clearAll()` بيمسح مفاتيح المستخدم كلها، والكومنت بيقول ليه: «the previous user's avatar and name persist and leak into the next session». و`HttpCache.clear()` بيمسح الـ responses المتخزنة.

اللي فاضل بعد الـ logout، بالجرد اللي في الدرس:

| الأثر | فين |
| --- | --- |
| الـ Hive boxes بتاعة الـ offline cache | `OfflineCacheService.clear()` موجودة ومحدش بيناديها |
| الصور على الـ disk | مفيش `DefaultCacheManager().emptyCache()` في أي حتة |
| الـ FCM token عند Firebase | `FirebaseMessaging.deleteToken()` مش متنادية خالص |
| الـ Keychain بعد إعادة التسطيب في iOS | مفيش علامة first-run بتمسحه |

السطر الأخير ليه أثر حقيقي من قراية الكود: بعد ما المستخدم يمسح الـ app وينزّله تاني، الـ prefs راحت فالـ router شايفه مش داخل، بس الـ `DioConfigurator` بيقرا `access_token` من الـ secure storage الأول. فالطلبات اللي بتحصل قبل ما يختار login أو guest (زي الـ startup check) ممكن تطلع بـ token الحساب القديم. ده بالظبط سبب الـ `clearIfReinstalled` في درس الـ Session.

#### الـ `.env` جوه الـ APK، بالكومنتات

```yaml
# pubspec.yaml
flutter:
  assets:
    - .env
```

الـ `.env` في الـ `.gitignore` ومااتعملوش commit قبل كده، وده كويس. بس هو asset، يعني ملف نص مقروء جوه كل APK وIPA، زي ما درس الـ release قال على flutter_dotenv. المفاتيح نفسها مش secrets (`BASE_API_URL` و`GOOGLE_CLIENT_ID` و`IOS_APP_STORE_ID`، والـ client id بتاع Google معمول عشان يبقى في الـ client). المشكلة إن الملف كله بيتشحن، <b>بالكومنتات</b>: سطر قديم متعلّق فيه إيميل وباسورد حساب الـ reviewer بتاع الـ store، وده موجود في الـ release build. أي حد يفك الـ APK يقراه في دقيقة.

ده الصف «إحنا نفسنا بالغلط» في الـ threat model، والأرخص في التصليح: الباسورد ده يتغير، والـ config يتنقل لـ `--dart-define-from-file` (بيقرا القيم بس، مش الكومنتات)، والـ `strings` check بتاع الدرس في الـ CI يدوّر على الإيميلات كمان.

وملفات Firebase (`firebase_options.dart`، و`google-services.json`، و`GoogleService-Info.plist`) في الـ repo، وده الطبيعي زي ما الدرس قال، بشرط إن المفاتيح متقفلة من الـ console.

#### الشبكة: الأساس صح، والـ logs فيها ثغرات صغيرة

الـ SSL bypass بتاع سيرفر الـ dev معمول زي ما الدرس قال بالظبط: شرطين، وassert:

<CodeBlock label="lib/core/api/dio_consumer/dio_configurator.dart">

```dart
/// Opt-in compile-time flag for SSL certificate bypass.
/// Build with `--dart-define=ALLOW_SSL_BYPASS=true` to enable in debug mode.
static const bool _allowSslBypass = bool.fromEnvironment(
  'ALLOW_SSL_BYPASS',
);

static void configure(Dio dio) {
  // SSL bypass requires BOTH kDebugMode AND the explicit --dart-define flag.
  // This ensures it NEVER runs in release builds and is off by default in debug.
  if (kDebugMode && _allowSslBypass) {
    // ...
    _setUpCertificateBypass(dio);
  }
```

</CodeBlock>

ومفيش pinning، وده قرار معقول لـ app نتايج رياضية بالـ threat model بتاع الدرس. والـ cleartext مفتوح في `src/debug/AndroidManifest.xml` بس. والـ logs بتخفي الـ `Authorization` والـ query keys الحساسة (`token`، `password`، `otp`)، وكلها ورا `kDebugMode`. اللي فاتهم:

- <b>الـ request body مش متفلتر:</b> `'\n📦 Body: ${_formatData(options.data)}'` بيطبع باسورد الـ login والتسجيل في الـ debug console. ده debug بس، بس الـ screenshots والـ logs اللي بتتلزق في issues بتطلع برّه الجهاز.
- <b>`print` من غير `kDebugMode`:</b> في `deep_link_handler.dart` و`widget_interaction_service.dart`، بـ `// ignore: avoid_print`. بيطبعوا URIs مش tokens، بس الـ `print` بيوصل الـ logcat في الـ release.
- <b>الـ document بيقول عكس الكود:</b> `PLAY_STORE_RELEASE.md` فيه «No debug logging in release (all gated on `kDebugMode`)» متعلّم عليه، والـ `print` دي بتقول غير كده. نفس حكاية `kNewsCommentsEnabled`: الكلام اللي جنب الكود لازم يتحدث معاه.
- <b>الـ JWT في الـ query بتاع الـ WebSocket:</b> `'$baseUrl?matchId=$matchId'` وبعدها `'&token=$token'`. Escore بيخفيه من الـ logs بتاعته، بس الـ query بيتسجل في access logs بتاعة أي proxy أو load balancer في النص. لو الـ backend قبل الـ token في أول رسالة بعد الاتصال، الـ URL مايبقاش فيه حاجة.

### الـ Feature flags: compile-time، والـ runtime config موجود ومش مستخدم ليها

درس الـ Feature Flags فرّق بين flag بيتقفل بـ release وflag بيتقفل من الـ console. Escore عنده النوع الأول بس:

| الـ flag | القيمة | الحالة |
| --- | --- | --- |
| `kUseTournamentFeed` | `true` | الكومنت بيقول «Flip to `false` to fall back ... if the new endpoint misbehaves in production»، يعني kill switch محتاج build جديد |
| `kNewsCommentsEnabled` | `true` | الكومنت والـ TODOs بيقولوا غير القيمة (فوق في جزء الـ Refactor) |
| `kLiveActivityEnabled` | `false` | كل كود الـ Live Activities ميت ورا الـ flag ده |

ومفيش `firebase_remote_config`. Shorebird بيقرّب المسافة: قلب `kUseTournamentFeed` بقى patch مش release من الـ store. بس الـ patch build، وبيوصل في الفتحة الجاية أو اللي بعدها، مش في ثواني والـ app مفتوح.

المثير إن Escore عنده بالفعل الأساس اللي الدرس بيبنيه، بس لحاجة تانية: الـ `app_config` feature.

<CodeBlock label="lib/features/app_config/data/repositories/app_config_repository_impl.dart">

```dart
// Fail-open: the startup gate must never block boot. Any failure (offline
// with no cache, parse error, server error) degrades to a safe
// "up to date / no maintenance" verdict.
return result.fold(
  (_) => const Right<Failure, StartupConfigEntity>(
    StartupConfigEntity.safeDefault(),
  ),
  Right<Failure, StartupConfigEntity>.new,
);
```

</CodeBlock>

- <b>contract في الـ domain</b> (`AppConfigRepository`) وimplementation في الـ data، زي `FeatureFlags`.
- <b>قيمة افتراضية آمنة</b> (`safeDefault`) لو مفيش نت أو السيرفر واقع، زي الـ `fallback`.
- <b>cache</b> في Hive لمدة 5 دقايق، و<b>timeout</b> 4 ثواني في `StartupCheckCubit`، وأي exception بيرجع للـ default.
- <b>بيبعت الـ platform والـ build والـ version والـ locale</b>، يعني السيرفر يقدر يرد بقيم مختلفة لكل نسخة.

الفرق عن الدرس إن الـ startup بيستنى الطلب ده (لحد 4 ثواني)، ومش بيستخدم قيم الفتحة اللي قبلها. ده مبرر هنا: الـ force update والـ maintenance لازم يبقوا حاليين. والمكان الطبيعي للـ kill switches في Escore هو نفس الرد ده: `features` فيها `tournament_feed` و`news_comments`، ورا interface `FeatureFlags`، والـ `safeDefault` فيه الـ fallbacks. ده الاختيار اللي الدرس سمّاه «endpoint بتاعك» في Level 4، والـ endpoint موجود خلاص.

<CodeBlock label="lib/core/config/feature_flags.dart">

```dart
/// Flip to `false` to fall back to the legacy path verbatim if the new
/// endpoint misbehaves in production — the old code path is kept intact.
const bool kUseTournamentFeed = true;
```

</CodeBlock>

والـ flags التلاتة مالهمش تاريخ نهاية: `kUseTournamentFeed` فرعه القديم ميت عمليًا من ساعة ما بقى `true`، و`kLiveActivityEnabled` شايل feature كاملة مش شغالة. الـ `removeBy` والتست اللي بيوقع في الدرس معمولين للحالة دي بالظبط: الـ flag يا يتمسح يا حد يكتب ليه لأ.

### لو هنبدأ Escore من جديد

ده ملخص كل دروس «في Escore» في قايمة واحدة، بالترتيب اللي هتعمله بيه في مشروعك:

1. **من أول commit**: CI بيشغّل analyze وtest، وlint بيمنع الـ domain يعمل import لـ Flutter أو data، وفيه feature مش مسموحلها تعمل import من feature تانية.
2. **قبل أول feature**: `sealed class Failure` بالبيانات بس من غير ترجمة، وmapper واحد من الـ exceptions، و`ApiConsumer` متسجّل كـ interface.
3. **قاعدة مكتوبة**: use case بس لو فيه قاعدة أو بيجمع أكتر من repository، وBloc بس لو الأحداث ليها قواعد ترتيب. والقواعد دي في `docs/` كـ ADR.
4. **constructor injection بس**، و`sl` جوه ملفات الـ DI والـ routes بس.
5. **flavors** من أول يوم، والـ `.env` فيه config عام بس.
6. **Crashlytics** بالـ classifier بتاع Escore بالظبط، ومعاه user id وbreadcrumbs، والـ BlocObserver بيبعتله.
7. **التخزين والأسرار**: config بـ `--dart-define-from-file` مش `.env` asset، والـ tokens في الـ secure storage بس، وجرد بكل مكان بيتمسح في الـ logout، وعلامة first-run للـ Keychain.
8. **الـ kill switches في رد الـ startup check** ورا `FeatureFlags`، وكل flag ليه تاريخ مسح.
9. **خليك على اللي Escore عمله صح**: الهيكل، والـ interceptors، وsingle-flight refresh، و`RefreshZone`، والـ startup gate الـ fail-open، والـ logout اللي مايخليش المستخدم يستنى، والـ risk register.
